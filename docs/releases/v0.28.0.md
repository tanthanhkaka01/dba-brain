## What this release is for

**Two things v0.27.0 got wrong are put right, and Oracle and PostgreSQL are reported in the metrics
they have.**

v0.27.0 began refusing a `common.cli` request whose value disagrees with its reference - and the
reference described two fields wrongly. Every SQL Server task that takes a parameter was refused, a
forced run of a SQL task over Telegram was refused after its `yes`, and so were the bot's own
emergency commands: `/spbot_kill_spid`, `/spbot_shrink_log`, `/spbot_start_job`,
`/spbot_disable_job` and `/spbot_restart_server`. All of them run again.

`LOCK_TRANSACTION_HOLDERS` enumerates the lock manager, and on a server where one transaction held
over a million locks that scan became the head of 68 waiting sessions. It now reads how many locks
are in use first and, above a limit, does not scan: it says so, at CRITICAL, and names the sessions
most likely to hold them.

Both report pages were written around SQL Server's metrics. An Oracle or PostgreSQL server now
states who and what it is, and what it collects under its own names reaches the fleet page and the
per-server page.

## Added since v0.27.0

- **An Oracle or PostgreSQL server says who and what it is.** `INSTANCE_STATUS` carried nineteen
  facts for SQL Server, two for Oracle and three for PostgreSQL. Oracle now states its machine,
  edition, full banner, database and unique name, role, open mode, log mode and archiver, platform,
  character set, RAC and start time (8i: what 8i has); PostgreSQL its build, platform, role, address
  and port, SSL, encoding, the connected database's collation, WAL level and archive mode, time
  zone, `max_connections` and start time. Each under its engine's own name - nothing is borrowed
  from SQL Server's vocabulary, and a fact an engine does not have gets no row. No new privilege.
- **An Oracle or PostgreSQL server is reported in the metrics it has.**
  - *Fleet page, server detail*: one row per engine metric, in the collector's own words - for
    Oracle the sessions and processes against their limits, dead sessions, tablespace free space,
    pool free memory, buffer cache hit ratio, rollback contention, invalid objects, unusable
    indexes, the index inventory, the largest segments; for PostgreSQL the wraparound horizon, dead
    tuples awaiting vacuum, bloat, long transactions, database activity, replication and slots, the
    WAL archive, invalid indexes. An Oracle database gains a size and a recovery model (its log
    mode).
  - *Per-server page*: nine health tiles for those questions, each shown only on the engine that
    has the metric. A SQL Server page is unchanged.
- **`sql_settings`: a metric's SQL can take a number from configuration.** A metric definition may
  state `"sql_settings": {"name": number}`, and the number is written into the
  `DECLARE @name <type> = <default>;` its SQL file carries. Only a number, only into a name the file
  declares; anything else fails the metric with the reason. `LOCK_TRANSACTION_HOLDERS` is the first
  to use it (`lock_scan_skip_above`, 500000).
- **The project has a page of its own: <https://dbabrain.dev/>.** The package's `Homepage` on
  PyPI leads there; `Repository` and `Changelog` still lead to GitHub. The README shows four
  screenshots of the showcase pages and two diagrams, and gains a *What it does* table, a *How it
  works* section and how to reach the maintainer. The pictures are in `docs/img/` and travel in the
  source distribution.

## Changed / breaking

- **`authorized_by` is an object on every request that carries it** - `authorize`, the emergency
  operations (`shrink-log`, `kill-spid`, `start-job`, `disable-job`), the host operations, the
  `sqlserver-*` patch and instance commands, and `run-cmd`. It is what the confirmation gate has
  always read (`{"channel": "telegram"}`); the reference said text. **Text there is now refused**
  with the field named - see *Upgrading* 1.
- **`LOCK_TRANSACTION_HOLDERS` can answer `lock_scan_skipped`.** Above the limit the metric returns
  one CRITICAL row under that item, and up to six rows `SPID=n` whose value is the session's log
  records, not a lock count - the largest writer and the oldest open transaction CRITICAL, the rest
  WARNING. Below the limit its rows are what they were. See *Upgrading* 2.
- **On the fleet page, a number that was not collected is a dash**, with a neutral badge - not `0`.
  The session count is the collector's own value on every engine; for Oracle it had been only the
  sessions whose status is `ACTIVE`, so that number rises. A PostgreSQL database shows no
  compatibility level where it showed `0`.
- **On the per-server page, a tile with no row says which of three things is true**: `OK - none
  found` where its collector reports only trouble and ran clean, *no such metric* where the engine
  has none (TempDB on PostgreSQL), and *not collected* only where something could have been.
  Blocking and Long-running queries read *not collected* on every Oracle and PostgreSQL page.

## Fixed since v0.27.0

- **A request the tool writes itself is no longer refused.** The reference described `run-sql`'s
  `prelude` as an array - it is SQL text - and `authorized_by` as text. On v0.27.0 that refused,
  with *The request does not match its reference* and nothing run: every SQL Server task that takes
  a parameter; a forced run of a SQL task over Telegram (`/spbot_run_sql_task`), after the `yes` was
  given; and the bot's `/spbot_kill_spid`, `/spbot_shrink_log`, `/spbot_start_job`,
  `/spbot_disable_job` and `/spbot_restart_server`. Held from now on by
  `tests/test_what_the_apps_send_is_what_the_reference_accepts.py`, which hands every request a
  shipped bot command writes, and the requests the SQL task runner builds, to the check `common.cli`
  applies.
- **`LOCK_TRANSACTION_HOLDERS` no longer scans a lock manager that is too large to scan.** The
  metric reads `sys.dm_tran_locks` whole, which latches the lock manager; with over a million locks
  held by one transaction its scan outlived the 60-second timeout and became the head of 68 waiting
  sessions. It reads the number of locks in use first, from a performance counter, and above
  `sql_settings.lock_scan_skip_above` does not scan. It names the sessions most likely to hold the
  locks - the open transactions, largest first by log written, and the oldest - each with its
  login, host, client address, program and database. SQL Server 2008 R2 has the same guard.
- **The fleet page no longer prints a zero for a number nobody measured.** An Oracle or PostgreSQL
  server showed *PLE 0* - page life expectancy is SQL Server's metric - under a red badge, and an
  Oracle 8i instance *0 sessions* while holding hundreds: its collector counts under
  `session_count` and the page asked for `server`.
- **An Oracle 8i server's machine name is shown.** It was collected since the 8i variant existed
  and never printed: the variant wrote `host=` and the page read `machine=`.
- **`build-showcase` takes its `extra_terms` again.** The reference described the field as an
  array; `build-showcase` reads it as an object of term to kind (`{"SITECODE": "database"}`), and
  so does the shipped `data/showcase.example.json`. On v0.27.0 `build-showcase @data/showcase.json`
  was refused before it read a page. Found refreshing the showcase for this release. Held by the
  same test file, which now also reads the request files the repository ships.
- The answer every command returns has seven keys, not five: `docs/13_common.md` and the README
  print `error_kind`, which v0.26.0 added.

## Known not to work

- Everything listed for v0.27.0 still holds.
- **The lock-scan guard needs the lock counters.** On an instance where
  `sys.dm_os_performance_counters` reads 0 for `Lock Owner Blocks` the guard reads 0 and the scan
  runs as it always did.
- **A skipped scan names likely holders, not lock counts.** Who holds how many locks cannot be
  counted without the scan; the ranking is by log written, with the oldest open transaction beside
  it.
- **Oracle from 10g on has no collector for the process limit, tablespace free space, the pools,
  the buffer cache or rollback contention** - those are 8i files - so its pages gain only what it
  collects. MySQL's pages are unchanged.
- The README's pictures are named by their URL in the public repository, so that PyPI can show
  them; a copy of the README read offline shows their captions only.

## Upgrading

From v0.26.0 or earlier, read v0.27.0's *Upgrading* first.

1. **Your own scripts that call an emergency, host, patch or `run-cmd` command and send
   `"authorized_by": "a name"`**: send an object instead, for example
   `"authorized_by": {"channel": "ops"}`, or leave the field out. Text was never read, and is now
   refused with `error_kind: request` naming the field.
2. **If you alert on `LOCK_TRANSACTION_HOLDERS`**: expect a new CRITICAL item, `lock_scan_skipped`,
   when an instance holds 500,000 locks or more. To use another limit, add
   `"sql_settings": {"lock_scan_skip_above": <number>}` to that metric in your
   `data/metric_definitions.json`; without the field the metric runs with the default in its file.
3. Nothing else: the new `INSTANCE_STATUS` facts and the report rows appear with the first
   collection after the upgrade.

`SCHEMA_VERSION` is unchanged, so the store needs nothing.

```bash
pip install --upgrade dbabrain
python -m db_ops.common.cli upgrade-config '{}'                   # read the plan
python -m db_ops.common.cli upgrade-config '{"dry_run": false}'   # then apply it
```
