## What this release is for

`v0.9.0` added an uptime line to `self-status` and it was the machine's. The question people ask
`self-status` is about the **installation** — how long has DBA Brain been up here — and that is the
one it could not answer. Patch rather than minor because this corrects the answer 0.9.0 gave rather
than adding a capability the toolkit did not have.

Both are reported now, because they are different facts and a reader wants a different one
depending on why they asked:

```
uptime    : 165.85 h  (host up since 2026-08-29T10:30:17Z)
db_ops up : 2.35 h  (since 2026-09-05T07:53:06Z)
```

A node whose daemon restarted an hour ago sits on a host that has been up for a week. Printing one
of those as "uptime" answers whichever question the reader did not ask.

## Added since v0.9.0

- **`db_ops up` in `self-status`** — how long the daemon of *this tool root* has been running.

  `self-status` structurally could not see this: the process answering is the short-lived one the
  bot spawned to ask, not the scheduler, and it opens no store on purpose — it is the one status
  that still answers when the store is what is down. So the daemon leaves a small JSON file in
  `runtime/`, written at startup and removed on a clean stop.

  **The pid is what makes the file trustworthy.** A hard kill leaves it behind, and a reader that
  believed the timestamp alone would report a daemon as up since a stop three days ago — the most
  confident possible way to be wrong about the one thing the line exists to say. Four distinct
  answers rather than two:

  | | |
  | --- | --- |
  | `running` | the pid is alive; hours and start instant reported |
  | `not running (no daemon has started in this tool root)` | no file — stopped cleanly, or never run here |
  | `not running (last start …, pid … is gone)` | a file whose pid is dead: it died **without unwinding**, which is worth saying |
  | `unknown` | the caller did not supply a runtime directory |

## Fixed since v0.9.0

- **`daemon --once` left its state file behind.** A single pass returns from inside the loop and
  missed both shutdown paths, so the file stayed with a pid that was about to die and the next
  reader would have called it `stale` — a daemon that died without unwinding, which is the opposite
  of what a deliberate single pass is.

## Changed / breaking

Nothing an existing tool root must do. `self-status`' envelope gains `data.db_ops_uptime`
(`status`, `hours`, `since`, `pid`, and `version` / `node_role` when running). The daemon writes
`runtime/daemon_state.json`; it is generated state, never configuration, and is not carried in a
config bundle.

Two internal moves, both re-exported so no import breaks:

- `is_pid_alive` / `is_windows_pid_alive` / `is_zombie` moved from
  `db_ops.telegram.command_processor` to the new `db_ops.lib.process_liveness`, because `common`
  needed them and may not import an app. `command_processor` re-exports them under the private
  names it already used.
- The new `db_ops.lib.daemon_state` owns the file's shape, so the app that writes it and the
  reader that consumes it agree without either importing the other.

Nine tests for the state file, and the whole lifecycle exercised against a **real daemon** rather
than only in unit tests — because what is being claimed is the behaviour of a process, and no
fixture is one:

```
while running        {'status': 'running', 'since': '2026-09-05T08:07:49Z', 'pid': 21864}
after taskkill /F    {'status': 'stale',   'since': '2026-09-05T08:07:49Z', 'pid': 21864}
after daemon --once  no file
```

That run also settled which pid to record. The file holds `os.getpid()` read from inside the
scheduler loop, which on Windows is **not** the pid `Start-Process` hands back — 21864 against
4544 for the same daemon. A pid written from outside names the launcher shim, and a liveness check
against it would answer for the wrong process.

## Known not to work

- **The line reads `not running` until the daemon is restarted on this version.** A daemon already
  running from an earlier build never wrote the file; that is an accurate report of what can be
  seen, not a defect, and it resolves on the next restart.
- Everything listed as open in `v0.9.0` is still open: `run_copy_backup` ignores `dry_run`; a
  reports directory the process cannot write leaves the fixed latest URL 404; nothing outside
  db_ops notices db_ops being absent; an app command's `error_text` carries the exit code and not
  the reason.
