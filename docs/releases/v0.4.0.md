# v0.4.0 — every app runs from a clean install, and a schema copy between instances

| | |
| --- | --- |
| Date | 2026-08-24 |
| Previous | `v0.3.3` |
| Python | 3.12, 3.13 |
| Artifacts | PyPI wheel + sdist, `ghcr.io/tanthanhkaka01/dbabrain:0.4.0` |

## What this release is for

`v0.3.3` shipped all fourteen packages, and six of them could not complete a single scheduled cycle
on a fresh install. This release is the difference between *present* and *working*: every app was
run from an empty virtualenv with nothing configured but one database, and everything that failed
was fixed.

It also adds the first new capability since the migration began — `copy-schema`, which reproduces
one SQL Server schema on another instance.

## Fixed since v0.3.3

Every one was found by installing the artifact and running it. All of them passed the full suite.

- **The web console showed no apps at all.** Five zeroed tiles and "nothing is failing" — which is
  what a *healthy* console looks like, so it did not read as a fault. The console reads its layout
  from `webhost_config.json` through the config store, `db-ops init` never wrote that file, and the
  repair (`db sync-config`) refused because `data/config_catalog.json` was missing too. It could
  neither be populated nor say why. Both files ship now, and an empty dashboard names the command
  that fills it. *Proof: fresh wheel → init → sync-config (148 rows) → all 14 apps listed, all 15
  console pages HTTP 200.*

- **`db-ops daemon --once` never returned.** The default schedule had the **web console** active,
  and `--once` waits for started commands to finish — a server never finishes. *Proof: 2.2 seconds
  and 6 commands, against an indefinite hang before.*

- **`sla validate` and `sql-tasks` could not start.** Each opens a config file before deciding it
  has nothing to do, so a missing one is a crash. `sla_policies.json` is product data and now
  ships; `sql_commands.json` and `sql_targets.json` are estate data and now scaffold **empty**.

- **Telegram failed once per second on a correct install.** `init` writes the token ref as a
  template, so the shipped nothing-is-wrong state is a ref pointing at a secret nobody has added.
  That raised — and took `APP-CONTROL` down with it, which reports through the same chat. No token
  and no groups are now *states*: both skip and say what is missing.

- **`ops-status` was broken on Windows.** Its scheduled command wrapped the request in single
  quotes, which is POSIX syntax; `cmd.exe` passes the apostrophes through and the JSON arrives
  mangled, so it exited 2 on every run. The payload moved to a file, which needs no quoting in
  either shell.

- **`control inventory-summary` crashed** with `FileNotFoundError` out of `pathlib.open` for a file
  that is *generated*. It now names the file and the two commands that build one.

- **The export could publish work nobody had finished.** It copies the working tree, and did once
  ship five modules another session was mid-way through writing. `build_plan` now asks git which
  files it is about to ship are uncommitted and prints them.

- **Real database and instance names in shipped examples.** Three of them reached the
  `copy-schema` docstrings and tests from the feature request, which was written from the
  deployment that produced it. Replaced with neutral names that make the same point. Caught by
  the export's identifier gate — an earlier export of the same files had reported clean, so
  nothing else would have.

## Added since v0.3.3

- **`db-ops common copy-schema`** — reproduce one SQL Server schema on another instance. Nine
  phases in dependency order (partitioning → change tracking → tables → per-table tracking →
  indexes → checks → data → modules → foreign keys), every phase idempotent so an interrupted run
  resumes by being re-run, `sp_getapplock` around the whole operation, a destination assertion
  beyond `DB_NAME()`, client-side batched data copy with `IDENTITY_INSERT`, and a report of what
  catalogue-based scripting silently drops. `plan` is the default posture; nothing is written until
  `"plan": false`.

## Changed / breaking

- **The default schedule ships six commands active, three off.** Backup/restore and the inventory
  workflow need estate configuration; the web console is a server and should not be daemon-managed.
  Each carries a note saying what to configure. **An existing `data/app_commands.json` is not
  touched** — this changes only what a new `db-ops init` writes.
- `db-ops init` writes **17 files**, up from 12.
- Nothing else requires action from an existing installation.

## Known not to work

- **PyPI and GHCR artifacts are not published yet.** CI is green on the release commit and the
  clean-room run reached `status=done` on every scheduled command, but the wheel and the image are
  produced by *publishing the GitHub Release* — a web-UI step the operator takes. Until then §3.7's
  external checks (install from PyPI, pull the image) cannot be run.
- **`G-06` is not met and cannot be self-certified**: a first run by somebody who is not the author.
  Everything else in that gate is met.
- **`copy-schema` has never been run against two real SQL Server instances.** Its 49 tests are
  offline, against fake cursors. The phases, ordering and idempotence are asserted; the behaviour
  against a live pair is not.
- **The web console has only been verified against a locally built wheel**, not one installed from
  PyPI.
- Backup/restore, the inventory workflow and the SRE app are present and documented but were only
  smoke-tested (their commands return 0); no full workflow was executed.
