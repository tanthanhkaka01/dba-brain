## What this release is for

One line added to `db-ops common self-status` (`/spbot_self_status` in the bot). The report already
said which build you are talking to, on which machine, and how much room is left. It did not say how
long any of it had been standing — which is the second question asked when something looks wrong,
and the one that lines an installation up against an incident or a deploy.

Minor rather than patch because it is an addition, not a correction: `data.uptime` is a new key in
the JSON envelope, so a program reading that answer sees a surface it did not see before.

## Added since v0.8.1

- **`uptime` in `self-status`**, as two figures, because one is not enough:

  ```
  uptime    : 165.01 h  (host up since 2026-08-29T10:30:17Z)
  ```

  Hours to two places answer *"has this been up long enough to trust what it says"*; the instant
  answers *"since when"*, which is the half that can be compared against another node, a deploy or a
  timeline. UTC, like every other timestamp in this toolkit — an estate spans machines and a
  local-time answer cannot be compared with anything.

  Read from `/proc/uptime`, falling back to `GetTickCount64` on Windows: one call, no privilege, and
  no WMI process to spawn or local-time string to parse. A platform that can answer neither reports
  `unavailable` rather than `0`, the rule the whole module follows.

  **The line says "host up since", not "up since".** This is the machine's clock and not the
  daemon's. `self-status` reads *itself*, and the process reading is the short-lived one the bot
  spawned to ask — not the scheduler; whether the scheduler has been running is `ops-status`, which
  reads the store. On a node whose daemon restarted an hour ago the two numbers are nothing like
  each other, and a bare "uptime" would be read as the one the reader came for.

  Inside a container `/proc/uptime` is the **host's** clock again, so the source travels with the
  number — measured at 163.30 h in a container against 165.01 h on the Windows machine under it.

## Changed / breaking

Nothing an existing tool root must do. `self-status`' JSON envelope gains `data.uptime`
(`seconds`, `hours`, `since`, `source`); nothing was removed or renamed.

Six tests. One of them nearly recorded the wrong verdict about this very change: after reverting the
`.2f` format to `.1f` to prove the test could fail, restoring the correct file left the test still
failing — the two versions differ by one character and are therefore **the same size**, so the copy
did not move the mtime far enough for Python to invalidate `__pycache__`. The stale bytecode was
what ran. Worth knowing before concluding anything from a test run that followed a same-size edit.

## Known not to work

- **`uptime` is the host's, not the installation's.** Nothing here reports how long the *daemon* has
  been running, and `self-status` structurally cannot: it is a different process. `ops-status`
  answers whether the apps have been running, from the store.
- Everything listed as open in `v0.8.1` is still open: `run_copy_backup` ignores `dry_run`; a
  reports directory the process cannot write leaves the fixed latest URL 404; nothing outside db_ops
  notices db_ops being absent; an app command's `error_text` carries the exit code and not the
  reason.
