# v0.34.0 — an AI assistant in Telegram that works with dbabrain's own tools, and the report pages judge the hour

| | |
| --- | --- |
| Date | 2026-11-02 |
| Previous | `v0.30.0` |
| Python | 3.12, 3.13 |
| Artifacts | PyPI wheel + sdist, `ghcr.io/tanthanhkaka01/dbabrain:0.34.0` |

## What this release is for

**An AI assistant in Telegram that works with dbabrain's own tools.** A chat listed in
`data/ai_assist.json` becomes a conversation with Claude, which reads the runtime store, the tool
root's files, a monitored server and the bot's commands through read-only tools that run on the
node - nothing on the internet connects in - and proposes the command for the user to run. Every
question, call, tool run, token and dollar is kept in the store; a quota in USD holds the system
and each user, and nobody is switched on unless listed. See `docs/07_telegram_app.md`.

**The report pages judge the last hour, not the newest row.** Disk latency's newest row is the
average since the engine started: a stall eight days old kept a data file CRITICAL, and a file
slow right now could stay off the list because its long history was fast. The server page and the
inventory now difference the file counters the store already keeps and grade the last hour; page
life expectancy is the hour's average; CPU, the disk queue and the wait sample keep the severity
the collector gave at least half of the hour's samples. The latest interval and the last 24 hours
are printed beside each. Alerts still judge the instant - that is their job - and are unchanged.

(0.31.0 and 0.32.0 were built and run on the worker, never released - the operator, 2026-10-26 and
2026-10-29. Everything they carried is in this version.)

**Keeping an alert quiet no longer empties the store.** `report_policy.disabled_metric_codes` is
the place to silence a metric that is too noisy on one server. Until this version the collector
read it too, so the metric also stopped being collected: a server whose host metrics had been
listed there once, for a reason long gone, showed no sockets, cores or host RAM on its page. The
list now keeps a metric's alerts out of the reports and nothing more.

**SQL Server on Linux is read for what it reports.** Through SQLPAL the engine's view of the
machine is not the host's: the scheduler monitor reported no idle time at all on a host that was
mostly idle, the process memory a fifth of what the engine had committed, and the "physical
memory" is the engine's own limit. Those three readings are now taken for what they are.

## Fixed since v0.30.0

- **`rotate-password` counts what it rotated.** It read an `ok` no result carries, so a clean
  rotation printed *rotated 0 of 1 login(s)* with `failed: 1`; a failure's reason named no ref.

- **A backup or restore that finished is no longer recorded `TIMEOUT`.** The stale-run check read
  the open rows, and a run that wrote its own `DONE` and exited before the check wrote had the
  `TIMEOUT` written over it, with a timeout alert, in the same second. The check now writes only a
  row that still says RUNNING. (Listed under *Known not to work* in v0.30.0.)
- **SQL Server on Linux: the CPU tile no longer reads 100 %.** The `cpu` row of
  `SYSTEM_CPU_MEMORY` is `100 - SystemIdle`, and on Linux `SystemIdle` read 0 on every sample. It
  now grades SQL Server's own share, which the same ring buffer reports correctly
  (`cpu_basis=sql_process`), and the server page says that it is the engine's share.
- **SQL Server on Linux: *SQL Server holds* is what it holds.** It read
  `physical_memory_in_use_kb`, which on Linux stayed at about 4 GB while the engine had committed
  21 GB. It now reads the memory manager's committed memory there; Windows is unchanged.
- **`metric-toggle`** no longer leaves `"metric_overrides": {}` behind, and no longer says *nothing
  to change* when switching a metric on took it off `report_policy.disabled_metric_codes`.

- **An Oracle older than 10g no longer runs the RMAN backup SQL**: `BACKUP_AGE` and
  `BACKUP_LAST_RESULT` are bounded to 10g and later in the catalogue, with the reason stated.
- **The Workload sections print the online / total CPU pair wherever the engine stated it**, as
  the CPU tile does.
- **`build-showcase` no longer breaks a page's `\u003e` escapes** - a value is decoded before it
  is read as a `DOMAIN\login`, and a `<placeholder>` is not a name.
- **A Windows host whose performance counters are slow to load keeps its free-space rows**:
  `OS_DISK_USAGE`'s counter reads run to a 22 s budget inside the metric's 30 s, and one that
  runs out leaves `disk_perf_counters = TIMEOUT` (`LOGGING`) beside the volumes instead of the
  whole metric timing out.

## Added since v0.30.0

- **A python-fed SQL task reads a second database by its credential name.** The command names the
  source - `input.source_connection: {"server_id", "db_type", "credential_name"}`, never a password
  - and the runner resolves it like a target and writes it to the program's stdin as
  `{"source_connection": {...}}`. Changing the login is one edit in `users.json`.
- **`input.payload_format: "xml"`** for a SQL Server older than 2016, which has no `OPENJSON`: each
  batch is `<rows><row key="value" .../></rows>`, read with `nodes()` / `value()`.
- **`rotate-password` changes a SQL Server password the server has expired.** A login refused with
  18487 / 18488 was `SKIPPED` - no session exists for `ALTER LOGIN` - and the password had to be
  changed by hand. It is now changed at login (ODBC's `SQL_COPT_SS_OLDPWD`), re-authenticated on a
  new connection and stored; a dry run says the password has expired. ODBC 17 or 18 only.
- **PostgreSQL's `LOG_FILE_SPACE`: the WAL** - files, size, `max_wal_size`, `wal_keep_size` -
  WARNING when it holds more than twice what the settings keep. Needs superuser or `pg_monitor`.
- **`DOCKER_CONTAINER_STATS` `:cpu_share` and `:disk:<mount>` rows**, and `OS_CPU_USAGE`'s
  `cores_per_socket` / `logical_per_socket`; Oracle's workload counters carry `timed_statistics`.
- **Oracle's `PERFORMANCE_IO_LATENCY` carries its raw counters** (`reads`, `writes`,
  `io_stall_read_ms`, `io_stall_write_ms`, `counters_since`) on 9i+ and 8i, so an Oracle file gets
  the same windows. Where `timed_statistics` is off the stall is 0 and so is the latency.

- **The server page carries everything the inventory says about the server, and more.** A Server
  detail section, before Databases: the fleet row and every Server Detail row (the engine build and
  patch, edition, endpoint, each engine's own facts, deployment, FCI, backup jobs, notes), the
  Config tab with its advice, every host field the OS collectors keep, services, top processes,
  network and event log, security counts and the findings - from the inventory's own record, no
  query added. The build and edition also join the page's header line.
- **`backup_restore entry-active`** switches backup and restore entries on or off by their
  `active` flag alone - every id named or none, a note appended to each entry that changes, and an
  entry switched on first held to the loader the scheduled app uses.
- **`metric-severity` with `metric_code` `"*"`** remaps every metric of one server at once
  (`metrics.severity_map`, its reason in `severity_map_note`); a metric's or an item's own map still
  wins. For a server whose every alert is expected, such as a VM that is switched off.
- **`metric-toggle` takes `reason`**: with `state` off on one metric it is written as that
  override's `disabled_reason`, and switching the metric on clears it.
- **`SYSTEM_CPU_MEMORY` names its basis**: `sql_committed_mb` and `sql_memory_held_mb` with
  `sql_memory_basis` on the `sql_memory` row, `memory_scope` (`host` or `sql_server_limit`) on both
  memory rows, `cpu_basis` on the `cpu` row on Linux.

## Changed / breaking

- **A PostgreSQL or Oracle server page states what SQL Server's does, from what it reads.** A
  container's CPU tile is its share of the CPUs it may use with *1.35 of 8 CPUs busy* and what the 8
  is (its limit, or the host's count), not `docker stats`' 319 %; its Disk space tile is the volume
  it writes to, from `df` inside it. An Oracle with no host access takes its CPU from its own
  counters, and reads *not timed* where `timed_statistics` is off. The Disk space tile takes only
  fullness, never a file's or a database's size. The Databases table gives an Oracle database its
  size and file count, says n/a for CHECKDB on an engine that has none, and puts PostgreSQL's WAL
  on its header line.
- **The CPU tile prints the processors in one form for every host**, as the OS counted them:
  *3 sockets, 17 cores (8 + 6 + 3)*, *1 socket, 30 cores* - no longer `N sockets × M cores` where
  the total happened to divide.
- **A metric that only failed to collect is told to fix the collection** on both report pages'
  problem lists, not given its metric's advice (*find the top process*, *free space*) for a
  reading that was never taken. A real reading beside the failure keeps the metric's advice.
- **Disk latency and page life expectancy are judged on the last hour on both report pages**, with
  the same thresholds (20 / 50 ms, 2000 / 300 s). Disk latency is the slower of read and write
  over the hour, each direction counted with at least 20 I/Os; the since-boot average is printed
  and not graded; with no pair - a restart in the hour - a file is not graded. The latency chart
  draws each collection interval. Findings move: files slow long ago leave the list, files slow
  now join it.
- **CPU, the disk queue and the wait sample are read over the last hour on both report pages**: the
  severity the collector stored on at least half of the hour's samples, the hour's average beside
  it. A wait finding the hour did not hold is lowered; it is never raised.

- **`report_policy.disabled_metric_codes` no longer stops collection.** The metrics it names on a
  target are collected and stored, shown on the server page and the inventory, and left out of the
  warning / critical reports that go to Telegram. The SLA app still leaves a policy out of scope on
  a target where every metric it reads is listed. **A code listed because the metric cannot run on
  that target starts running** - see *Upgrading*.
- **SQL Server on Linux: the memory rows grade their low-memory flags only.** A percentage of the
  engine's own limit, which it fills by design, is no longer graded as pressure;
  `process_physical_memory_low` and `system_low_memory_signal_state` still are. The `cpu` row's
  value on Linux is SQL Server's own share, so its history changes level at the upgrade.
- **The memory tile names what its total is**: the host's from `OS_MEMORY_USAGE` first, otherwise
  *used / SQL Server's limit* on Linux. The inventory takes no host RAM from a Linux limit.

- **An instance's `report_policy` keeps only `disabled_metric_codes`**: `enabled`,
  `severity_overrides`, `disabled_event_codes` and `disabled_report_events` were read by nothing
  and `upgrade-config` removes them.

## Known not to work

- Everything listed for v0.30.0 still holds, but the restore recorded `TIMEOUT` as it finished,
  which is fixed.
- **The console has no page for the AI assistant yet.** Its questions, calls, tokens and cost are
  in the store and are read with `telegram ai-usage` and `telegram ai-show`.
- **A PostgreSQL base backup already on a restore's target is copied again** instead of being
  confirmed in place: the gate holds its `backup_manifest` to the size recorded for the whole
  directory, which never matches. The copy that follows is proven as usual, so nothing wrong is
  restored - it costs the transfer. Found on 2026-11-02, fixed in the next version.
- **The assistant only proposes commands.** `tools_mode` is `off` or `read_only`; it never runs a
  command that changes anything, and a proposed `/spbot_` command is run by the user.
- **On SQL Server on Linux the host's CPU and RAM come only from the OS collectors.** A target with
  no host access shows SQL Server's own share and its limit, each labelled as such.
- **`committed_kb` was not run on a live SQL Server 2012** (on Linux it cannot occur; on Windows
  the figure it replaces is unchanged).

## Upgrading

1. **After `pip install --upgrade dbabrain`, run `upgrade-config`** - the plan first
   (`python -m dbabrain.common.cli upgrade-config '{}'`), then `'{"dry_run": false}'`; it brings the
   node's reference files to this version. Then
   `python -m dbabrain.db.cli --config config.json sync-config '{}'`.
2. **Read every `report_policy.disabled_metric_codes` list before the first collection.** A code
   there because the metric cannot run on that target - no SQL for its version, no rights - starts
   running and failing. Switch it off for collection instead:
   `python -m dbabrain.common.cli metric-toggle '{"server_id": "...", "state": "off", "scope":
   "<METRIC_CODE>", "reason": "..."}'`. An OS metric on a target with no host access is skipped by
   itself and needs nothing. A code there for a noisy alert stays where it is.
3. **`upgrade-config` names any `report_policy` key it could not remove** - a `severity_overrides`
   or `disabled_event_codes` holding a value. It never did anything; to lower a status on one
   server, write it as `metrics.severity_map` (`metric-severity`), then remove the key.
4. **SQL Server on Linux**: a `severity_map` set on `SYSTEM_CPU_MEMORY` because its CPU read 100 %,
   or because its memory rows were always WARNING, can be removed once this version runs.

5. **The AI assistant is off until a node switches it on.** Install the extra
   (`pip install 'dbabrain[ai]'`; the image carries it), put the Anthropic key into the secret store
   (`secret-set`), and in `data/ai_assist.json` set `enabled`, `api_key_ref` and each user in
   `users[]` with `"active": true`; give the assistant's group the level it names
   (`telegram group-level --group <title> --level ai_assist`). `upgrade-config` writes every other
   field, and turns a 2.87.58 - 2.87.61 `chat_ids` list into that level on the listed groups.
6. **A group Telegram made a supergroup** before this version still has its settings on the old,
   silent id: `telegram group-migrate --from-id <old> --to-id <new>` moves them. From this version
   the intake does it as it happens.

`SCHEMA_VERSION` is unchanged, and the store keeps its database, schema and rows. Five tables are
added (`ai_*`, `AiAssistStore` 1) the first time the assistant runs.
