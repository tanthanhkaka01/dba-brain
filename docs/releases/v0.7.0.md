# v0.7.0 — a forced task run now costs a confirmation

| | |
| --- | --- |
| Date | 2026-09-04 |
| Previous | `v0.6.0` |
| Python | 3.12, 3.13 |
| Artifacts | PyPI wheel + sdist, `ghcr.io/tanthanhkaka01/dbabrain:0.7.0` |

## What this release is for

`/spbot_run_sql_task` runs a configured SQL task **forced**: it skips the task's time window, its
repeat interval and its active flag. A task that writes then writes to production outside every
window that was agreed, and until this release the only thing standing in front of it was the
command's chat clearance.

Clearance is the wrong control for that. `command_type` answers *who may ask*; it has never
answered *how hard it is to ask*. Raising the command to clearance 50 — the tier of
`/spbot_kill_spid` — changed who could run it and left it costing nothing to run, and that gap is
what this release closes. The confirmation now comes from the same gate every other dangerous
operation uses, priced by the same file, so an operator learns it once.

**Upgrading requires action if anything runs `run-sql-id --force` unattended.** See
*Changed / breaking*.

## Added since v0.6.0

- **`db-ops common authorize`** — the confirmation gate on its own, for a caller that performs the
  work itself. Every other gate belongs to the operation it guards: `kill-spid` confirms and then
  kills. A forced task run is the first case where the operation lives in an app and only the
  authorization is shared, and the alternative to a command of its own is a second yes/no prompt
  written app-side — which is how two commands come to spell the same danger differently. It takes
  the operation name, what will be touched and what that costs, and answers with the gate report.
  How hard it is to confirm still comes from `emergency_operations.json`, and an operation that
  file does not list costs **two** answers, not none.

- **`run-sql-task` is a named operation**, at level 50 in `emergency_operations.example.json`:
  one typed `yes`. The prompt names the task, how many targets it will touch and whether the task
  is inactive, because "run task 24?" tells an operator nothing they can check.

## Fixed since v0.6.0

- **A test pinned an operator's policy and failed when the policy was tightened.** The clearance
  check for `/spbot_run_sql_task` asserted that every command able to execute SQL carried the
  *same* number. Raising that one command to 50 — a deliberate tightening — turned the suite red on
  a correct change, which is the second time this test failed for a strengthening of the thing it
  guards. It now asserts what is actually true and cannot be broken by tuning: never below the
  write tier, and always above every read-only command. Found by CI on the commit that raised the
  clearance.

- **Every confirmed command was refused on a fresh install.** `db-ops init` wrote the command
  catalogue and never wrote `emergency_operations.json`, and the package carried no copy of it —
  so an install that was not the author's own priced every operation at the strictest level (two
  answers, the second the target's id typed out) while `/spbot_kill_spid`, `/spbot_shrink_log`,
  `/spbot_start_job` and `/spbot_disable_job` each collect exactly one `yes`. The gate then refused
  with *the request does not carry answer 2 of 2*, which reads like a defect in the command rather
  than a missing file. **This affected v0.4.0 through v0.6.0.** The ladder now ships with the
  package, `init` writes it, and the gate falls back to the packaged copy when a tool root has none
  — the same fallback `data_files.json` has. A ladder that exists but will not parse is still
  priced at the strictest level, because absent and broken are different faults. Found by the
  public tree's suite: the confirmation tests passed in the tree that has the file and failed in
  the tree that does not.

- **A refused export no longer deletes the repository it was writing into.** `export-public`
  scans the copy it just wrote and removes it when a configured identifier appears — and that
  removal was a full `rmtree` of the target, which for the normal case (exporting into the public
  checkout) takes `.git`: the history, the remote and any unpushed work. The same hazard the
  `--force` path was fixed for in August, still live in the refusal path, which nobody exercises on
  a good day. Found by triggering it: the scan correctly refused a tree during this release and the
  delete then walked into `.git`, surviving only because Windows will not unlink a read-only object
  file. A refusal now empties the copy and keeps the metadata; a target that is not a repository is
  still removed outright.

## Changed / breaking

- **A forced SQL task run is refused unless it is confirmed.** `run-sql-id --force` now costs one
  typed `yes`, read the same way every other gate reads it:

  | Caller | What it does now |
  | --- | --- |
  | A terminal | is asked, and answers at the prompt |
  | A chat command | is asked over chat; the reply travels as `--confirm yes` |
  | **Unattended automation** | **must pass `--assume-yes`**, or the run is refused |

  A script that calls `run-sql-id --force` from cron or a scheduler and never sees a terminal will
  now stop rather than run. Add `--assume-yes` to it — the waiver is deliberate and recorded in the
  gate report as *no human was prompted*, so a run nobody watched never reads afterwards like a run
  somebody approved. **The scheduled scan is unaffected**: a schedule authorized itself when it was
  written, and `--dry-run` is never asked to confirm anything.

- **The shipped `/spbot_run_sql_task` moves from clearance 10 to 50**, and gains a `confirm`
  argument. Typed in one line the argument order is now
  `/spbot_run_sql_task <sql_id> yes [the task's own values]`; sending `/spbot_run_sql_task <sql_id>`
  alone asks one question at a time, as before. The confirmation sits **in front of** the task's own
  parameters and not behind them, which is the only unambiguous place: the parameter block is
  `consume_rest`, so anything stored after it is also inside it and the word `yes` would be appended
  to the values the task runs with. An existing install keeps its own clearances — this changes the
  catalogue a new tool root is written from, not one already configured — but the `confirm` argument
  and the `--confirm` in the command line are needed for the command to work at all, so an estate
  that carries its own copy must take both.

- No schema changes, no threshold changes, no configuration migration.

## Known not to work

- **A forced run at a terminal waits at the prompt rather than exiting.** That is the point of the
  prompt, but it means a caller that has a terminal and cannot answer on it — a wrapper script run
  by hand, say — blocks instead of failing. Non-interactive callers are refused immediately, which
  is the case that matters for automation.
- **`--assume-yes` is the only way to run a forced task with no human anywhere.** There is no
  per-task exemption and no configuration that removes the gate; if a task legitimately runs
  unattended and forced, the waiver has to be written into the caller.
- **OS-level metrics from a `pip` install still need the `[ssh]` extra**, unchanged from v0.6.0.
- Interval **grading** remains withdrawn, unchanged since v0.5.0: the workload collectors report,
  and no severity is derived from a rate.
