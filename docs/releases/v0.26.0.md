## Summary

**An upgrade no longer leaves a task stopped for an hour.** A container recreated without a pinned
`hostname` comes up under a new name, and read the runs its predecessor was killed in as another
machine's - so it waited out their timeout plus an hour of grace before running those tasks again.
The tool root now has an identity that survives the recreate, and the new container frees those
runs on its first scan.

**A SQL task run cannot run for ever.** Its timeout reached the database driver as a per-call query
timeout, which a procedure answering many small results never trips, and nothing else bounded the
run. A run past its timeout is now closed as an error by timeout, and its process stopped, the
next time its task is scanned.

## Added

- Transport switches that verify the machine: `sqlserver_tls_verify` per instance, the store's `sslmode` honoured; `sre ssh --stdin`.
- **`sql_tasks.cli close-run`** - close one run left `running` by hand, with a reason, when its
  process is known to be gone.
- **`telegram.cli command-level`** sets who may run a bot command (`--shipped` raises every command
  below this version's level); **`upgrade-config`** adds the console apps a node's file lacks;
  **`webhost.cli bootstrap-admin`** adds the first-run admin to a store that already holds accounts.
- **`instance-add` with `"keep_default": true`** adds a second database login to a registered server
  and leaves its default login and its record alone.
- **Accounts are managed in the console** (Administration -> Users, admins only), and **the server
  page lists the last 24 hours' Query Store findings**, one row per plan.

## Changed

- **`runtime/node_identity`** - the tool root's identity, written once, recorded on every run's
  claim. Keep `runtime/` on the host (the Docker examples mount it); a node that loses it gets a new
  identity, which is the behaviour before this version, not a failure.
- **Metrics and reports are launched every 30 s** (`APP-METRICS`, `APP-REPORTS-CREATE`; they were
  120 s), so a metric is at most 30 s late past its own interval. New nodes get it from `init`; an
  existing node keeps its own schedule - see *Upgrading*.

- **Every `common.cli` answer says what kind of failure it was** (`error_kind`: `request`,
  `not_configured`, `refused`, `unreachable`, `failed`, `config`, `internal`), and **every request is
  checked against the reference** before the command runs. Unknown keys and old spellings are only
  measured in this version (`DB_OPS_REQUEST_CHECK_LOG`); refusing them comes later.
- **The report pages use the whole window**; the SLA page reads by engine and by instance; the
  server-metrics and index pages pick an instance per engine and look like the other pages.

The full list is in [`CHANGELOG.md`](../../CHANGELOG.md).

## Fixed

- The console signs out only on a POST with its token; the store's `sslmode` reaches the driver.
- Result files under `runtime/output` are removed after `output_retention_days` (default 7); a report alert queued in parts is found by the dedupe window.
- The console refuses one address before it can lock an account (`web.max_failed_logins_per_ip`, default 5).
- Logs rotate nightly on a Windows master and keep one line per record; a threshold override never lowers a CRITICAL/ERROR/NO_DATA verdict; a container restart warns for an hour, not for ever.
- A WinRM command with no deadline runs to its end; secret and state files are replaced whole (secret files `0600`); deploy names are quoted.
- A restore target's cleanup touches only the mapped databases' folders; a retention under a day is honoured; the source under another name is refused as a target.
- A backup job's `cleanup_retention` under a day is applied, by each engine's own means: SQL Server by file age below the newest full, PostgreSQL by whole chains and `pg_archivecleanup`, Oracle through RMAN after each successful level 0. Until now such a job kept fourteen days.
- Two restores onto one machine can no longer share a staging folder, whichever instances they restore onto; the retention report measures a backup's age on the clock of the machine that holds it.
- A timed-out or stopped app command ends its whole process tree; a removed command's open row is closed.
- A rate-limited long message resumes at the next part; an operator's routing change is not lost to the workflow.
- **A document with a caption over 1024 characters is delivered**, the whole text following as a message.
- **The background-task poller kills only its own task, and the whole of it**, never a process that
  reused its PID.
- **An interrupted bot command is not run again by itself**; its sender is asked to re-send it.
- A staging cleanup no longer deletes the full a newer SQL Server differential restores onto.
- `prune --apply` never deletes a database's newest full, nor anything after it.
- One backup, SQL task, metrics target or report that fails unexpectedly no longer stops the rest of
  its pass.
- `rotate-password` stores each new password before changing the next, and rolls back on a store
  failure.
- A restore never takes the source as its target, and a cross-machine restore stages only into a
  directory marked as db_ops's own (see Upgrading).
- **The Telegram send pass stops starting messages at half of the workflow's own `time_window.timeout`**
  (the daemon states it in `DB_OPS_APP_TIMEOUT_SECONDS`).
- **A message Telegram accepted is not sent again** when recording it hits a busy store.
- **A message a killed pass left half-sent is re-queued** after 15 minutes instead of being lost.
- **One failing chat no longer costs a pass the others' counts and rate-limit pauses.**
- **The bot keeps hearing commands** when a later workflow step fails: the update offset is saved as
  soon as the updates are stored, and the Telegram JSON files are written atomically.
- **One app command that cannot be started no longer stops the daemon** (and no crash loop).
- **A point-in-time restore with `copy_recent_hours` 0 copies everything up to the moment.**
- **A recreated container frees its predecessor's open runs at once**, instead of after their
  timeout plus an hour.
- **A SQL task run past its timeout is closed as an *error by timeout*** and its process stopped,
  the next time its task is scanned; left to itself it is stopped at twice its timeout plus the
  connect timeout. Before, one run went 13 hours on a 2-hour timeout and held its target.
- **A SQL Server restore copies only its chain** (newest FULL at or before the moment, its DIFF, the
  LOGs after) instead of every file of `copy_recent_hours` - 56.8 GiB instead of 527.9 GiB on a
  weekly-FULL source - and the space check counts the same list.
- **`copy_selection`** - `"chain"` (default) or `"window"` per restore entry: copy only the chain, or
  every file of the range as before; the space check counts whichever is chosen.
- **A restore's space check no longer counts files that are already staged**, and asks for twice
  the bytes it copies by default, on every engine. A share-driven SQL Server entry can also have
  the database each restore builds measured (`space_check.measure_restore: true`, off by default):
  a 56.8 GiB compressed chain restored to 366.6 GB.
- **`QUERY_STORE_QUERY_ISSUES` reports a small query on a worse plan that runs often**
  (`QUERY_PLAN_REGRESSED_FREQUENT`), judges every finding on recent rows, and no longer repeats one
  heavy execution every 15 minutes for six hours.
- **On a Linux node the copy's space check measures the copy.** It walked the share as a path, found
  nothing there, counted 0 bytes and passed every time; it now reads the share the way the copy does,
  and also checks that what the node fetches fits in its own temp folder (see Upgrading).
- **A script-driven restore onto another machine checks the room before it copies**, by its
  entry's `space_check` - described as on by default, and read by nothing until now.
- **Logins replay onto a lab target** - the replay looked for its target among the monitored
  instances only, and a lab (inactive, metrics off) was never found.
- **A statement timeout is reported as one**, not as *could not reach* the instance.
- **`/spbot_create_db_docker install_docker=yes` installs Docker behind a proxy** - from the distro
  packages when get.docker.com cannot be fetched, instead of reporting an install that never happened.
- **`QUERY_LONG_RUNNING` and `QUERY_LONG_WAITING_OR_ROLLBACK_REQUESTS` carry `client_ip=`** on SQL Server.
- **The SQL Server 2008 R2 sleeping-open-transaction metric carries `client_ip=`, and its blocking
  metric names the head blocker** (session, login, host, address, open transactions, last SQL)
  instead of counting blocked sessions per database.
- **`build-showcase` leaves a page's markup alone** - a table called `meta` had turned
  `<meta charset>` into a fake name in the published showcase - and leaves a plain word the pages
  themselves print.
- **`instance-add` no longer leaves a login behind when it refuses a password** it cannot encrypt.

## Known limitations

- **The upgrade to 0.26.0 itself still waits for its predecessor's open runs** - rows written by
  0.25.0 carry no identity. Close one with `close-run`, or let it age out as before.
- **Stopping a SQL task run closes its connection, not the statement** - at its timeout or at its
  deadline alike. What the server does with a
  statement in flight when its client goes away is the engine's; on SQL Server it may run on until
  it next writes to the connection.
- **The SMB restore onto a Windows target, and the share cleanup, are proven offline only.**
- **An existing store keeps its archive tables without keys** until `db.cli archive-keys --apply`
  is run; on a large store it reads every archived row.
- **A PC node has no supervisor.** Run a daemon started by hand under a service manager.

## Upgrading

**Restore entries state their target (action required).** Before the first scheduled restore on the
new version:

1. `python -m db_ops.backup_restore.cli --config config.json list-restores` - it names the first
   **active** script-driven entry that relies on the source being taken as its target, and the
   field it needs. Add it and run again until the list prints. Entries that are switched off and
   lack the same fields stop nothing: they are listed under *Inactive and incomplete*, and need
   fixing only before they are switched on. Every such entry needs `db_type` and
   `target_server_id`; an in-place one (target on the source's machine) also `target_container`,
   `target_visible_dir` and, for SQL Server, `env.MSSQL_PORT`.
2. Nothing to do for existing staging directories: one that is an earlier copy of the same source is
   adopted and marked (`.dbops-staging`) on its next run. Only a directory holding files the source
   does not have is refused - nothing copied or deleted - with the `touch` command in the message.

3. **Every SQL Server restore entry that overwrites its own last restore states
   `"overwrite_existing": true`** - a full restore over a database ONLINE on the target is refused
   without it (G2.10). Script-driven SQL Server entries also state `env.MSSQL_USER` (still `sa` when
   absent, with a warning; refused in the next release).

4. **A password kept only in an environment variable for an SSH, WinRM or SRE login goes into the
   secret store first** (`db-ops encrypt-secret`): `password_env` is now read as `password_ref`, and
   nothing a request names is looked up in the environment (G3.5). `rotate-password` no longer takes
   `allow_name_host`; a ref no `db_instance` uses is skipped with what to add (G3.4).
5. **Optional - the 30 s schedule on an existing node.** `data/app_commands.json` is the node's own,
   so the new default reaches only nodes `init` creates. To take it:
   `python -m db_ops.common.cli app-command-set '{"app_code": "APP-METRICS", "time_window": {"repeat_interval": 30}}'`,
   and the same for `APP-REPORTS-CREATE` (on Windows, from a file: `@request.json`).
6. `python -m db_ops.common.cli check-objects '{}'` lists, as `fallback` notices, the active records
   that leave a host's platform, an SSH `auth_type`, a port, a database or a login to a default.
   Nothing stops today; the next release refuses them.

6. **A Linux node's share-driven SQL Server restores are measured for the first time.** Until now
   their space check counted 0 bytes and always passed. From this version an entry whose copy does
   not fit the target's free space times its `space_check.factor` (2.0 when absent) is refused before
   anything is copied, as on a Windows node - and a share that cannot be listed is refused as
   unmeasured unless the entry says `"on_unknown": "proceed"`. Run each entry once by hand
   (`restore-workflow --restore-id <id>`) and read its `space check:` line before the first night.

7. **A script-driven restore onto another machine is checked before its copy.** Its entry's
   `space_check` (on at factor 2.0 when absent) was not read on this path. A first copy that does
   not fit the target's staging filesystem by that factor is now refused with nothing copied; a
   repeated drill is asked only about the files it still has to copy. Set `space_check.factor` on
   an entry whose target is deliberately tight.

8. **`space_check.factor` defaults to 2.0** (it was 1.5), on every engine. An entry with no
   `space_check`, or one without `factor`, now needs twice the bytes it copies free on its target;
   state `"factor": 1.5` to keep the old margin.
9. `check-secret` no longer reads a host from a ref's name: a ref no configuration names answers
   `NO_TARGET`. Name it on its instance (`default_credential_name`, or `cmd_access.credential_name`),
   or give its `users.json` `remote_credentials` group a `host`.

10. **A SQL task's `timeout` bounds the whole run of a target.** A run still going past it is
    stopped and recorded as an error by timeout. Before upgrading, compare each task's longest
    finished run with its `timeout` (the `sql_runs` table has both) and raise the ones that are
    close; `0` means no timeout.

11. **Give every script-driven restore its own `target_backup_dir` on its target machine.** Two
    active entries that share or nest one on the same host - even onto different instances of it -
    are now refused when the file is loaded. `list-restores` names the pair.
12. **Read `cleanup_retention` on every backup job that states less than a day (86400).** It is
    now applied: files, chains or RMAN backup sets older than it are removed after the job runs.

`SCHEMA_VERSION` is unchanged, so the store needs nothing.

**Security changes that need an action (batch 3).**

1. Start the worker daemon with the passphrase in its environment: `read -rs DB_OPS_SECRET_KEY &&
   export DB_OPS_SECRET_KEY`, then `docker compose run … -e DB_OPS_SECRET_KEY db_ops daemon` (no
   `--key`). `control deploy` already does this.
2. Report links now ask for a console login; set `web.reports_require_login: false` only behind an
   authenticating proxy.
3. Bot levels: the shipped catalogue sets `/spbot_add_sql` 100, `/spbot_sql_to_xlsx` and
   `/spbot_sql_export` 50. A node's own `telegram_support_commands.json` is used as written; if it
   still says 10, the log warns once and names the change. `python -m db_ops.telegram.cli
   command-level --shipped --dry-run` lists every command below this version's level, and the
   same without `--dry-run` raises them.
4. Console edits to commands, scripts, host logins or permission files ask for the admin's password.
5. A Vault with a self-signed certificate needs `certificate_api_ca_file` in the restore entry.
6. Give the bot "delete messages" rights in groups where it asks for passwords.

```bash
pip install --upgrade dbabrain
python -m db_ops.common.cli upgrade-config '{}'                   # read the plan
python -m db_ops.common.cli upgrade-config '{"dry_run": false}'   # then apply it
```
