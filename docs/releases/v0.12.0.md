# v0.12.0 — the first thing a new user types now works

| | |
| --- | --- |
| Date | 2026-09-08 |
| Previous | `v0.11.0` |
| Python | 3.12, 3.13 |
| Artifacts | PyPI wheel + sdist, `ghcr.io/tanthanhkaka01/dbabrain:0.12.0` |

## What this release is for

Someone ran the shortest possible install — a new directory, a new virtualenv,
`pip install dbabrain`, nothing else — and asked how they were supposed to start. The honest
answer was that they could not.

The directory held `.venv` and nothing else: no README, no guide, no configuration. The
getting-started document only appears after `db-ops init`, which a reader has no way to know
exists. And the first thing anyone types is the name they just installed:

```
PS> dbabrain
dbabrain : The term 'dbabrain' is not recognized as the name of a cmdlet...
```

The distribution is `dbabrain`; the only console script was `db-ops`. So the opening move of every
new install failed, in a directory with nothing in it to suggest what else to try. Minor rather
than patch because two commands are new — see *Added*.

## Added since v0.11.0

- **`dbabrain` is a console script.** Same dispatcher as `db-ops`, which stays: it is in every
  runbook, every dated record and every operator's notes, and a rename would make all of them
  wrong to gain nothing.

- **`dbabrain guide`** prints the getting-started document and **writes nothing**. Until `init` has
  run there is no file to read, and deciding whether to run `init` is exactly when a reader wants
  to know what they are getting.

- **A first-run banner.** Run bare in a directory with no tool root, the toolkit now says what to
  type:

  ```
  There is no tool root in this directory yet, so there is nothing to run against.

    dbabrain init      create one here: config.json, data/, and a guide to fill it in
    dbabrain guide     read that guide now, without creating anything
  ```

  Twelve app names is the right answer to "what can this do" and the wrong one to "I have just
  installed this" — none of those apps can run before a tool root exists, so leading with them is
  twelve dead ends. `init` was thirteenth in that list with nothing marking it as the one command
  that works first. Inside a configured tool root the full listing is unchanged, and `--help`
  always gives everything.

- **The sdist now carries `docs/`**, `README.md` and `CHANGELOG.md`. See *Known not to work* for
  the half of this that is still missing.

## Fixed since v0.11.0

- **The one document a fresh install ships was telling readers the product does less than it
  does.** `AGENTS.md` ended by listing backup and restore validation, SLA checks, scheduled SQL,
  reports, host provisioning and the web console as "not in this release". All six are in
  `db-ops --help` and have been for many versions. That is the expensive kind of stale — not wrong
  about a detail, wrong about the scope — and a reader who believed it concluded this was a
  metrics collector.

- **It never mentioned `timezone`**, required since 0.10.0, whose absence silently puts every
  hour-bounded schedule on UTC.

- **It never mentioned the daemon**, or `DB_OPS_NODE_ROLE=worker`. A reader who followed that file
  exactly finished with one manual collection and nothing scheduled — and a daemon left in the
  default `master` role runs nothing while looking perfectly healthy.

- It used two names for one command, `encrypt-secret` in the main flow and `encrypt-secret-text`
  in the Telegram section. Both work — the second is a dispatched alias — so this was a
  readability defect rather than the dead end it first appeared to be. Stated precisely because
  the first reading of it was wrong.

## Changed / breaking

Nothing an existing tool root must do. `db-ops` behaves exactly as before, including bare inside a
configured root.

## Verified

```
ruff check .                    All checks passed!
pytest tests -q                 6131 passed, 26 skipped, 10 xfailed, 0 failed
```

Nine new tests pin the experience this release is about, including one that fails if `dbabrain`
ever stops being a console script, and one that fails if the shipped guide starts claiming a
shipped capability is missing.

Writing those guards produced the same class of defect twice, which is worth recording because it
is the failure mode of every test written against documentation:

- the first version invented two attribute names, found neither, and reported four **real**
  commands as missing;
- the second matched a phrase that the guide **wraps across a newline**, so it passed against the
  exact stale text it existed to catch and would have gone on passing forever.

Both now read the command registry from the dispatcher and match on collapsed whitespace, and each
guard was confirmed to fail against the defect it describes before being kept.

## Known not to work

- **The wheel still ships no `docs/`.** The sdist carries them now and `dbabrain guide` answers the
  getting-started half offline, but `pip install` uses the wheel, so a reader who wants the full
  reference is sent to a URL. Fixing that means relocating `docs/` under the package, and 121
  places in the tree reference it by its current path — a refactor with its own review rather than
  a line in a packaging file. It is the largest remaining gap between this and the stated goal of
  reaching a collecting install by pointing an agent at the documentation.
- **Upgrading over an existing root is still untested**, and from 0.9.x it is the one that silently
  moves schedules when `timezone` is absent.
- Everything listed as open in `v0.11.0` is still open, including the slow carry and the
  cross-server limit on `--source-schema`.
