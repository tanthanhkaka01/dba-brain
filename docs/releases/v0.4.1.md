## What this release is for

A gate that reports a tree clean has to have read the tree. `check-identifiers` derives its search
terms from the inventory, but it only opens file types on a list, and template file types were not
on it — so a whole class of shipped files was never certified. This closes that, and cleans the
templates it should have been reading all along.

## Fixed since v0.4.0

- **The identifier scan skipped every template file type.** `check-identifiers` reads the files
  whose suffix is in `identifier_scan.DEFAULT_EXTENSIONS`, and `.html` and `.j2` were absent, so
  the report templates were never opened — a green scan that had not looked. Term coverage and
  *file* coverage are different things, and only the first was being reasoned about.

  The scan now reads `.html`, `.htm`, `.j2`, `.jinja`, `.jinja2`, `.css`, `.js` and `.xml`.
  *Proof: the whole tree now scans 834 files, where the same run previously skipped the templates
  entirely; a template that the old scan passed is flagged by the new one.*

- **A report template's comments carried environment-specific detail.** The house style is that a
  comment explains the incident that motivated the code, and in a template written against a live
  estate that puts deployment-specific detail into a shipped file. The comments in
  `server_report.html` keep their reasoning and no longer name anything from the environment they
  were written against.

- **A shipped Telegram command was aimed at one specific instance.** The command catalogue a fresh
  install scaffolds is meant to be commands that work on any server — they take a `server_id` or
  target argument. `spbot_trace_session` was the exception: pinned to a single instance, so a new
  install got a command aimed at a machine it does not have. Removed from the catalogue, which now
  scaffolds 20 generic commands. The generic `trace-session` capability still ships in
  `common.cli`, so an operator can add their own pinned entry.
