## What this release is for

**A backup is only worth what can be proven about it when the server is gone.** This version keeps
proof of every backup and acts on it. The backup catalog is hash-chained, so an edited or removed
row is named. Every backup run re-hashes the oldest-checked files of its entry and looks for
ransomware's marks in the folder; three or more stored files changed or gone, or a ransom note,
engage a **lockdown** that stops every prune, delete and overwrite until a person ends it with a
note. `restore-candidates` lists the backup chains that ended before the first sign of an attack.
A restore checks the chain - SQL Server LSNs, PostgreSQL WAL from the base's start segment - before
it touches the target, and a drill checks the restored data's consistency. Retention is stated per
file type (a log kept shorter than its full, Oracle's pieces each by their own window), and a file
its retention removed is recorded `pruned`, not gone.

**The AI assistant answers in several groups and in its users' private chats**, guides a new
install in the node's own shell, and has a page in the console with its usage and every request in
full.

## Fixed since v0.34.0

- **A PostgreSQL base backup already on a restore's target is confirmed instead of copied again.**
  The gate held its `backup_manifest` to the size recorded for the whole directory, which never
  matched; the manifest's checksum decides now. (Listed under *Known not to work* in v0.34.0.)
- **The Linux SQL Server backup script could delete a database's last FULL.** `find ! -newer`
  matched the newest full itself, so a database whose backups had stopped for longer than the
  window lost it. Found reading the script for per-type retention; the newest full is excluded by
  path (`! -path`), held by `tests/test_a_retention_under_a_day_is_applied.py`.
- **A scrub that could read nothing looked clean.** Files in a docker volume were unreadable from
  the host and every scrub there said `checked 0`. Found on a candidate node; they are hashed inside
  the container now, and an unreadable scrub is a WARNING.
- **WAL cut by `pg_archivecleanup` read as gone, and a file a sibling entry's retention removed read
  as gone.** Both engaged a false lockdown on a candidate node: twenty WAL segments the cleanup had
  cut at the oldest base's start segment. A gone segment before the oldest present full base is the
  cleanup's, and a gone file is held to the windows of every job writing its folder.
- **`lockdown off` answers the lockdown as it now stands**, not the row read before it ended.
- **`metrics collect --test-run` accepts a host** - it refused a `major_version` a machine without
  a database cannot have.
- **An Oracle `ctl_` or `autobackup_` piece staged without a catalog row is typed CONTROLFILE**, no
  longer RMAN_L0.
- **`build-showcase` no longer rewrites a measurement as a machine**: a two-octet number with a
  short unit after it (`3d 0.2x`, `17.1s`) is not an address's shorthand. An instance joined to its
  database in a backup file's name is found and rewritten. `check-identifiers` runs in about a minute
  instead of over ten (its word lists are matched as one trie - the same matches).

## Added since v0.34.0

- **Lockdown** - `control.cli lockdown on|off|status` and `/spbot_lockdown` in Telegram (private,
  clearance 50; on and off ask why). While on: no prune, no delete, no restore over an ONLINE SQL
  Server database, no ad-hoc SQL that writes, no delete after an offload; backups, the scrub and
  alerts keep running. A new store table, `lockdowns`.
- **A rolling scrub after every backup run**: the entry's `scrub_files_per_run` files checked
  longest ago (default 20, 0 off) are hashed again; one changed or gone makes the run CRITICAL and
  names it.
- **Ransomware's marks in a backup folder** are looked for after every backup: a ransom note or an
  encrypted file's name is CRITICAL and engages the lockdown; a file three times bigger or a third
  the size of its history is a WARNING.
- **A hash-chained catalog**: `backup_files.row_hash`, checked by
  `backup_restore catalog-verify-chain`.
- **`backup_restore restore-candidates --backup-id`**: each chain newest first, verified or not,
  and whether it ended before the first sign of an attack.
- **Chain checks before a restore**: SQL Server LSNs (a DIFF of another FULL, a missing log) and
  PostgreSQL WAL continuity from the base's start segment are refused naming the file, before the
  target is touched. `list-backup-files` answers the LSNs, `start_wal` and the WAL segment names.
- **Consistency after a script-driven drill**: `DBCC CHECKDB`, `pg_amcheck --all`, RMAN `VALIDATE
  CHECK LOGICAL`, from the entry's `checkdb`.
- **Retention per file type**: `cleanup_retention` may be `{"FULL": ..., "LOG": ..., "CERT": "keep",
  "default": ...}`; SQL Server, PostgreSQL and Oracle prune each type by its own window, and
  `prune-backup-files` / `prune-backups` too. A backup entry states `cleanup_retention` once for its
  jobs.
- **Recoverability on the backup & restore page**: drills by `tier` (daily, weekly, monthly) with
  OK / OVERDUE and their 7- and 30-day success rate, each database's coverage and what it lacks, and
  each entry's retention and point-in-time reach (also on each server page).
- **`STORAGE_FILE_PLACEMENT` alerts**: CRITICAL when a SQL Server backup shares a drive with its
  database's files, WARNING when every backup stays on the database host.
- **Each backup file's own start time** (`backup_files.backup_started_at`) and **`catalog-backfill`
  for PostgreSQL and Oracle**.
- **Guard rails**: `prune-backups --apply` refuses to delete more than half of an entry's files at
  once (`--allow-mass-delete`); a restore into an instance the inventory calls production needs
  `allow_production_target: true`; SSH host keys are pinned when `DBABRAIN_SSH_KNOWN_HOSTS` names a
  file; a new restore entry refuses a backup file no backup catalogued.
- **The rebuild runbook**, `docs/security.md` §5b: what to keep off the node and the rebuild in
  order.
- **The AI assistant in several groups and in private chats**: `ai_assist.json` `telegram_chat`
  takes a list of levels, and `private_chat_enabled` answers the active users of `users[]` in their
  own chat with the bot. A message answering a bot command that asks for a value is never sent to
  the model.
- **The console's *AI assistant* page** (Administration, admins, read-only): usage by day, user or
  model; every request with its messages, API calls and tool runs.
- **The assistant writes command lines for the node it runs on** - its OS, shell, install and tool
  root - and guides a new install in order; `dbabrain init` says it exists.

## Changed / breaking

- **Expect `STORAGE_FILE_PLACEMENT` alerts on the first collection** wherever backups are kept on
  the database's own host or drive. They stay until the backups leave it, or until the metric is
  remapped on that server (`metric-severity`).
- **A restore into a production instance is refused** unless the entry sets
  `allow_production_target: true`.
- **A new restore entry refuses an uncatalogued backup file** (`integrity.uncatalogued: refuse`).
  Existing entries keep `compare_copy`; `upgrade-config` writes it out.
- **`telegram_chat` as a list needs this version's code first**: an older node refuses the file.
- **`private_chat_enabled` is a new mandatory field** of `ai_assist.json`, shipped `false`.
- **Backup jobs' `cleanup_retention` folds onto the entry** - `upgrade-config` step
  `retention-per-type` does it and names any entry whose behaviour that changes; a job and its entry
  that disagree are a `check-objects` violation.
- The backup catalog moves from schema 3 to 7 in place on first use. The runtime store's
  `SCHEMA_VERSION` is unchanged (5).

## Known not to work

- **The fleet inventory page can grade a volume from an old total.** Where SQL Server reports a
  drive's free space without its size (`xp_fixeddrives`, SQL Server 2008), the page divides it by
  the size in the canonical inventory file, which may be months old: a resized volume reads nearly
  full. It also grades disks on its own 10 / 15 % thresholds instead of the collector's verdict, and
  grades a drive known only from that file. Found on 2026-11-05; fixed in the next version. The
  per-server page and the alerts are right.
- **The share-driven restore path does not check the chain yet**: its headers come through `sqlcmd`
  over WinRM, which `list-backup-files` cannot read. The script-driven path checks it.
- **Restore staging is still pruned by the longest window** of an entry, not per file type.
- **The catalog's chain head is not copied off the node yet**, so a rebuilt node can tell that its
  catalog changed only from a copy kept elsewhere.
- **Not yet run against a real server**: `catalog-backfill` for PostgreSQL and Oracle (run it with
  its dry run first), and the drill's consistency check.
- **No canary file and no `RECOVERABILITY_CHANGED` / `UNEXPECTED_BACKUP` detection yet**; the backup
  scripts still widen file permissions after a backup, and backups and prunes still share one login.

## Upgrading

1. **After `pip install --upgrade dbabrain`, run `upgrade-config`** - the plan first
   (`python -m dbabrain.common.cli upgrade-config '{}'`), then `'{"dry_run": false}'`; it folds each
   backup job's `cleanup_retention` onto its entry, writes `private_chat_enabled`, and states
   `integrity.uncatalogued` on existing restore entries. Then
   `python -m dbabrain.db.cli --config config.json sync-config '{}'`, and
   `python -m dbabrain.common.cli check-objects '{}'` - 0 violations.
2. **Read the plan's `retention-per-type` lines before applying it** where several jobs of one entry
   stated different windows: the fold names every entry whose behaviour changes.
3. **To use a restore entry with `refuse`**, backfill its source's catalog first
   (`backup_restore catalog-backfill`, dry run, then `--apply`); otherwise the drill refuses files no
   backup recorded.
4. **To pin SSH host keys**, set `DBABRAIN_SSH_KNOWN_HOSTS` to a file the node can write. Unset,
   nothing changes.
5. **Keep a copy off the node** as `docs/security.md` §5b lists: the `export-data` bundle, the
   store's backup, and the passphrase offline.
