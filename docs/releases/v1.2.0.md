## What this release is for

**An agent picks the right MCP tool.** Commands that share a request used to share its description, so
`table-info`, `object-source`, `db-activity` and `query-plan` opened with the same sentence, and so did the
`smb-*` tools, `key-request` and `key-renew` and others. Each tool now opens with what it alone does. Its
input schema also states the request's fields - type, allowed values, bounds, what each is for, which are
required - instead of a prose list, so a client can check a call before it sends it.

**A Telegram message outlives Telegram being unreachable.** A 502 from Telegram, a read that timed out, a
reset connection or a TLS handshake that failed used to mark the queued message failed, and it was never
sent. Now the message goes back to the queue and the next pass sends it.

## Upgrading

No step beyond the usual `dbabrain upgrade-config`, which brings the shipped `shared_config_objects.json`
(where each tool's own sentence lives) up to this version.

## Changed

- **MCP tool descriptions**: each tool's description opens with its own sentence. Tools that share a request
  no longer open alike; `run-sql` and `run-sql-write` each have their own.
- **MCP input schemas**: a tool's `inputSchema` states its request's fields, `server_id` first. The fields
  the node fills in (connection, host login, policy, secrets) and those a request is refused for are not
  offered. The description no longer lists the fields.
- **MCP descriptions carry only what is the tool's own**: that `server_id` names the server and the node
  completes its login, and that an emergency operation takes `confirm` and a `reason`, are said once, in the
  server's instructions.
- **MCP `metric-batch`**: its schema is led by `server_id`; the connection facts are the node's.
- An unknown `server_id` names `list-targets` beside `/spbot_list_server_id`, so an MCP client is pointed
  at a tool it has.

## Fixed

- **Telegram**: a 5xx answer, a timeout, a reset, a TLS failure or a connection closed mid-response no longer
  marks a queued message failed. The row goes back to the queue with what it had delivered, the pass stops
  sending, and the next pass sends it; the bot's run reports Telegram as not reached instead of failing.
  Reading updates that fails leaves the rest of the pass running and the offset where it was. A message
  whose send timed out may have reached the chat, so it can arrive twice: the price of never losing one.
- **`dbabrain mcp call` and `dbabrain mcp tools` on Windows** died with `UnicodeEncodeError` when the answer
  held a character outside the console's code page and was redirected to a file. A piped or redirected
  answer is written as UTF-8; a console shows `?` for such a character. `dbabrain mcp serve` is unchanged.

## Verified

- The test suite on Python 3.12 and 3.13.
- `dbabrain mcp serve` on an empty home with no key, driven by the MCP SDK's own client over stdio: every
  tool listed, every input schema valid JSON Schema 2020-12, the tools that only read answered.
- Telegram: tests interrupt a send with each kind of failure; the message stays queued and the next pass
  sends it.
- The wheel installed into an empty Python 3.12 virtual environment: `dbabrain --version` 1.2.0,
  `dbabrain init`, `dbabrain daemon --config config.json --once` with no key - every command that needs
  none finished `done`, and those that need a key were skipped and said so; `dbabrain mcp tools` listed
  every tool.
- `ruff check .`: all checks passed. `gitleaks` over the published files: no leaks found.

## Known limitations

- **Over MCP, "read only" is a hint to the client, not a security boundary.** Tools are switched off by
  name (`disabled_tools`), and `run-sql`'s check reads the statement's text. Treat an MCP client as having
  the node's own access: connect only clients and accounts you trust, keep the approval prompts on, switch
  off the tools you do not need, and give the node logins that can only read.
- **A Telegram message can arrive twice** after a send that timed out but had reached the chat.
- **Oracle's `query-plan`** is refused: Oracle's `EXPLAIN PLAN` writes to a table.
- **PostgreSQL's top queries** need the `pg_stat_statements` extension; without it `db-activity` says so.
- **A key serves one node per email** unless it is copied; a second `key-request` replaces the first.
- **A container worker that restarts does nothing until it is unlocked**, its Telegram messages included.
- **A single node without a worker** has no command to change the store's passphrase yet.
- **Oracle's and PostgreSQL's point in time from a source whose clock is not UTC** has not been tested.
- **A PostgreSQL or Oracle restore under another name** (`RENAME` / `DUPLICATE TO`) is not supported; an
  entry mapping a name for those engines is refused.
- **After a PostgreSQL or Oracle restore the target's logins are the source's**: the inventory's password
  for the target no longer logs in until it is set again.
- **An MCP node cannot run a restore**: `restore-by-id` is not an MCP tool, by design; run it on the node.
