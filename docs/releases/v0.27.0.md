## Summary

**A SQL task whose Python program reaches the database itself can run again - with one login, not
the key to all of them.** 0.26.0 stopped handing the secret-store passphrase to the program behind
a SQL task's `input`: right for a fetcher, an HTTP client or vendor code, and wrong for a program
that does the task's database work itself on connections of its own, which then failed every run
with *No decryption key provided*. Found on the first node upgraded to 0.26.0, where a
queue-draining task failed from its first run. Such a task now asks for **its target's
connection**, which the runner has already resolved for the task's own SQL, and reads it on stdin.

## Added

- **`input.target_connection`** on a SQL command whose `input_type` is `python`: `true` writes
  `{"connection": {...}}` - the target's connection, its login included - to the script's stdin.
  Off by default; only a boolean is accepted, by `sql-command-add` and by the runner.

## Changed

- **A `common.cli` request with a wrong value or a missing required field is refused** (rules R49),
  with `error_kind` `request` and the field named, before anything runs. 0.26.0 only measured it; a
  day of real requests on a node held no such finding. Unknown keys and deprecated spellings are
  still only measured.
- **Every `input` script gets an empty stdin** unless it asks for its connection: a script that
  reads stdin gets end-of-file at once, instead of whatever the daemon's own stdin was on that host.
- The passphrase stays withheld from every script, as in 0.26.0: `DB_OPS_SECRET_KEY`,
  `DB_OPS_KEY_BASE64` and `SQLCMDPASSWORD` never reach one.
- **A record that leaves a which-thing fact to a default is refused where it is used** (rules R50,
  the owner's no-fallback rule; v0.26.0 reported these as `fallback` notices). An instance reaching
  its host states `platform`, and over SSH `cmd_access.auth_type`; an instance with an engine states
  `port`, a PostgreSQL / MySQL one `database_name`, an Oracle one `service_name`; a script SQL
  Server restore states `env.MSSQL_USER`; an SMB restore into a container states
  `target.sqlcmd_path`, and one with a certificate API its `certificate_api_token_ref` - there is no
  built-in token ref any more; a SQL Server restore states its databases, or `restore_all_databases`
  (*Upgrading* 5). Such a record fails alone, naming the field: a metric target's
  metrics, a SQL task's run, a host operation, a restore entry (with its file when active).
  `check-objects` counts each as a violation; `instance-add` and `remote-credential-add` refuse to
  write one. See *Upgrading* 6.
- **`restore-workflow --dry-run` no longer copies** (see *Fixed*). A script that ran it to stage the
  files ahead of a restore stages nothing now.

## Fixed

- **A Python `input` program that opens its own connections no longer fails every run** with *No
  decryption key provided*, once its command says `"target_connection": true` and it reads its
  connection on stdin. Proven by `tests/test_a_sql_task_fed_by_a_python_script.py` (the connection
  reaches a script that asks, on stdin only, with the passphrase still withheld; a fetcher gets
  neither; asking with no connection to give refuses before the script runs; the runner hands over
  the login it resolved, and only when asked) and `tests/test_registering_a_sql_command_and_its_targets.py`
  (`sql-command-add` keeps the field, writes nothing when it is off, refuses `"yes"`).
- **The PostgreSQL WAL archive no longer keeps every backup-history file.** Each base backup leaves
  a `<segment>.<offset>.backup` file and `pg_archivecleanup` keeps those unless told: 129 of them
  on a lab archive after three days, and `wal_files_kept=` read as WAL growing when only they were.
  Found reading a soak's retention on the lab host. They now go with the WAL they describe (`-b` on
  PostgreSQL 17+, the same name-ordered cut by hand before), and the job prints
  `backup_history_removed=`. Read on that lab before the change, nothing deleted: `-n -b` and the
  hand cut chose the same 129 files and no segment; `tests/test_a_retention_under_a_day_is_applied.py`.
- **The SQL Server backup job says what its retention removed** - `retention: <db> removed N
  file(s) past the window (<window>), below its newest full <file>` per database, on Linux and
  Windows. It deleted silently, so only the host could show the window had been applied (found in
  the same reading). `tests/test_a_retention_under_a_day_is_applied.py`.
- **`worker-run` no longer prints the passphrase.** The `[remote] $ ...` line it echoes, and the line
  a failure names, showed `--key-base64 <key>` and `-e DB_OPS_SECRET_KEY="$(echo <key> | base64 -d)"`
  in clear on the console (found upgrading a worker). Every passphrase in a shown line is `***`; the
  line run on the host is unchanged. `tests/test_a_remote_command_is_shown_without_its_passphrase.py`.
- **`restore-workflow --dry-run` copies nothing.** It ran the whole copy - tens of GB onto the
  target - and dry-ran only the restore; found asking why a rehearsal showed no `space check:` line.
  The space check runs (it only reads; a refusal is reported as what the real run would meet), the
  copy is skipped, nothing is prepared on a Windows target, and the restore and the cleanup dry-run
  what is staged now. `tests/test_backup_restore.py` (the workflow's dry run, two preflight tests).
- **Every sync of a node's configuration no longer rewrites its SQL tasks.** A catalogue a node was
  given before v0.22.0 still labelled them by `sql_name`, renamed `display_name` then, so each sync
  from either side rewrote all of them with nothing changed - every worker upgrade reported "30
  updated". `upgrade-config`'s `field-names` step now renames the catalogue's `label_field` /
  `key_fields` with the records; the shipped catalogue's own two old names (SLA policies by `name`,
  Docker connections by `engine`) are corrected.
  `tests/test_a_catalogue_names_each_field_by_its_current_spelling.py`.
- **A daemon starting against a shared store no longer closes another node's live runs.** One
  started on a master against a worker's store closed the worker's web host and two runs two seconds
  old, and the worker's status read the web host as timed out for five days while it served. The
  start-up recovery reconciles only the commands of its own `node_role`; it reads a row's owner from
  the row's `host_name` too; and a service is closed only when it is this host's with no live
  process. `tests/test_a_starting_daemon_leaves_another_nodes_runs_alone.py`.
- **The SQL-task and backup/restore sweeps read a run's owner the same way** - with its `host_name`
  column, which the SQL-task sweep's query did not even select. A row an older build wrote was
  judged on its owner at start-up and on age alone by the sweeps: this host's dead run waited for
  its timeout, another host's restore was closed at its timeout instead of after the grace. Found
  reading what the fix above left out. Same test file (the sweeps' cases).
- **One retired SMB restore entry no longer stops every SQL Server restore.** An inactive entry
  missing a required field refused the whole file - the scheduled pass, `list-restores`,
  `restore-add` - as the script-driven entries did until v0.26.0. It is kept out with its reason,
  listed under *Inactive and incomplete*, and named when asked for by id; an active one is still
  refused with the file. Found reading the review's open items.
  `tests/test_an_inactive_entry_that_cannot_be_read_does_not_stop_the_others.py` (8 new cases, 4 of
  them failing on v0.26.0).
- **A skipped restore check says why.** The workflow's last step opens each restored database it
  is told about; an entry it cannot check is skipped, and every skip read *no target login
  configured* - also over an entry whose login was there and whose `database_mappings` was empty.
  Found reading a production node's nightly restore: *0 database(s) checked, 1 entry(ies)
  skipped* after 13 databases restored, every night. Each skip now names what is missing - the
  host, the login, the databases, the secret, a port. The check asks about what the entry states:
  its `database_mappings`, or - with the new `restore_all_databases: true` - every database its run
  restored, under the backup's name (see *Upgrading* 5).
  `tests/test_a_restore_is_checked_before_it_is_called_done.py`.
- **A restore target's `sqlcmd_path` is read.** An SMB entry into a container that stated
  `target.sqlcmd_path` had it silently dropped - the loader passes an unmapped target key through
  only when the entry has no value yet, and the parser's own default `sqlcmd` always was one - and
  the path was inferred; the reference did not describe the field at all. Found writing R50, whose
  rule for that entry names exactly this field. It is a `restore_target` field now, and read.
  `tests/test_a_record_that_leaves_a_fact_to_a_default_is_refused.py`.
- **The Query Store metric reports a frequent plan regression at CRITICAL when it is one.** A plan
  that was both a single-metric WARNING and the frequent regression's CRITICAL was reported as the
  WARNING: the severity list reached the warning first. And its windows could move by a minute -
  the UTC offset was the difference of two clock calls; it is one reading now
  (`DATEPART(TZOFFSET, SYSDATETIMEOFFSET())`), in the deadlock count too, which counted hours and was
  half an hour off in a +05:30 zone. `tests/test_query_store_alert_window.py`.

## Upgrading

From v0.25.0 or earlier, read v0.26.0's *Upgrading* first.

1. **Your own scripts that call `common.cli`**: a request the reference says is wrong now answers
   `error_kind: request` naming the field instead of running. To find them before upgrading, run
   them once on 0.26.0 with `DB_OPS_REQUEST_CHECK_LOG=<file>` set and read the file.
2. Find each SQL task whose `input` script opens its own database connection (it calls
   `request_fill.sql_connection`, or reads `data/encrypted_secret_text.json` some other way). Give
   its command `"target_connection": true` - through `sql-command-add` with `"replace": true` - and
   have the script read its connection from stdin instead of resolving the login itself:

   ```python
   connection = json.load(sys.stdin)["connection"]          # one login, as the runner resolved it
   target = sql_run.resolve_stated_connection({"connection": connection}, database=args.database,
                                              what="my_task")
   ```
3. A fetcher - a script that only fetches rows over HTTP or from a file - needs nothing.
4. A script that ran `restore-workflow --dry-run` to stage the files: run `copy-backup` for that.
5. **A SQL Server restore entry states which databases it restores**: `database_mappings`, or
   `restore_all_databases: true` for every database whose FULL is on the share, each under its
   backup's name. An entry with an empty list and no flag is refused (rules R50) - add one of the
   two through `restore-add` with `"replace": true`. Either way each restored database is opened
   after the run; one that does not open fails the run and keeps its backups. PostgreSQL and
   Oracle entries restore the instance and need neither.
6. **Before upgrading, run `check-objects` on the node** (`python -m db_ops.common.cli
   check-objects '{}'`, on v0.26.0): every `fallback` notice it lists is a record v0.27.0 refuses.
   State each field it names - through `instance-add` / `remote-credential-add` / `restore-add`
   with `"replace": true` - until it lists none. An inactive record is not listed and runs nothing;
   it is held to the rule when it is switched on or used.

`SCHEMA_VERSION` is unchanged, so the store needs nothing.

```bash
pip install --upgrade dbabrain
python -m db_ops.common.cli upgrade-config '{}'                   # read the plan
python -m db_ops.common.cli upgrade-config '{"dry_run": false}'   # then apply it
```
