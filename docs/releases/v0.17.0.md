## What this release is for

Two readers, and the first one is the reason the release exists.

Somebody opened the fleet inventory page on one node and on another, and the two disagreed about
nine servers. One said `Transaction-log RPO violated on 9 server(s)`. The other printed
`4/4 DB within policy` in green over a server whose newest transaction-log backup was **168 days
old**, and raised no card at all. Same estate, same hour, same collectors, byte-identical code.

The difference was a missing file. With no `data/backup_policy.json`, no backup type is *required*
of anything, every database grades `OK`, and `compliant == eligible` falls out of that honestly.
The defect was that **"no rule required this" and "no rule exists" produced the same sentence** — so
the most dangerous configuration state a monitoring tool can be in rendered as its healthiest
possible output. The node was missing ten catalogued config files, and every `sync-config` it had
ever run reported `ok`.

The second reader had a Python script outside the tool that fetched rows from an HTTP API, opened
its own database connection, held its own copy of the credential, and was scheduled by something
else — the shape this tool exists to replace. They asked for it to be a SQL task.

## Fixed

- **A missing backup policy is a blind spot, not a pass.** `db_ops.lib.backup_policy` asks
  `policy_is_configured` before it judges anything. Without a policy the verdict is `UNKNOWN`,
  `compliant` is 0 while `eligible` still counts the databases evidence was found for, the coverage
  cell reads **No policy configured**, the badge is grey *Unverified*, and Priority Attention
  carries a card naming the file and the count of unjudged databases. **On upgrade:** a node that
  genuinely has no policy file will show that card and lose its (meaningless) green backup column
  until the file is restored, which is the point. A policy that deliberately requires nothing is
  unaffected — it is a *configured* policy and still grades `OK`.
- **A background command that was killed is no longer reported as having succeeded.** A restore
  dispatched from Telegram was interrupted fourteen minutes into a 33 GB copy and the chat was told
  *"Restore workflow completed"*. It had written no completion record, no success marker and no
  exit code — every channel it declares was silent, and silence was read as success, because
  reading it as failure had previously reported a *successful* SQL task as `Exit code: 1`. The rule
  now depends on what the command promised: one that declares how it reports completion and then
  leaves nothing is **failed**, with `unknown` where the exit code goes rather than a fabricated
  `1`; one that declares nothing is still given the benefit of the doubt.
- **An incomplete restore entry names its missing fields.** `parse_restore_config` read six fields
  by subscript, so the first one absent was the whole error text: `'prod_backup_share'`, an internal
  key naming neither the entry, nor the file, nor anything the operator had written. It now names
  every missing field at once, the entry they belong to, and the spelling each is actually written
  in — `source.backup_share`, `target.vm_import_linux_path`. The 2026-09-11 fix covered "nothing is
  configured"; this is the other half.

## Added

- **`db-ops init` writes `data/backup_policy.json`**, with the common plan already in force: daily
  FULL, a LOG backup required of any database in full or bulk-logged recovery, DIFF not required. A
  fresh install grades backups from its first collection instead of waiting to be told how. It is
  the one shipped default that must **not** be empty.
- **`sync-config` names every catalogued file the node does not have.** The count was already in
  `totals["missing"]` and printed nowhere.
- **A SQL task can be fed by a Python program: `input_type`.** `script_type` goes on saying what the
  SQL half is (`single` / `array` / `folder`); the new `input_type` (`none` / `python`) says where
  the rows come from. A python task runs one program from `assets/tasks/python/`, reads **one JSON
  document from its stdout**, and hands the rows to its own SQL as a bound `nvarchar(max)`
  parameter, in batches, through the same executor and credential as every other task. Its contract
  is four refusals: one JSON object on stdout, rows as a list under `rows_path`, diagnostics on
  stderr, and exit 0 or the task fails having sent nothing.
- **`final_script_paths`: SQL that runs once, after the last batch.** A step that rolls the loaded
  rows onward is not a row consumer, and in `script_paths` it would run once per batch.
- **`backup-add` and `restore-add`** register one entry in `data/restore_config.json` from a JSON
  request object. `env_secret_values` (and `password` / `sql_password` inside a restore's `source`
  and `target`) are encrypted straight into the store, so the field that was otherwise a plaintext
  hand-edit never reaches the disk in the clear. What is written is loaded back through the app's
  own loader before it is committed, so a refusal names the field the scheduled run would have
  failed on.
- **`remote-credential-add`** registers a host's OS login: the `users.json` `remote_credentials`
  entry, the secret, and the `cmd_access` block that names it. There was no command for this at
  all. It refuses the three ways the hand-edit goes wrong — `method: "local"` on a remote host,
  an ssh password with no explicit `auth_type`, and `platform` written inside the block.
- **`db use-store` can name the PostgreSQL store**, not only select the backend: `--host`, `--port`,
  `--database`, `--schema`, `--username`, `--password-ref`. `connection_string` is rebuilt whenever
  the target moves, because it is authoritative when non-empty — changing `schema` beside it used to
  alter the breakdown and nothing about where the node wrote.
- **`instance-add` documents `db_type: "host"`**, the machine-with-no-database record. It always
  accepted one; the help listed four engines, so every host-only record got hand-edited instead. Its
  `--key` / `--key-base64` are parsed now, too — the usage line has advertised them since the first
  day and the function read only the environment variable.

## Known not to work

- **A restore can report `done` on a database that did not come online.** The workflow's verdict
  comes from its steps returning, and a step can return having left a database mid-restore. Measured
  on a live estate: `backup_restore_history` recorded `FAILED` for one database — the
  server could not expand its log file — while the same run announced *"Restore workflow
  finished. status=done"*, and the database was unreachable afterwards. The failure is recorded; it
  is recorded in the one table nothing reads back, so `job_runs`, `ops-status` and the alerting all
  count the run as clean. **Check the target after a restore drill until this is fixed.** The next
  release adds a database-state check as the last step of a restore, for all three engines.

- **`self-status` does not name the node's timezone.** It reports what the installation *is* —
  version, host, role, store, uptime — and the zone is the one field that changes what it *does*,
  because every `time_window.from_hour` is read against it. An offset appears on the two uptime
  lines and the zone appears nowhere. `db timezone` prints the whole answer in the meantime.

- **Eight catalogued config files have no shipped seed.** `config_catalog.json` lists thirty;
  `init` writes twelve. `sync-config` now *names* the ones a node lacks (that is this release), but
  `capacity_policy.json`, `restore_drill_policy.json`, `maintenance_policy.json`,
  `sqlserver_instance_policy.json`, `metric_importance_overrides.json`, `docker_db_connections.json`,
  `sre_config.json` and `network_reservations.json` still have to be written by hand. Four of them
  are graders' policies, and only `backup_policy.json` has the guard that makes an absent policy
  read as *unjudged* rather than as a pass.

- `--force` on `db_ops.sql_tasks.runner` **blocks when the run is not attached to a terminal**. Its
  confirmation gate reads stdin; backgrounded or piped, the process selects the task and writes no
  `sql_runs` row at all. Use the plain scheduled path, which needs no gate.

## Upgrading

Nothing in this release requires a config change. A node that already has `data/backup_policy.json`
behaves exactly as before; a node without one starts saying so.
