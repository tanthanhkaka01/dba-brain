## What this release is for

**The toolkit had two names, and now it has one.** It was published as `dbabrain` and installed a
package called `db_ops`; the command was `db-ops` or `dbabrain`, every environment variable began
`DB_OPS_`, and a reader met both names on the same page. From this version everything that is the
code's own name is `dbabrain` - the package, every module path, the command, the environment
variables, the image's layout, the console's default mount - and the earlier name is not read
anywhere, as an alias or as a fallback.

What lives outside the code keeps its name: the database and schema your `store_config.json` names,
the rows the store keeps its schema version under, a folder on a host, a certificate, a docker
container or network, the marker inside the secret store. A node's configuration that names the
code is moved by `upgrade-config`, which gains a step for it.

## Fixed since v0.28.0

- **A file transfer refuses a remote path that is not absolute.** `fetch-file`, `send-file` and
  `relay-file` resolved a relative remote path against the login's home and answered `COPIED`. It
  was found when Git Bash rewrote `/opt/...` in a request into `C:/Program Files/Git/opt/...` and
  the file landed under the login's home on a Linux host. They refuse such a path before a session
  is opened, and the refusal names the rewrite when the path carries it.
  `tests/test_a_remote_path_is_stated_whole.py`.
- **`control.cli inventory-health` fetches from the worker's folder.** Its `--host-runtime` default
  still named a folder the worker had left; it follows the worker's folder now.

## Added since v0.28.0

- **`control.cli deploy-code` ships the code only.** It builds the image, loads it on the worker
  and compares its id, keeps the worker's compose file and a tar of `data/`, `assets/` and
  `config.json`, points the compose file at the new image - moving the environment names and
  container paths the rename changed, and nothing else - runs `upgrade-config` and `sync-config` in
  the new image and starts it. The worker keeps its own configuration; without `--apply` it prints
  the plan. `tests/test_deploy_code_ships_the_code_only.py`.
- **`upgrade-config` step `package-rename`** (`lib.package_rename`): a module path, a path into the
  package, the `tools/` alias (a path with either slash, as a Windows node writes it) and the name
  of an environment variable this version reads are pointed at the new name; a value that only shares the letters - a table in the store's schema, a
  host folder, an id, a secret's ref - is left as it is.
  `tests/test_upgrade_config_renames_the_package.py`.
- **Rule R51**: the code carries one name; a value that lives outside it keeps its own. Held by
  `tests/test_the_tree_carries_one_name.py`.

## Changed / breaking

- **The package is `dbabrain`.** `import db_ops` and `python -m db_ops.<app>.cli` stop working:
  use `import dbabrain` and `python -m dbabrain.<app>.cli`.
- **The `db-ops` command is removed**; `dbabrain` is the one command.
- **Every environment variable is `DBABRAIN_*`** - `DBABRAIN_SECRET_KEY`, `DBABRAIN_NODE_ROLE`,
  `DBABRAIN_HOME`, `DBABRAIN_DATA_DIR`, `DBABRAIN_TIMEZONE` and the rest. **A `DB_OPS_*` name is not
  read**: a service that still sets `DB_OPS_SECRET_KEY` starts without its passphrase.
- **The image lays the tool out under `/app/tools/dbabrain`**, and the console's default mount is
  `/dbabrain/` (a `webhost_config.json` that states its own mount keeps it).
- **Telling a published build from a private one**: both are named `dbabrain` now; `self-status`
  tells them apart by version.
- **The display name and the scratch names follow.** Help text, one log line and two page titles
  (`DBA Brain · Reports`, `DBA Brain · SLA / SLO compliance`) no longer say `DB Ops`; a transfer's
  partial file is `<name>.dbabrain_partial`, the Oracle restore's work files are
  `/tmp/dbabrain_restore.rman` and `.sql`, the PostgreSQL restore's start log is
  `dbabrain_restore.log`, and it stages in `dbabrain_staging` and copies WAL to `dbabrain_wal`
  unless the entry states `PG_STAGING` / `RESTORE_STAGING` (a `dbops_wal` or `dbops` staging
  folder left on a restore target can be removed). What is on your hosts keeps its name: the
  backup folders (`.../backup/dbops`), the RMAN tags.
- **The file that marks a restore's staging folder is `.dbabrain-staging`** for a folder marked
  from now on. The name is the entry's to state (`staging_marker`), and `upgrade-config` (step
  `earlier-defaults`) writes `.dbops-staging` into every entry that already stages on a target,
  so a folder that is marked keeps being recognised.
- **Where lab databases live is stated in `sre_config.json`** (`sre.docker_db.containers_dir`,
  `sre.docker_db.backup_mount`), and the code holds no folder to fall back to: a lab command
  takes a flag, else that block, and is refused by name when neither says. `upgrade-config`
  writes the two folders every earlier version used into a node that states none.
- **The backup certificate's default name is `dbabrain_backup_cert`.** A SQL Server backup job or
  restore that names no certificate took `db_ops_backup_cert`. `upgrade-config` (step
  `earlier-defaults`) writes that name into every record that had been leaving it to the default,
  so no existing record changes certificate; only a record added afterwards, naming none, takes
  the new one. **Run `upgrade-config` before the first backup on this version** (*Upgrading*).

## Known not to work

- Everything listed for v0.28.0 still holds.
- **The lock-scan guard needs the lock counters.** Where `sys.dm_os_performance_counters` reads 0 for
  `Lock Owner Blocks`, the guard reads 0 and the scan runs as it always did.
- **Oracle from 10g on has no collector for the process limit, tablespace free space, the pools,
  the buffer cache or rollback contention** - those are Oracle 8i files.
- `pack-files` does not check its paths the way the other transfers now do: its files are on the
  host that holds them, which may be this one.

## Upgrading

1. **After `pip install --upgrade dbabrain`, run `upgrade-config`** - the plan first
   (`python -m dbabrain.common.cli upgrade-config '{}'`), then `'{"dry_run": false}'`. Its step
   `package-rename` moves what your `data/*.json` say about the code, and its step
   `earlier-defaults` writes `BACKUP_CERT_NAME: db_ops_backup_cert` into each SQL Server backup job
   and restore that named no certificate - **do this before the first backup on this version**: a
   record that still names none would look for a certificate of the new default name. Then
   `python -m dbabrain.db.cli --config config.json sync-config '{}'`.
2. **Rename the environment variables** wherever you set them - a compose file, a service unit, a
   shell profile, a scheduled task: `DB_OPS_` becomes `DBABRAIN_`.
3. **A container deployment**: mount the tool root's folders at `/app/tools/dbabrain/...` instead
   of `/app/tools/db_ops/...`. `control.cli deploy-code` does this and steps 1-2 for a compose file
   it manages.
4. **Your own scripts** that `import db_ops` (a SQL task's `input` script, a helper under
   `assets/`) import `dbabrain`, and read `DBABRAIN_SECRET_KEY`.
5. **The console**: if your `webhost_config.json` states `"mount": "db_ops"`, the console stays at
   `/db_ops/`; change it to `dbabrain` to follow the new default.

`SCHEMA_VERSION` is unchanged, and the store keeps its database, schema and rows.
