## Summary

A restore is now reported from the state of the databases it touched, not from the step that ran
last. Registering a SQL task, a Telegram group and a Telegram user is covered by commands rather
than by editing configuration files. Several checks that could report success on a broken target
now report the fault.

## Fixed

- **A restore's verdict is computed.** The workflow ends with a `verify` phase that queries each
  database it touched; a database that will not answer is a failed restore whatever the preceding
  steps reported.
- **`restore-add` accepts a script-driven restore.** Previously it required `source` and `target`,
  which are absent from the script-driven shape used for Oracle, PostgreSQL and container-to-
  container drills.
- **`user-level --pending` grants a level to a username the node has not seen.** The level is
  adopted on that user's first message. Without the flag an unknown name is still refused.
- **Reports print addresses in full.** A render-time abbreviation produced forms that appeared in no
  configuration file and so passed every identifier check.
- **Multi-part reports survive Telegram's rate limit.** Parts are paced, HTTP 429 is waited out, and
  a message refused for the limit returns to the queue. Both outcomes are logged.
- **A forced SQL task run started without a terminal no longer waits indefinitely.** The
  confirmation prompt gives up after 120 seconds and refuses. For an unattended run pass
  `--assume-yes`.
- **`check-credentials` and `check-secret` see a legacy-Oracle target's secrets.** Both previously
  reported clean while every collection for that target failed.
- **`telegram route` refuses a JSON request** instead of searching for a notify level of that name
  and answering with an empty chat id.
- **An SLA run with no policy reports `NOT_CONFIGURED`**, not `PASSED`.
- **`metrics collect` states why it collected nothing.** `target_count: 0` covered five situations
  requiring different actions.
- **The command menu order reaches a new install.** The file written by `init` did not carry it.
- **`sla validate --notify` works on a node that has never queued a message.**
- **`/spbot_list_sql_runs` answers when called with no arguments.** A skipped optional argument left
  a hole in the request. A default declared on the parameter is now applied.
- **A SQL task whose Python step is killed reports what is known:** the task ran no SQL of its own,
  and work the program had already done is not rolled back.
- **A task runs on its own schedule.** The daemon scan and the SQL task app interval are one second,
  so neither rounds a task's `repeat_interval` up.

## Added

- **`db-status`** — whether a server is up and usable, at three depths: the instance, one database,
  one schema. SQL Server, PostgreSQL and Oracle. JSON object in, JSON object out.
- **`sql-command-add` and `sql-target-add`** — register a SQL task in two calls: what it runs, and
  where. They cover what `add-sql` cannot express: a task fed by a Python program, an array or
  folder of scripts, and additional targets for an existing task. The SQL is given as a file path or
  as text, in which case the file is written for you. Both validate before writing.
- **`{target_server_id}` and `{target_database}` in a Python step's arguments**, substituted per
  target, so one command serves several targets.
- **`telegram group-add`** — register a group that has never posted.
- **`timezone`**, and `self-status` now names the clock the node runs on.
- **A shipped seed for every catalogued configuration file.** A new install lacks none.

## Changed

**A restore that previously reported success may now report failure.** The verdict is computed from
the state of the databases rather than asserted by the last step, so restores that were failing
silently now say so. Expect the reported success rate to fall; what falls is the false part.

No other change requires action. New configuration seeds are written by `init` and do not overwrite
existing files. No store schema change ships in this release.

## Known limitations

- A backup job requires `archive_mode` and `summarize_wal` to be on for the PostgreSQL instance it
  targets. Both need that instance restarted.
- A restore does not check free space on the target before it starts.
- A store carried between tool roots brings its in-flight `running` rows.
- `--force` on a SQL task runs every target of that task, including targets with `active: false`.

## Upgrading

Install the version. `init` on an existing root adds new configuration seeds without touching files
that are already present.
