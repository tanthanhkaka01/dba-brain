## What this release is for

DBA Brain is published, and until now it never asked its operator which timezone they were in. The
answer was taken from three places, none of them configuration: the machine's `TZ` (27
`datetime.now()` call sites, including **every** `time_window` hour comparison), a hardcoded `+07`
in the reports app, and an env var nobody set. The shipped `docker-compose.yml` pinned
`TZ: Asia/Ho_Chi_Minh` into the container — that line *was* the timezone configuration, and it went
out with the image.

So a report header read `Snapshot 2026-09-07 07:32:56` with no zone on it, and a window written for
the small hours ran during the working day for anyone whose clock was not the author's.

There is now one field, `timezone` in `config.json`, and it decides two things: what every rendered
time says, and what a `time_window`'s `from_hour`/`to_hour` mean. **Minor rather than patch because
it changes what an existing tool root does** — see *Changed / breaking*, which is the section to
read before upgrading.

## Changed / breaking

**Read this before upgrading. There is one action, and skipping it changes when your jobs run.**

Add `timezone` to `config.json` before starting the new version:

```json
"timezone": "Asia/Ho_Chi_Minh"
```

An IANA name (follows daylight saving) or a fixed offset (`+07:00`, `UTC`). `DB_OPS_TIMEZONE`
overrides it per node, the way `DB_OPS_NODE_ROLE` overrides the node role — so one `config.json`
copied to a worker in another zone still works.

**Why it matters, concretely.** `time_window` bounds used to be evaluated in the *node's local
time*. They are now evaluated in the configured timezone. If the field is absent it defaults to
**UTC**, with a warning on stderr naming the file — the tool still starts. So a root running on a
host set to `+07`, upgraded without adding the field, silently moves every hour-bounded schedule
seven hours. Nothing errors. `from_hour: 1` stops meaning 01:00 and starts meaning 08:00 local.

Set the field to the zone the host was already on and behaviour is identical to v0.9.1.

Two smaller changes in the same area:

- **Rendered timestamps now carry their offset**, in one format everywhere:
  `2026-09-07 07:32:56 +07`. That replaces four different spellings, including
  `format_message_time`'s `UTC+07:00` in Telegram alerts, and the report headers that printed a
  wall clock with no zone at all. **Stored timestamps are unchanged** — still UTC
  `%Y-%m-%dT%H:%M:%SZ` on both backends. Nothing in the store was migrated or needs to be.
- **`store.report_exists_on_local_date()` lost its `utc_offset_hours=7` default** and takes
  `utc_offset_minutes` with no default. A Vietnam business calendar was a default argument in the
  store layer; minutes rather than hours because half-hour zones exist.

`docker-compose.yml` and `docker-compose.runtime.yml` no longer pin `TZ`. If you run the published
compose file and relied on that line, the `timezone` field replaces it.

`tzdata` is now a core dependency. IANA names need a zone database and Windows ships none, so
without it the same `config.json` worked in the image and raised on a Windows master. Fixed offsets
need no zone database at all.

## Added since v0.9.1

- **`timezone` in `config.json`** — required by the schema, defaulting to `UTC` when absent so an
  install that predates the field still starts. A value that is present and unparseable raises when
  the config is read, naming the file, the value and the two accepted shapes; the alternative is an
  estate of reports stamped in a clock nobody questions for a month.

- **`db_ops/lib/timezone.py`** — the one implementation. Pure, imports nothing from `db_ops`, and
  bound once by `db_ops.config.parse_config`, so no app parses the field and no producer is handed
  a timezone it has no other reason to know about. The producer that gets missed in that kind of
  plumbing is exactly the one that prints a second clock.

- **`runtime_nodes`** (store schema version 3, additive on both backends) — one row per node
  recording which clock it is running on, plus its role, hostname and version. Master and worker
  share one store and each reads its own `config.json`, so "is the estate on one clock?" had no
  answer the store could give — and a `time_window` firing at the wrong hour on one node looks
  exactly like a schedule that was never due. It keeps the **declaration** and the **resolved
  offset**: under daylight saving the second changes twice a year, and only the first can be
  written back into a config file.

- **`common.cli timezone`** — reports what this node resolved. Reads nothing, writes nothing, so it
  still answers when the store is down, which is when the question gets asked.
- **`db.cli timezone --record --list`** — writes that answer into `runtime_nodes` and reads the
  cluster back. It lives in `db.cli` and not beside the first because `common` may not import `db`;
  the architecture test caught that during this work.

## Fixed since v0.9.1

Everything below was found by working through the call sites, and each is the same defect wearing a
different hat: a wall clock read from somewhere nobody configured.

- **`VIETNAM_TZ`** — a `+07` offset compiled into the reports app, deciding both the backup-health
  run-hour window and the clock in the report header, for every operator of a published tool.
- **Report filename stamps disagreed with the rows they described.** The `YYYYMMDD_HHMMSS` prefix
  came off the host clock while the store row was UTC, so a report built at 14:48 `+07` was
  `20260905_144812_*.html` beside a row saying `07:48:12Z`. Both are now the configured zone, and a
  test asserts the stamp and the header inside the file agree.
- **The log file carried two clocks.** `logging`'s `%(asctime)s` stamps with `time.localtime` while
  the daemon's own event lines had moved to the configured zone — interleaved, in one file, with
  nothing on either line saying which. The formatter's `converter` now reads the same zone, and so
  does the daily rotation boundary, so a file named `_20260907` holds the day its lines claim.
- **Backup retention kept more than it was asked to.** The cutoff was `datetime.now(timezone.utc)`
  compared against file mtimes **as the database server printed them** — server-local, no zone — so
  at `+07` it kept seven extra hours. Both sides are on one clock now.
- **Backup ages were measured on the wrong clock** in `lib/backup_policy.py` and
  `reports/inventory_health.py`, in the same shape: a naive `datetime.now()` subtracted from a naive
  `latest_finish` read off a database server. Correct only while the host happened to match the
  servers, which on the worker was true only because of the compose `TZ` line this release deletes.
- **A backfilled report covered the wrong day.** `?date=2026-09-07` built a **UTC** end-of-day, so
  at `+07` it swept in the first seven hours of the operator's 8th and dropped their evening.
- **Two report pages rendered in the viewer's browser zone.** `server_report.html` drew one axis
  with `toLocaleDateString` and one label in UTC, so the same file read differently in Hanoi and in
  Chicago. Both pages now have the offset baked in at build time — a report is a file that gets
  shared, and it has to say the same hour to everyone who opens it.
- **Six listings stripped the `Z` and left the rest**, which is the worst of the three options: the
  reader got a wall-clock time that was neither theirs nor labelled. One function now.

## Also in this release

**The store declaration said something untrue.** `data/store_config.json` read "Create the schema
with `python -m db_ops.db.cli init`", which is not true for a database that does not exist. Measured
against PostgreSQL 18.6, and now documented in `docs/01_runtime_store.md`, both `store_config`
files, `data/README.md` and the PostgreSQL quickstart:

| | SQLite | PostgreSQL |
| --- | --- | --- |
| The file / database + schema | **created for you**, on first use | **must already exist** |
| The tables, indexes, seed rows | created on first use | created on first use |
| A login | none | `username` + `password_ref`, both already in place |

An absent database fails at connect (`3D000 database "..." does not exist`) rather than being
created silently. Two error strings in that documentation were measured rather than asserted, and
one of them was wrong when first written: an unknown role gives `28P01 password authentication
failed`, **not** "role does not exist" — PostgreSQL will not tell you which of the two it was. A
role with `USAGE` but not `CREATE` on the schema connects successfully and then fails on the first
DDL with `42501`, which reads like a bug in the toolkit rather than a missing grant.

The quickstart had claimed switching to PostgreSQL was "a one-word edit of `backend`". It is not,
and it now says what else is needed.

## Known not to work

- **A stored timestamp written by an older version is unaffected and correct**, but a *report file*
  archived by an older version carries a stamp in that node's host clock. `label_from_file_stamp`
  labels it with the configured zone, so a page archived before this release can show an offset it
  was not built in. Only the archive is affected; nothing recomputes from it.
- **`DB_OPS_MESSAGE_UTC_OFFSET_HOURS` still works and is deprecated.** It is read only when neither
  `timezone` nor `DB_OPS_TIMEZONE` is set, so an install that set it keeps its clock across the
  upgrade. It will go in a later release.
- **A fixed offset does not follow daylight saving**, by definition. `+01:00` is Berlin in January
  and wrong in July. Use the IANA name unless the zone genuinely has no DST.
- **The `runtime_nodes` row is written at daemon start-up and by `db.cli timezone --record`** —
  nothing else writes it, so a node that has not restarted since upgrading does not appear. Failures
  writing it are swallowed on purpose: turning "could not note the timezone" into "the daemon did
  not start" would be worse than the gap.
- Everything listed as open in `v0.9.1` is still open: `run_copy_backup` ignores `dry_run`; a
  reports directory the process cannot write leaves the fixed latest URL 404; nothing outside
  db_ops notices db_ops being absent; an app command's `error_text` carries the exit code and not
  the reason.
