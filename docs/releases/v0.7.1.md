## What this release is for

Nothing here is a new capability. All four fixes came out of one exercise — running a real estate
from a brand-new install for eleven hours while the usual node was stopped, and reading the two
stores side by side afterwards — and every one of them had been failing quietly for days.

That is what they have in common, and it is the reason to upgrade. A store that stops pruning says
so in one log line per sweep. A transport that cannot authenticate is recorded as a metric warning.
A query that is valid on one backend and not the other only raises on the path nobody takes by
hand. None of them announces itself, and each was found by comparing two things that should have
agreed rather than by anything reporting a fault.

Upgrading needs no action. No configuration changes, no command changes, no schema migration to
run — one table is created automatically the first time the sweep needs it.

## Fixed since v0.7.0

- **`job_runs` never pruned, in two layers.** The sweep moves aged rows into `job_runs_history`
  and deletes them, but `app_command_requests.job_run_id` is a foreign key with no `ON DELETE`, so
  one finished "run now" request pointing into the batch failed the whole delete — and the daemon
  swallows a failed sweep by design, because housekeeping must never stop the scheduler. The
  referencing requests now move into `app_command_requests_history` first, in the same transaction.

  That alone would still not have pruned anything: `RunRequestStore` creates that archive table,
  and only when the console runs, which the sweep does not. Every store that had used the console
  on an earlier build therefore had the requests table, the foreign key, and no archive — and the
  fix read that as "nothing to move". The sweep now creates the table when it finds it missing,
  once before the first batch rather than inside one, because the copy and the delete being a
  single transaction is what stops a row being archived twice.

  Both backends behave identically here: SQLite refuses the delete with
  `FOREIGN KEY constraint failed` exactly where PostgreSQL refuses it with `23503`.

- **A WinRM failure blamed the host when the cause was a missing dependency.** Without the
  `[winrm]` extra there is no `pypsrp`, and PowerShell remoting falls back to driving
  `Invoke-Command` through a local PowerShell. Against some Windows hosts that backend cannot
  authenticate, and it hands back Windows' own wording — `0x8009030e ... A specified logon session
  does not exist`, *"the provided credentials are not valid on the target server"*, *"add the
  server name to the TrustedHosts list"*. Every sentence points at the host. Nothing said the call
  had run on the weaker of two backends.

  The fallback now appends one line naming the extra to install, and only when it fails to
  authenticate — a fallback that works is not worth a word, and a hint that also fires on a
  script's own non-zero exit is one people learn to ignore. `docs/installation.md` now says to
  name every transport the estate uses, not only its databases.

- **The daily-report guard raised on PostgreSQL and worked on SQLite.**
  `report_exists_on_local_date` compared with SQLite's `datetime(created_at, '+7 hours')`;
  PostgreSQL has no `datetime(text, text)` and the dialect translator does not rewrite it, so
  `db-ops reports create-backup-health-report` without `--force` failed with `42883 function
  datetime(text, unknown) does not exist`. The scheduled path passes `--force` and never reached
  it, which is why it survived. The local day is now computed in Python and bound as a plain UTC
  range: the same answer on both engines, and one an index on `created_at` can serve. A
  `local_date` that is not a date is refused rather than answered `False` — "no report today" is
  the answer that lets a duplicate out.

- **An abandoned SQL task run stayed `running` for good once a later run replaced it.** Shipped in
  v0.7.0 and repeated here because the notes for that release were completed after it was cut: the
  sweep read the newest run per task rather than every run that never ended, so a death inside the
  target's timeout window became invisible. It now judges every `running` row on its own age, and
  the alert carries both the run's start and the time the message was written, with the offset
  shown.

## Known not to work

- **A broken WinRM transport is still recorded as a metric warning.** The collector writes
  `WARNING: Command exited with code 1` for a host it cannot reach at all, which looks exactly like
  a threshold breach — 148 such rows on one estate before anyone read them as a dead transport. The
  hint above makes the cause findable once you are looking; it does not make the metrics say it.

- **The schedule still cannot see a second scheduler.** Two nodes pointed at one store will both
  run the same due work. Stop one before starting the other.
