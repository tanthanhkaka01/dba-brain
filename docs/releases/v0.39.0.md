## What this release is for

**A restore never overwrites what it was not told to.** Every restore entry states
`overwrite_existing` - true or false, required, false unless set - and without `true` nothing is
replaced on any engine: a SQL Server database of the landing name in any state stops the restore, a
PostgreSQL data directory or an Oracle database holding data of its own stops it before the target is
touched. A target the inventory does not mark as lab, dev or production is not taken for *not
production*: it is refused until its record says what it is. The fields that decide what a restore
does are required, each refused by name when unstated.

**A restore is held to where it stopped.** After the check, the target's own record (`restorehistory`)
is compared with what the restore planned - the moment of a point in time, or the end of the chain -
and a database that opened clean somewhere else fails the run. A point in time is handed to SQL
Server in the source server's clock: from a server on +07 it landed seven hours early and said done.

**A restore keeps the chain it applied and says every step.** Every backup file a restore applied is
recorded in order (`restore_chain_files`): applied, skipped with SQL Server's reason, or failed. The
chat gets the flow a backup has - the copy, each file as it goes in (full, diff, each log), the check,
the clean-up - and the backup page and each server page list the restores and the files each applied.

**A failed restore is continued, and leaves nothing in the clear.** A database a failed run left
restoring goes on from the file after the last one the target applied; a restore that worked deletes
the plain files it decrypted, and those an earlier failed run of its entry left.

## Changed since v0.38.0

- `overwrite_existing` is **required** on every restore entry and **off unless set**; without `true` a
  restore replaces nothing, on SQL Server, PostgreSQL and Oracle. **To do on upgrade:** run
  `upgrade-config` - it writes `false`, never `true`.
- A script-driven SQL Server restore entry states its databases and the name each lands under
  (`database_mappings`) or `restore_all_databases: true`. **To do on upgrade:** `upgrade-config` moves
  `env.MSSQL_DATABASES` into the fields.
- A restore entry states `allow_production_target`, `checkdb`, `copy_selection` and `space_check`;
  `upgrade-config` writes the value each entry ran on.
- A restore onto a target that is not in the inventory, or whose record states no `environment`, is
  refused unless the entry allows production; `instance-add` requires `site` and `environment`.
  **Nothing is written for you** - state each target's environment.
- The words a report page shows are data (labels, health areas, the fleet cards, each metric's *What
  to do*), worded for the server's operating system and engine; the OS leads the server page's host
  line. **To do on upgrade:** `upgrade-config` (`report-texts`).
- A restore's messages follow its flow - both the script-driven restore and the share-driven one -
  with one message per file it applies, a SQL Server log included.
- On the repository, an incremental that needs its whole chain expires with it.
- A share-driven restore started by hand takes its run claim.
- A backup job's `timeout` is stated - 0 is no limit, nothing is an hour by default. **To do on
  upgrade:** `upgrade-config` writes 3600 into a job that states none.
- `overwrite_existing: true` under a lockdown is refused before the copy, naming the lockdown.
- No secret enters through MCP: a request carrying one is refused; `secret-set`, `ai-key` and the
  commands that need an age identity are no longer MCP tools.
- A backup file's restore column says what happened to that file - `restore done`, `restore fail` with
  its reason, `skipped` - and how many restores were done and failed; never the run's bare phase.

## Added since v0.38.0

- `restore_chain_files` (catalog schemas 8 and 9): every file a restore applied, in order, with its
  result - `planned`, `applied`, `skipped` (a log the restore passed over and still reached its end)
  or `failed`. The catalog upgrades itself the first time the new version opens the store.
- A restore's dry run says where each database lands and what the target holds under that name, and
  plans on a fresh target; a chat can ask for it.
- The backup page's *Restores* section, and the same on each server page.
- `/spbot_offload` - a backup entry's repository pass from a chat; `telegram set-menu` - the bot's
  "/" menu from the node's own commands.
- The AI assistant tells the restore half of the new flow.
- A restore from the repository onto SQL Server running natively on Windows (over OpenSSH).
- `dbabrain ai-key`: the AI assistant's key stored and the assistant switched on, in one command -
  the first step of the guide; and the docs say how a model reaches the estate (no public IP, no
  inbound port, no server).

## Fixed since v0.38.0

- **A SQL Server point-in-time restore from a server not on UTC landed hours early and said done** -
  on both restore paths. A moment at or after the newest log is replayed to that log's end.
- **A share-driven restore could open a database at a gap in its logs and say done**: a log refused
  as too recent was passed over whatever followed it.
- A failed restore could not be continued: its database, left restoring, refused the next run.
- A restore's plain decrypted files stayed on the target for the whole retention.
- A restore left `sudo` authentication errors in its source host's journal.
- `restore-candidates` read every chain of the new flow as unusable; a point-in-time restore copied
  the whole backup directory; a restore from the repository onto another server kept the source's file
  paths; `/spbot_restore` was stopped at 2 hours.
- `dbabrain mcp serve` without its extra named a package PyPI does not have.
- The scrub engaged the lockdown over files a script removed on its window's last seconds.
- A restore's staging kept the files a run had just copied (a plain copy from a source that never
  encrypts), and the retention sweep kept them as unknown.
- A PostgreSQL point-in-time restore from the encrypted repository found no base backup.

## Known not to work

- **Oracle's and PostgreSQL's point in time from a source not on UTC** has not been run on a host: both
  were run against UTC sources and stopped at the moment asked; SQL Server's was run from a +07 source.
- **A PostgreSQL or Oracle restore under another name** (`RENAME` / `DUPLICATE TO`) is not built; an
  entry mapping a name for those engines is refused.
- **An Oracle restore from the repository** is not built: an Oracle entry states `restore_from:
  server` (the duplicate reads the source host's RMAN folder over SSH).
- **After a PostgreSQL or Oracle restore the target's logins are the source's** - the whole instance
  is the source's; the inventory's password for the target no longer logs in until it is set again.
