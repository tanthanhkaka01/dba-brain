| Artifacts | PyPI wheel + sdist, `ghcr.io/tanthanhkaka01/dbabrain:1.1.0` |

## What this release is for

**What an AI agent can read, and what it needs a key for.** Four new commands give an agent what a DBA
reads first when something is slow: `table-info` (a table's columns and indexes), `object-source` (a view's
or a procedure's text), `db-activity` (what the server runs now: requests, blocking, waits, top queries) and
`query-plan` (a statement's estimated plan, compiled and never run), on SQL Server, PostgreSQL, Oracle and
MySQL. Each is a command and an MCP tool. And the MCP server now starts without a dbabrain key: the tools
that only read answer, and a tool marked destructive says how to get the key.

**What an MCP request may reach.** Every command stays a tool, and a request can no longer reach past it:
it cannot state how a server is reached, slip unread text into `run-sql`'s statement, or write outside the
node's output folders. `run-sql` is no longer marked read-only, because it runs with the rights of the login
the node stores for that server.

**Lock holders on a busy SQL Server.** `LOCK_TRANSACTION_HOLDERS` used to skip a server above its lock
limit and wrote a row per lock into tempdb while it read them. It now groups the locks as it reads them,
and above the limit it samples them, so the transactions holding locks are named at any count.

## Upgrading

1. An Oracle bridge's secret (`sql_access.secret_ref`) is read from the secret store only, no longer from
   an environment variable of that name: store it with `secret-set` before upgrading if it was there.
2. Upgrade the code before a `metric_definitions.json` that states the four new `sql_settings` of
   `LOCK_TRANSACTION_HOLDERS`; its item `lock_scan_skipped` is now `lock_scan_sampled`, graded by its holders,
   and `lock_scan_skip_above` is 1,000,000.

## Added

- `table-info`, `object-source`, `db-activity` and `query-plan`, as commands and MCP tools that read. Each
  takes a `server_id`; names in a request are written into the SQL as literals.
- `dbabrain mcp tools` marks each tool `needs key` or `no key`.

## Changed / breaking

- **MCP without a key**: `dbabrain mcp serve` and `dbabrain mcp call` start on a node with no dbabrain key.
  A tool that only reads (`readOnlyHint`) answers; a tool marked destructive - `run-sql` and `run-sql-write`
  among them - is refused before any of it runs, with how to get a key. `dbabrain mcp connect` still needs
  one.
- **MCP requests**: a `sql_access` route in any tool's request is refused (the inventory's is used);
  `define` is put into the statement before `run-sql`'s check; a tool that reads writes only under
  `runtime/output/` or `runtime/instance_bundles/`.
- **MCP `metric-batch`** takes a `server_id`. It runs no command where `run-cmd` is switched off, and only
  reads where `run-sql-write` is. `metric-batch`, `guide` and `inventory-summary` are marked as changing
  something; `key-status` as reading.
- **MCP `read-file`** reads no secret file of the node and answers no file holding a stored secret.
- **MCP `run-sql`** is marked destructive: it runs with the rights of the stored login, DML and DDL included
  where that login has them; its SELECT check guards against a mistake, not against the login.
- A login a node fills in goes only where its inventory's `sql_access` sends it.
- `LOCK_TRANSACTION_HOLDERS`: CRITICAL is a holder's age or who waits on it, no longer the lock count.

## Fixed

- `LOCK_TRANSACTION_HOLDERS` wrote a row per lock into tempdb while reading them, which held up other
  sessions when a server held more than a million write locks. The locks are grouped as they are read; the
  sample's shares were compared with a full count of the same locks.
- `seal-ssh-key` on an install without the `[ssh]` extra said `Need bcrypt module`; it names the extra.
- A new install's `check-references` reported the assistant's chat as dangling until one was configured;
  it says not configured.
- A Windows share path holding a quote ended the `smbclient` command it was put into; it is refused.

The changelog has every item: [`CHANGELOG.md`](../../CHANGELOG.md).

## Verified

- The test suite on Python 3.12 and 3.13.
- `table-info`, `object-source`, `db-activity` and `query-plan` against SQL Server 2022, PostgreSQL 18,
  Oracle 23 and MySQL: every view answered, but PostgreSQL's top queries without `pg_stat_statements` (said
  so) and Oracle's plan (refused by design); a statement that sleeps eight seconds was planned in 0.2 s.
- The MCP server on a node with no key: a tool that only reads answered, `run-sql`, `run-sql-write`, `run-cmd`
  and `backup-database` were refused before running, and the same `run-sql` ran once a signed key was in the
  store.
- The wheel installed into an empty Python 3.12 virtual environment: `dbabrain --version` 1.1.0,
  `dbabrain init`, `dbabrain daemon --config config.json --once` with no key - every command that needs
  none finished `done`, and those that need a key were skipped and said so.
- `ruff check .`: all checks passed. `gitleaks` over the published files: no leaks found.

## Known limitations

- **Over MCP, "read only" is a hint to the client, not a security boundary**, and from this version it is
  also what a node without a key answers. Tools are switched off by name (`disabled_tools`), and `run-sql`'s
  check reads the statement's text. Treat an MCP client as having the node's own access: connect only
  clients and accounts you trust, keep the approval prompts on, switch off the tools you do not need, and
  give the node logins that can only read.
- **Oracle's `query-plan`** is refused: Oracle's `EXPLAIN PLAN` writes to a table.
- **PostgreSQL's top queries** need the `pg_stat_statements` extension; without it `db-activity` says so.
- **A key serves one node per email** unless it is copied; a second `key-request` replaces the first.
- **A container worker that restarts does nothing until it is unlocked**, its Telegram messages included.
- **A single node without a worker** has no command to change the store's passphrase yet.
- **Oracle's and PostgreSQL's point in time from a source whose clock is not UTC** has not been tested.
- **A PostgreSQL or Oracle restore under another name** (`RENAME` / `DUPLICATE TO`) is not supported; an
  entry mapping a name for those engines is refused.
- **After a PostgreSQL or Oracle restore the target's logins are the source's**: the inventory's password
  for the target no longer logs in until it is set again.
- **An MCP node cannot run a restore**: `restore-by-id` is not an MCP tool, by design; run it on the node.
