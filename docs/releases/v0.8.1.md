# v0.8.1 — three ways the tool changed something it had promised not to

| | |
| --- | --- |
| Date | 2026-09-05 |
| Previous | `v0.8.0` |
| Python | 3.12, 3.13 |
| Artifacts | PyPI wheel + sdist, `ghcr.io/tanthanhkaka01/dbabrain:0.8.1` |

## What this release is for

Three defects found by *using* 0.8.0 on the day it shipped, all of the same family: the tool did
something other than what it said. A dry run deleted files. A page that publishes a report deleted
the report. A command that answers a person answered twice and Telegram cut it in half.

None was found by the suite, and each is fixed with a test that was checked against the old code
first — two of them because the first version of the test passed with the defect still in place.

If you run this on Windows, or in any container where the process cannot create a symlink, **the
web console did not work at all in 0.8.0** and this is the release that fixes it.

## Fixed since v0.8.0

- **Every report URL answered 404 on Windows, including the timestamped ones.** Two things are
  symlinks: `webroot/<mount>`, which is what puts the reports under `/report_dba/`, and
  `database-inventory.html`, the fixed URL the reports, the SLA page and `/spbot_self_status` all
  hand out. Both need `SeCreateSymbolicLinkPrivilege`, which an ordinary Windows account does not
  hold, so both failed with `WinError 1314`, logged a warning, and the server went on serving an
  empty directory.

  The module's own docstring is what let this survive: it said failures were *"logged, not fatal,
  so the server still serves the timestamped files directly"*. It reads as a graceful degradation
  and it was total — nothing served.

  Neither symlink is required now. The mount prefix is resolved in the request handler when the
  link is absent, and the latest link falls back to copying the newest report over itself.

- **The failure path deleted the file it was meant to publish.** `refresh_latest` unlinked the
  existing entry and *then* attempted the symlink, so where a symlink is refused each request for
  the link removed what was there and put nothing back — and the link is refreshed on every request
  for it, so a correct file placed there by hand survived exactly one page view. "Already current"
  is now decided before anything is removed, for a copy as well as for a symlink.

- **`restore-workflow --dry-run` deleted backup files.** The workflow passed `dry_run` to the
  restore step and called `run_delete_backup(step_config, logger=logger)` — no flag, and the
  function had no parameter to receive one, so all three delete engines removed files. Found by dry
  running a real restore drill before the real one: it removed 26 files while reporting itself as a
  plan. They were past retention and the next real run would have taken them, which is why nothing
  was lost and why nobody had noticed. The flag reaches every engine now.

  Still open and stated rather than half-fixed: **`run_copy_backup` has no `dry_run` either**, so a
  dry run does still pull the files across. That is additive rather than destructive, and it is
  four engines' worth of change.

- **`/spbot_list_my_commands` and `/spbot_list_sql_runs` replied twice.** Both printed the human
  listing and then emitted the JSON envelope carrying the same listing again. The bot relays
  `{stdout}` verbatim, so the reply was ~4300 characters, over Telegram's limit, split into two
  messages with the second one pure noise. `common/cli` settled this in 2026-08-16 —
  `format: "txt"` prints the listing and returns, the default prints the envelope alone — and
  `db.cli` never adopted it. Both commands take `format` now and both bot configs pass `"txt"`:
  760 characters instead of 4300, one message.

## Changed / breaking

Nothing an existing tool root must do.

- On a platform where symlinks work — Linux, and Docker on any host tested — behaviour is
  unchanged: symlinks are still preferred and still used, so no report is duplicated.
- `db-ops db sql-run-history` and `telegram-command-history` now print **either** the listing
  (`"format": "txt"`) **or** the envelope, never both. A caller that parsed the JSON is unaffected;
  a caller that read the leading text lines should ask for `"format": "txt"`.

**The web fix measured on four deployment shapes**, with the real functions rather than fixtures —
the three URLs a person opens (the fixed latest link, a timestamped report, a stable-named page):

| Shape | mount | latest link | URLs |
| --- | --- | --- | :-: |
| Windows, native | prefix resolved in process | copy | 200 / 200 / 200 |
| Ubuntu, root | symlink | symlink | 200 / 200 / 200 |
| Docker, non-root (uid 1000) | symlink | symlink | 200 / 200 / 200 |
| Docker on Windows, NTFS bind mount | symlink | symlink | 200 / 200 / 200 |

On 0.8.0 the first row is 404 / 404 / 404.

Nine tests added, every one of them run against the old code before being kept. Two are worth
naming because their first versions were green while the defect was live:

- the "latest link is not rewritten when it is already current" test compared the link's mtime
  across two refreshes — and `shutil.copy2` carries the source's mtime across, so the number it
  watched could not move. It counts the copies now.
- the `db.cli` output guard required a `print` of a computed value to be followed by a `return`,
  and `print(listing); return response.emit(...)` satisfies that while being exactly the defect. It
  requires the branch to end *without answering again*, and was checked against both shapes.

The suite also gained the half it never held: the webhost tests all either built the mount as a
real directory or forced `symlink_to` to fail, so nothing pinned the symlink path that Linux
actually uses. Two tests do now, skipped where the account cannot create one — 25 passed + 2
skipped on Windows, 27 passed in a Linux container.

## Known not to work

- **`run_copy_backup` still ignores `dry_run`** (above). A dry run of `restore-workflow` copies.
- **A reports directory the process cannot write** leaves the fixed latest URL 404 — neither a
  symlink nor a copy can be created there. Measured in a non-root container. The stamped reports
  and stable-named pages still serve. That configuration cannot produce reports in the first place,
  so it is a gap rather than a case.
- **Nothing outside db_ops notices db_ops being absent.** `APP-CONTROL` watches the apps from
  inside a running daemon, so the one condition it cannot report is no daemon at all — an estate
  went four hours uncollected on 2026-09-05 in silence. Unchanged here.
- **An app command's `error_text` is the exit code and a config banner.** The reason — which
  database, which job, which server message — is in a different `job_runs` row that nothing points
  at, so `ops-status` says "1 failing" and sends its reader looking. Unchanged here.
- Everything listed as open in `v0.8.0` is still open.
