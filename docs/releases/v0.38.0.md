## What this release is for

**A backup file is only ever moved or deleted with its facts.** Every copy of a backup states the
file's name, bytes and sha256 and lands only when the streamed bytes match; every delete of a
backup file is one file, one command, with the facts its backup recorded, checked on the host
before it is removed. The old commands that deleted by pattern, by folder or by mirroring refuse to
run and name what replaces them. On that base, a backup now travels to the repository encrypted in
the copy itself, proven by decrypting it back before its source is released, and an offload cut
midway picks itself up.

**Claude works on the estate through MCP** - `dbabrain mcp serve` for Claude Code and Claude
Desktop, and `mcp connect` / `serve --http` for a connector - with every command's own gate kept and
every answer redacted of the secret store's values.

**The AI assistant has a name, and answers how to run a backup or a restore by hand**: the exact
dry run, run and watch lines for one entry, built from that entry's configuration, and only the
lines the asker's Telegram level may run.

## Fixed since v0.36.0

- **A SQL Server Express instance could not be backed up.** Both SQL Server backup scripts wrote
  `WITH COMPRESSION`, which Express refuses (error 1844). Found reading an Express host before
  moving it onto the new flow; the scripts now ask the instance its edition and leave compression out
  for Express alone. The first FULL and its logs on that instance ran `DONE`.
- **`backup_restore offload` started by hand took 100 files per entry**, whatever the entry's
  `offload_files_per_pass` said - the flag's default replaced it. Found writing the assistant's
  backup runbook; a hand run now takes the entry's number, `--limit N` still overrides it.
- **A dry run of `restore-by-id` announced a restore** to the entry's group (*started*, *finished:
  done*). It now says it is a dry run at both ends. `restore-on-demand --dry-run` of a script restore
  restores nothing.
- **A restore's copy that could not start said the wrong thing**: "will not fit" was retried and
  reported as *is not on the target after the copy*. A refused round now ends the run with its own
  sentence.
- **The read-only SQL check let four kinds of call through** - a function named in quotes, a
  statement handed over as text (`query_to_xml`), an Oracle package's function (`utl_http`,
  `dbms_xmlgen`, `httpuritype`) and MySQL's `sleep` / `benchmark` / `load_file` / `get_lock`. Found
  by asking the public demo's assistant for an OS command, a file, a write and another account's
  data; each is refused now, and the packages that only read still go.
- **A differential or a log written after its full was released to the repository** was linked in
  the catalog to an older full still on the server, or to none. New rows link to the newest full; the
  backup page reads a chain by time.
- **A WAL or LOG entry beside its full entry released nothing at its source**: the newest chain was
  read per entry, and a log stream's entry has no full. It is now the database's on its server.
- `db-status` said UNKNOWN for every Oracle instance and PDB; `trace-session` on a target that is not
  SQL Server failed with a syntax error and now names what to read there instead.
- A PostgreSQL restore of a cluster with no WAL archive no longer fails copying one; `pg_amcheck` and
  `pg_verifybackup` are found under `/usr/lib/postgresql/<major>/bin`; every lab database container
  runs under Docker's init.

## Added since v0.36.0

- **`dbabrain mcp`** - a local MCP server (`pip install "dbabrain[mcp]"`, `dbabrain mcp serve`): one
  tool per `common.cli` command plus `store_schema` / `store_query`, a request completed from a
  `server_id` so Claude never sees a password, a destructive command still refusing without its
  `confirm` / `reason`, every answer redacted and capped, every call a `job_runs` row. `mcp connect`
  and `serve --http` reach the same tools from a connector. `docs/16_mcp_app.md`.
- **Encrypted on the way to the repository** (`offload_encrypt`): the copy reads the bytes once at
  the source, holds them to the backup's size and sha256 as they stream, and lands them only as
  `<file>.age`; the source is released only after the `.age` decrypts back to the backup. A large
  FULL is read about four times on its way to release instead of about eight.
- **An offload cut midway resumes**: an orphan `.age` is adopted once it decrypts back to the
  catalog's file, a file another pass is still encrypting waits instead of being encrypted twice,
  and a partial of a dead run is named by the repository check.
- **A delete by facts, one file at a time** - `common.cli delete-verified-file(s)`,
  `delete-empty-folder(s)`; **a copy by facts** - `copy-files` with `overwrite` required; a
  restore's staging as `prepare-staging` -> `copy-files` -> `finish-staging`.
- **The repository** keeps `<offload_folder>/<server_id>/<db_name>/...`, encrypted per server with
  keys that expire for encrypting and never for decrypting, a retention in seconds per file type
  (`offload_retention`), a check of every pass against the catalog (`offload_repository_check`),
  and SFTP for a Windows server reached over SSH (`offload_transfer: sftp`). A restore from an
  encrypted copy decrypts on its way to the target.
- **The certificate vault**: a SQL Server backup certificate pair is read twice, kept encrypted in
  the runtime store, also written as an age file a recovery key opens, and only then - when asked -
  deleted on its server. A certificate is never copied with the backups.
- **PostgreSQL base backups are TAR, compressed on the server** (PostgreSQL 15+): a few files, about a
  sixth of the bytes; a restore reads both forms.
- **Who can take a database's files**: `SECURITY_DATA_ENCRYPTION` and `SECURITY_HOST_ADMINS`, read
  hourly; a change - an account added to an admin group, a database's encryption changed - is the
  alert. A production instance on a Developer, Express or Evaluation edition is named.
- **The backup page** shows each backup's repository copy, a timeline from written to released, *On
  the server now*, the newest differential, and a differential's or log's restore chain with whether
  every file can still be had.
- **The assistant's name is `assistant_name`** in `data/ai_assist.json` (shipped `Phanes`), and its
  read-only tool `backup_runbook` answers how to run one backup or restore entry by hand: the CLI,
  the master's `worker-run` form and the Telegram command, dry run first, what each run touches and
  where to watch it. A changing line is given only to a Telegram level that may run the bot command
  that does the same.
- A backup's Telegram messages follow its flow: step 1 the backup, steps 2-5 the repository pass in
  one message, a failed step named with why.

## Changed / breaking

- **The old delete and copy commands refuse to run**: `delete-files`, `prune-staged-backups`,
  `copy-backup-dir`, `backup-chain`, and `delete-file` without `"force": true`; `prune-backup-files`
  answers its plan and refuses `delete`. Each refusal names its replacement.
- **A restore entry stating `copy_mode: "tar"` is refused** by name.
- **`offload_retention_full` / `_diff` / `_log` are refused**; `offload_retention` (seconds per file
  type) replaces them, and `upgrade-config` writes it.
- **A 0.36 `data/ai_assist.json` is refused** until `upgrade-config` writes `assistant_name` and
  `backup_runbook_enabled`; until then the assistant's job does not answer.
- **New core dependency: `pyrage`** (age encryption), installed with the package.
- A plain (not TAR) PostgreSQL base backup stages slower on a restore than it did through one tar
  stream: it is now one checked copy per file.
- The runtime store gains two tables (`backup_certificates` and the repository's key and encryption
  tables) the first time they are used; nothing existing changes shape.

## Upgrading

1. **`pip install --upgrade dbabrain`, then run `upgrade-config`** - the plan first
   (`python -m dbabrain.common.cli upgrade-config '{}'`), then `'{"dry_run": false}'`. It writes
   `assistant_name` and `backup_runbook_enabled` (`stated-ai-assist`), `offload_retention` per type
   (`retention-per-type`), `data/mcp_tools.json` (`stated-mcp-tools`) and the new required offload
   fields. Then `python -m dbabrain.db.cli --config config.json sync-config '{}'`.
2. **A script of your own that calls `delete-files`, `delete-file` without force, `copy-backup-dir`
   or `backup-chain` is now refused.** Call `delete-verified-file` with the file's facts (or
   `delete-file` with `"force": true`, once per file), and `copy-files` with each file's size and
   sha256.
3. **A restore entry with `copy_mode: "tar"`**: state `auto`, `cat` or `sftp`.
4. **To use Claude through MCP**: `pip install "dbabrain[mcp]"`, then follow `docs/16_mcp_app.md`.

## Known not to work

- **A SQL Server point-in-time restore from a server whose clock is not UTC lands early by its offset, and
  reports done.** SQL Server reads STOPAT and the backup headers in the source instance's clock, and the
  restore hands it the moment in UTC: from a server on +07 a restore to a moment stops seven hours before
  it, and a moment soon after a full can find no full before it. A restore to the newest backup (no
  moment) is not affected. Until the next version, state the moment in the source server's own clock
  with no offset. Found after this version was qualified, by restoring random moments of the last 14 days;
  fixed in the next version.
- **A restore to a moment at or after the newest log backup fails**: SQL Server leaves the database
  restoring (Msg 4326) and PostgreSQL 13+ stops the recovery. Restore to the newest backup instead (no
  moment). Fixed in the next version.

- **`dbabrain mcp serve` without the `mcp` extra names the wrong package** in its hint
  (`pip install "dba-brain[mcp]"`, a name that does not exist on PyPI). Install
  `pip install "dbabrain[mcp]"`; the hint is corrected in the next version.
- **Not proven on a host**: a restore through the new staging (`prepare-staging` -> `copy-files` ->
  `finish-staging`) and the new cleanup of a restore's staging - no restore drill ran during this
  version's qualification. They are held by tests, and the staging steps ran on a real host over
  SSH in a scratch folder.
- **The encrypting copy's time for a large FULL has not been measured** yet; what it saves is
  computed from the steps it removes.
- **A share-driven `restore-workflow` started by hand takes no run claim**, so a hand run and a
  scheduled run of the same entry could overlap. Do not start one by hand inside its entry's window.
- **No `UNEXPECTED_BACKUP` detection**; **the catalog's chain head is not copied off the node**;
  **restore staging is still pruned by the longest window** of an entry, not per file type.
- **There is no Telegram command for the repository pass** (`offload`): from a chat, `/spbot_backup`
  runs the backup, and the scheduled workflow runs the repository pass after it.
