## Summary

`repeat_interval` now means the same thing in every file that can carry it: seconds between the
**starts** of two runs. The shared configuration blocks are described as data that a program can
check, and four commands answer what a block means, whether a job is due and why, and whether a
node's configuration points at things that exist. SQL task output is quieter and complete: one table
per shape, one file with every row, and no progress message per batch.

**And one long job no longer stops the rest.** An app command can declare `run_mode: async`, so the
scheduler calls it again while a run is still going — which is safe because a run is now a *claim*
the store will not issue twice, per task-and-target, per backup job and per restore. A run whose
process is still alive keeps its place however long it takes, and one whose process is gone is
released at once instead of at its timeout.

## Fixed

- **A slow SQL task or backup no longer holds up every other one.** `APP-SQL_TASKS` and
  `APP-BACKUP-RESTORE` now declare `"run_mode": "async"`, so the daemon starts them when they are
  due instead of waiting for the run in flight to finish. A 22-minute task used to stop every other
  SQL task for 22 minutes. `"max_parallel"` caps how many run at once (4 by default); a command that
  says nothing keeps the old behaviour of one at a time.
- **The same unit of work can no longer be started twice.** One `running` row per task-and-target,
  per backup job and per restore is now enforced by the store itself, so two overlapping runs cannot
  both decide the work is free — the second is told it is taken and moves on. This is what makes
  running an app twice at once safe, and it also closes a way two nodes could double a production
  SQL task or start a second restore into a database mid-restore.
- **A run whose process is still alive is no longer timed out and restarted.** Every run records the
  process that owns it; a task that legitimately outruns its timeout keeps its place instead of
  having a second copy started on top of it. A run whose process is gone is released at once.
- **The restore verification asked the wrong SQL Server.** It connected on port 1433 whatever the
  entry said, so a restore into an instance on another port was checked against a different server:
  every database reported *not present on the instance*, while the one that had genuinely failed —
  left in `RESTORING` — went unseen. The port now comes from the entry's own `sql_instance`. A named
  instance has no port to give and is skipped with a reason rather than guessed at.
- **The verification is told which Oracle instance and which PostgreSQL cluster to look at.** Oracle
  ran `sqlplus / as sysdba`, which takes whatever `ORACLE_SID` the shell carries, and PostgreSQL ran
  `psql` with no port: right for one instance in one container, wrong the moment a host holds two.
  Both now carry what the restore itself was given.
- **A verification that reached nothing no longer reports a healthy state.** A PostgreSQL check that
  could not run — a missing client, a rejected login — was labelled `ACCEPTING`, the word for a
  cluster answering normally. It now reads `NO ANSWER`, and both engines report the error they were
  given instead of an empty line: *No such container*, *psql: not found*, or the exit code.
- **A restore checks that the files fit before it copies them.** The preflight adds up the backup
  files it is about to move, reads the free space where they are going, and refuses unless
  `free >= size x 1.5`. Per entry, `"space_check": {"factor": 2.0}` asks for more room — the value
  to use when the restored database will live on the same filesystem as the staged files — and
  `{"enabled": false}` turns the check off. A restore whose numbers cannot be read is refused as
  well, naming which number was missing. The refusal reports both sizes and changes nothing.
- **The daemon survives a restart of its store.** A failure the store reports as transient — a
  connection lost, a server starting up or shutting down, too many connections — is waited out with
  a backoff for up to ten minutes per outage. Before this, a database restart of a couple of seconds
  ended the scheduler: nothing restarted it, and the only sign was that no new rows appeared. Any
  other error, and an outage longer than that budget, still stop the daemon as before.
- **A command's answer is no longer lost to one byte of noise.** When a child process printed a
  character the machine's code page produced but UTF-8 cannot read, the reply was discarded and the
  caller was told the command *"exited 0 without a JSON response"* — while the command had in fact
  run and succeeded. Output is now read tolerantly; requests are still written strictly.
- **SQL tasks and reports measured `repeat_interval` from the wrong instant.** A SQL target with
  `repeat_interval: 300` whose task took 240 s ran every 540 s; a report pushed its own next cycle
  out by the time it took to send. Every scheduler now measures from the previous run's start.
- **A SQL task file export carries every row, not the first result set.** A task that runs its SQL
  once per batch returns one result set per batch; the file held only the first. Result sets with
  the same columns are merged into one table; `txt`, `csv` and `json` also keep sets of different
  shapes, and `xlsx` / `xml` note any set they leave out.
- **`plain` output shows one table per shape, not one per batch.**
- **A batched SQL task no longer sends a progress message per batch.** A Python-fed task sent one
  message per 2,000-row batch while `logging_on_run` was on. It now reports start and finish;
  `"progress_per_file": true` on the command restores per-batch messages.
- **`/spbot_list_my_commands` shows an uploaded file by name** (`<uploaded file: name.xlsx,
  19.5 KB>`) instead of printing the file's base64 content. Any other very long argument is
  shortened.
- **A SQL Server backup file name marks its stamp as UTC**: `APPDB_FULL_20260919_072256Z.bak`.
  Without the `Z` a UTC stamp read as local time on a node running on another zone. Restores accept
  both forms, so backups taken before the upgrade still restore.
- **The weekly full backup (PostgreSQL, Oracle) follows the node's configured timezone.** "Sunday"
  was read from the host's clock, so on a UTC host a +07 node's weekly full started seven hours
  late. db_ops now passes the weekday as `DB_OPS_WEEKDAY`; a job may still set it.
- **The documentation claimed `retry_interval` could lengthen a back-off.** It cannot; see *Known
  limitations*.

## Added

- **`describe-object`** — the fields of a shared configuration block (`time_window`, `notify`,
  `notify_rule`, `output`, `cmd_access`, `sql_access`, `cleanup_retention`): required or not,
  range, default, and what each interval is measured from.
- **`due-check`** — whether a job is due now and, if not, why not and when. It calls the function
  the schedulers call, so its answer cannot disagree with their behaviour.
- **`check-objects`** — every shared block in a node's configuration checked against the reference:
  a required field missing, a value out of range, a field nothing reads. Exits 1 on a finding.
- **`check-references`** — every pointer between configuration files (a backup's `server_id`, a
  notify level, a credential name) followed to its target. Exits 1 on a pointer that lands nowhere.
- **`data/shared_config_objects.json` and `data/config_references.json`** — the reference the two
  checks read. `init` writes both on a new root.
- **`run_mode` on an app command** — `sync` (the default, and what every command did before) or
  `async`, which lets the scheduler call the command again while a run is still going, up to
  `max_parallel`. `APP-SQL_TASKS` and `APP-BACKUP-RESTORE` ship `async`; everything else is
  unchanged. An `async` command must refuse its own duplicate work, which is what the run claim
  below does for it.
- **`space_check` on a restore entry** — `{"enabled": true, "factor": 2.0, "on_unknown": "refuse"}`.
  On at 1.5 when the entry says nothing. Set 2.0 when the restored database lands on the same
  filesystem as its staged backups: the copy is not the only thing that grows there.
- **`worker-run --on-host` and `--sudo`** — run a command on the worker host rather than in the
  container, with the same login.

## Changed

- **`output` is a shared configuration object**, parsed by one function and checked by
  `check-objects`. `sql-target-add` accepts the block itself as well as the flat
  `output` / `output_chat` form.
- **A SQL target may run slightly more often than before**, because its interval no longer includes
  the task's own duration. A run may also start up to `min(interval × 5%, 30 s)` early, so a sweep
  boundary does not cost a whole cycle.

- **The runtime store gained two columns and two unique indexes** so that a unit of work can be
  claimed rather than checked. See *Upgrading*: the first start does it, and reconciles any key that
  was already holding two `running` rows.

## Known limitations

- Nothing restarts the daemon if it does stop. A short store outage is now waited out, but an exit
  for any other reason leaves the estate with no scheduler and no alarm.
- `retry_interval` cannot postpone a retry: a failed run is due again when `repeat_interval` has
  elapsed, and a `retry_interval` larger than `repeat_interval` has no effect.
- A store carried between tool roots brings its in-flight `running` rows. A row whose process this
  host can see is now resolved at startup; one left by **another** host still waits out its timeout
  and an hour's grace, because this host cannot ask that one whether the process is alive.
- `--force` on a SQL task runs every target of that task, including targets with `active: false`.

## Upgrading

**The runtime store upgrades itself on the first start, and this version changes it.** Two columns
are added (`sql_runs.host_name`, `job_runs.claim_key`) and two unique indexes are created, so that a
unit of work can be claimed rather than merely checked. Before the indexes are built, any key left
holding **two** `running` rows — what every node killed mid-run leaves behind — is reconciled: the
newest stays, the older ones are closed as `timeout`, and the count is reported. Nothing is deleted.
Run `db init` if you prefer to do it deliberately rather than at the first daemon start.

Install the version. On an existing root the two reference files are not written by the upgrade;
`describe-object` and `due-check` fall back to the packaged copy and work unchanged. Run `init` (it
adds missing files without touching existing ones) or deploy the files, so that `check-references`
reads the node's own copy.
