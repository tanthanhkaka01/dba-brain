# v0.4.3 — moving an estate between machines, and two shipped commands that did not work

| | |
| --- | --- |
| Date | 2026-08-27 |
| Previous | `v0.4.2` |
| Python | 3.12, 3.13 |
| Artifacts | PyPI wheel + sdist, `ghcr.io/tanthanhkaka01/dbabrain:0.4.3` |

## What this release is for

Standing a second machine up on an estate you already run, without copying directories by hand —
and the defects that doing exactly that, on a machine that had never seen this project, brought to
the surface. Two shipped Telegram commands were broken, one module could not be imported on a fresh
install, and three files that ship inside the package had fallen behind the ones an operator edits.

**One upgrade action is required.** See *Changed / breaking*.

## Added since v0.4.2

- **`db-ops export-data` / `db-ops import-data`** — write a whole estate's configuration to one
  JSON file and apply it elsewhere. What travels is derived from `data/data_files.json`, so a
  config file added later crosses without editing any code. The secret store crosses as
  **ciphertext**; the passphrase is not in the file and there is no field for it, so the receiving
  machine supplies `DB_OPS_SECRET_KEY` itself. Every entry carries a sha256 and the whole bundle is
  verified before anything is written, so a truncated transfer leaves the target untouched rather
  than half-applied. `--plan` reports what would be written and changes nothing.

- **`data/data_files.json`** — the inventory of `data/`: every live file, the app that owns it, and
  how it moves between master and worker (`push`, `merge`, `field_merge`, `secret_merge`, `pull`,
  `local`). `deploy`, `worker-pull-data-config` and the merges read it before anything else, and a
  file that is not listed does not travel in either direction. `db-ops init` writes a copy to edit.

- **`json` as a SQL task `output.format`.** The renderer had always produced it — `run-sql --format
  json` worked — but a scheduled task could not ask for the same artifact. Now it can.

- **Container network reservations in `worker-status`.** Docker's default address pool overlaps the
  private ranges many estates route databases on, and a bridge that claims one takes that database
  off *that host only*: healthy everywhere else, and reported by the collector as an ordinary
  connect timeout. `worker-status` now reads the host's own networks and names the conflict as
  `HIJACK` (a monitored address is inside a container bridge), `OVERLAP` (a routed range is, with
  nothing monitored in it yet) or `UNCONFINED` (a network Docker chose rather than you).
  `data/network_reservations.example.json` explains what to declare; an estate on 10.x or
  192.168.x may legitimately leave `routed_ranges` empty.

- **Six more Telegram commands ship**: `/spbot_start_job`, `/spbot_disable_job`,
  `/spbot_restart_server`, `/spbot_shrink_log`, `/spbot_trace_session`, `/spbot_list_metrics`.
  All are operations that take their target as an argument; they existed and were simply never
  promoted into the shipped catalogue.

- **`MAINTENANCE_STATISTICS_AGE` grades its finding.** It emitted every stale statistics object at
  `WARNING` — 4,232 of them in one pass on one instance — which `collect_only` then kept out of
  reports, so nothing alerted and the finding was stated nowhere a person would read. The detail
  rows are `LOGGING` now, with a per-database row and one graded summary carrying the bands
  (`over_90d`, `stale_and_modified`), so the line a person reads says how bad it is.

- **`SQLSERVER_WAIT_STATS` reports an interval, not a total.** `sys.dm_os_wait_stats` is cumulative
  since the engine started, so a wait that dominated a restart six months ago out-ranks every real
  wait forever and no threshold can move. It is now measured between passes.

## Fixed since v0.4.2

- **`/spbot_kill_spid` was broken in every installation.** The shipped command sent
  `{"session_id": N}` while `common.cli kill-spid` takes `{"spid": N}`. Only the operator's own copy
  had ever been corrected.

- **A background command that finished was reported as failed on Windows.** A detached process is
  not a child of the workflow that polls it, and on Windows its PID is released the moment it
  exits — so the poller could not read an exit code and returned a hardcoded `1`. Every completed
  `/spbot_run_sql_task` arrived as `Exit code: 1` with no error text. The command now records its
  own exit code, on both platforms, and "not recorded" is reported as finished rather than failed.

- **`db_ops.control.deploy` could not be imported on a fresh install.** It read
  `data/data_files.json` at import time, which a new tool root does not have yet, so importing the
  module raised before anything ran.

- **The packaged `config_catalog.json` was two entries behind.** A fresh install's web console never
  showed network reservations, because the copy `db-ops init` writes had not been updated with the
  copy an operator edits.

- **`db-ops init` wrote a file no manifest listed** (`data/ops_status_request.json`), so no deploy,
  pull or config bundle would have carried it.

- **The daemon ignored `--key-base64` when `DB_OPS_SECRET_KEY` was already set.** Children were
  spawned with the inherited value, so the key on the command line did nothing and the failure was
  a wrong-passphrase error that did not match what had been passed. What you state now wins.

- **`APP-CONTROL` failed on Windows every cycle.** Its scheduled command wrapped inline JSON in
  POSIX single quotes, which `cmd.exe` passes through literally. It reads
  `data/ops_status_request.json` instead.

## Changed / breaking

- **`output` and `notify` are now required on every entry in `sql_targets.json`.** An absent
  `output` used to mean `plain`; a target without one is refused now, by name, with the block to
  add. **If you have targets registered before `output` existed, add one to each before
  upgrading** — `{"format": "plain", "telegram_chat": "sql", "chat_id": ""}` reproduces the old
  behaviour exactly. Anything registered through `db-ops common add-sql` already has both.

- **`/spbot_trace_session` takes a server and a database as its first two arguments.** It had them
  fixed in its own configuration and took only a SPID.

- **`/spbot_json_exp_ticket_detail` is removed.** It pinned one installation's `--sql-id 14` in its
  own arguments, so it ran whatever *your* task 14 happened to be. Use `/spbot_run_sql_task <id>`
  and set that task's `output.format` to `json`.

The bundle was measured rather than reasoned about: exported from a running estate, imported into a
wheel installed in a virtualenv on a machine that had never held the source, and the resulting
install then collected metrics from 21 targets with 0 errors and answered `check-credentials`
identically to the machine it came from.

## Known not to work

- `copy-schema` is covered by offline tests only. It has not been run against two live SQL Server
  instances.
- Backup/restore and the SRE app are documented but have not been executed end to end.
- Supported and tested on Python 3.12 and 3.13 only.
- `worker-status` detects a network conflict; nothing runs it on a schedule, so detection still
  depends on somebody asking.
