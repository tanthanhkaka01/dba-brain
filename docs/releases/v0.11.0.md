| | |
| --- | --- |
| Date | 2026-09-08 |

## What this release is for

The move procedure has a rule that exists for a good reason: a node that has never run gets a
store of its own before it writes where every other node's record lives, so that its first hours
are disposable. Until now "a store of its own" meant a local SQLite file, because that is the only
source `backfill-from-sqlite` could read.

A PostgreSQL **schema** is the same idea in a different container, and a better one when the
destination is already PostgreSQL: same server, same backups, same access, and the carry home is
a server-side operation rather than a file that has to exist on the machine running the command.

So the source is now either. `--source <path>` reads a SQLite file, as before;
`--source-schema <name>` reads another schema on the same PostgreSQL server and database.

## Added since v0.10.1

- **`db-ops db backfill-from-sqlite --source-schema <name>`.** Carries a stand-in's history out of
  another schema on this store's own server. `--source` and `--source-schema` are mutually
  exclusive and one is required.

  **One command, not two.** The hard part of this operation is not reading rows — it is that every
  primary key is an identity column, so ids cannot be carried, and every child link has to be
  rewritten through its parent's new mapping. `sla_results.sla_run_id` is a real foreign key and
  would be *rejected*; `metric_results.run_id` is not enforced and would be silently **wrong**,
  pointing at somebody else's collection run. Those rules exist once, in `TABLES`, and a second
  command with its own copy would drift — invisibly, in the direction nothing reports.

- **The source session is opened `READ ONLY`.** Not a convention: a bug that made this command
  write to the store it is reading would be writing to a store somebody is still deciding whether
  to trust. Verified — a `CREATE TABLE` on that session fails with
  `25006 cannot execute CREATE TABLE in a read-only transaction`.

## Changed / breaking

Nothing an existing tool root must do. `backfill-from-sqlite --source <path>` behaves exactly as
before; `--source` simply stopped being the only way to name a source.

The command keeps its name. `backfill-from-store` would have read better, but the name is in
`TEST_MOVE_ESTATE_TO_FRESH_DBABRAIN_INSTALL.md`, in two dated run records, and in operators'
notes — and a rename buys a nicer word at the cost of every one of those being wrong.

Three refusals, each measured rather than asserted, because each is a way of losing data quietly:

| Asked for | Answer |
| --- | --- |
| `--source-schema db_ops` into the `db_ops` store | `refused: source and destination are the same schema` — the watermark would be read from the table being written, so the window means nothing |

## Known not to work

- **It carries between two schemas of one database, not between two servers.** The source
  connection is built from the destination's own declaration with the schema swapped, so a source
  on a different host has no way to be named. That is a deliberate limit rather than an oversight:
  a cross-server carry needs a second full store declaration and a second set of credentials, and
  no one has needed it.
- **The carry is slow for large tables**, unchanged from v0.10.x and still worth knowing before
  somebody reads it as a hang: rows go over the network in batches of 1,000, the destination row
  count does not move until a table's transaction commits, and 759,461 rows measured about an hour.
  `pg_stat_activity` is the way to tell a working carry from a stuck one.
- Everything listed as open in `v0.10.1` is still open — in particular **upgrading over an existing
  0.9.x root is untested**, and it is the one that silently moves schedules if `timezone` is not set.
