# v0.5.0 — how much work an instance actually did, and an error that stopped being silent

| | |
| --- | --- |
| Date | 2026-09-03 |
| Previous | `v0.4.3` |
| Python | 3.12, 3.13 |
| Artifacts | PyPI wheel + sdist, `ghcr.io/tanthanhkaka01/dbabrain:0.5.0` |

## What this release is for

Neither report page could answer *"how much did this instance do in the last hour"*. Page life
expectancy and session count are gauges of the moment, and every DMV that counts work reports a
total since the engine started — read once, those answer "since it booted", which on the instance
this was found on was nine months. A bad afternoon last winter kept a tile red forever and a
problem starting this morning was diluted to invisibility by every good hour behind it.

Three collectors now record those totals raw, and the subtraction happens in the report. That is
the release: 90 metrics become 93, and both pages gain a workload section built from one shared
builder so they cannot describe the same hour differently.

It also carries a fix for an error class that was written to the store and to nothing else.

**No upgrade action is required.** See *Changed / breaking*.

## Added since v0.4.3

- **Three cumulative-counter collectors that grade nothing.**
  `PERFORMANCE_WORKLOAD_COUNTERS` (900 s) reads `sys.dm_os_performance_counters`,
  `sys.dm_resource_governor_resource_pools` and `sys.dm_io_virtual_file_stats`;
  `PERFORMANCE_WAIT_TOTALS` (900 s) reads `sys.dm_os_wait_stats` for a fixed watch list;
  `PERFORMANCE_QUERY_STATS_TOTALS` (1800 s) reads `sys.dm_exec_query_stats`. They record and never
  judge, which is the same shape as `PAGE_LIFE_EXPECTANCY` — no severity anywhere depends on the
  arithmetic, and nothing was added to the collect path.

- **`db_ops/reports/workload.py`, and the section both pages render from it.** On
  `server-metrics.html`, a folded section with three columns — latest interval, last hour, last 24
  hours — because "busy right now" and "busy last night" are different questions. On
  `database-inventory.html`, a chip strip per server, so *which of these is doing the work* can be
  answered without opening a server page. Each header states the span that was **measured**, not
  the one that was asked for: a 24-hour column built from 14 hours of samples says 14h.

- **`db_ops/lib/interval_rates.py` differences two stored samples.** Every message carries
  `counters_since`; a pair whose markers disagree is refused, because after a restart the totals
  begin at zero and a delta across one is the new absolute value — a burst of work that never
  happened. No pair, no column: the cumulative average is never offered as a substitute, since
  replacing it is the whole point.

- **`019_sqlserver_io_latency` reports bytes, not only counts.** Two files with the same read count
  and the same latency can differ by two orders of magnitude in throughput, and "is this volume
  saturated" is a question about MB/s.

## Fixed since v0.4.3

- **A SQL task run whose process died is no longer silent.** `mark_stale_running_sql_runs` closes
  out a run left `running` past its target's `timeout`, so the task can be scheduled again. It
  wrote the error row and logged it, and stopped there: `alert_on_error` was wired only into the
  exception handler inside `run_sql_target`, which a killed process never reaches. Found on a task
  whose cycle overran the daemon's own command timeout — the run sat in `error` for half an hour
  with no message anywhere, while the SQL it had started went on executing on the server and held
  that task's application lock, so every following cycle reported SKIPPED. The reaper now sends the
  target's `alert_on_error` message, and says in it that the SQL may still be running. Covered by
  `test_a_reaped_run_alerts_the_error_chat_like_any_other_failure` and, for the target that does not
  want alerts, `test_a_target_that_does_not_want_error_alerts_is_still_not_told`.

- **`as_epoch` existed twice, byte for byte.** `capacity_forecast._epoch` and
  `interval_rates._epoch` — one on the path that decides when a disk runs out, the other on the
  path that decides how much work an instance did. Both are now `db_ops.lib.coerce.as_epoch`.

- **The stdin JSON contract is tested against something a real stdin resembles.** The CLIs read
  `sys.stdin.buffer` so a request does not travel through the machine's code page; 57 contract
  tests handed them an `io.StringIO`, which has no `.buffer`, so the suite failed on both 3.12 and
  3.13. The stand-in is now a text stream over bytes, from one `stdin_holding` fixture.

- **A test that could only fail, and on Windows could only hang.** The encoding-mismatch test
  asked `subprocess.run` to write a payload cp1252 cannot represent. On Linux that raises in the
  caller; on Windows `communicate` writes stdin from `_writerthread`, which dies on the encode
  without closing the child's stdin, so the child blocks on `read()` for ever. The payload is now
  encoded by the test and handed over as bytes, and the case the estate actually hit — an ANSI
  writer emitting the em dash as `0x97`, which is valid cp1252 and not valid UTF-8, refused at the
  reader — is asserted for the first time.

## Changed / breaking

Nothing. The three new metrics are added to the catalogue and enabled by default; they record and
grade nothing, so no existing alert changes and no threshold moves. `db-ops init` on a new tool
root writes 93 metrics instead of 90. An existing `data/metric_definitions.json` is not rewritten
by an upgrade — add the three entries from `data/metric_definitions.example.json` to collect them.

`PERFORMANCE_QUERY_STATS_TOTALS` is the expensive one: aggregating the plan cache scans it, and on
one measured instance — 86,400 cached plans, 70,109 with statistics — it exceeded the 60-second
timeout three runs in a row while the same query returned in 0.4 s once warm. That is a finding
about that instance's plan cache, not about the metric. Disable it for such a target through
`metric_overrides` rather than raising the timeout.

## Known not to work

- `PERFORMANCE_QUERY_STATS_TOTALS` will time out on an instance with a large ad-hoc plan cache
  until `optimize for ad hoc workloads` is addressed there. That is the documented behaviour, not
  a defect, but it means the plan-cache table can be absent from the workload section on such a
  target while the other two columns are populated.
- The workload section needs **two** collections before it can show anything, so a freshly
  installed estate sees an empty section until the second pass of each collector — 15 minutes for
  two of them, 30 for the plan-cache one.
- Interval **grading** is still withdrawn. These collectors report; no severity is derived from a
  rate, and no threshold in this release grades an interval.
