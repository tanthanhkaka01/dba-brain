## What this release is for

**A backup and a restore say each step, one message each.** A backup says ten: the process, the backup
on the server started and done, the copy, the encryption, its plain files cleared, the repository's
upkeep, the process done - FULL, DIFF and LOG alike. A restore says eleven, each full and diff a start
and a done per database and each log its own message; a step that does not apply is still said, with
why, and a failed restore names the step it stopped at. Which of them reach a chat is the job's `notify`.

**Oracle restores from the repository, and every engine's point in time is the source's clock.** An
Oracle backup states its SID and records its RMAN chain after each run; a restore from the encrypted
repository picks that chain, newest or to a moment. A PostgreSQL base backup is catalogued file by
file. A point in time on Oracle or PostgreSQL is read in the source database's own clock, asked of it,
and refused when that clock cannot be known.

**A restore carries the instance around the databases.** A backup can seal the instance's metadata
(logins, jobs, configuration) into the repository; a restore reads it from the node, a server's folder
or the repository, and replays it before and after the databases.

**A server that is never used again can be retired.** `entry-remove`, `credential-remove`,
`instance-remove` and `report-server-remove` each remove one record, the deepest first, and are refused
while anything in `data/` still names it - every place listed. A plan unless told to apply.

## Upgrading

- Run `dbabrain upgrade-config`: it writes `server_metadata.enabled: false` into every restore entry
  that states none, `source: "node"` where one replays metadata, `repository_path: ""` on backup entries,
  and `record_chain` on Oracle backup entries (`true` where they offload).
- **State `oracle_sid` on every Oracle backup entry** - `upgrade-config` cannot know it, and an entry
  without one is refused.
- The backup catalog moves to schema 10 (a column on `backup_runs`) the first time the new version
  opens the store.

## Changed, added and fixed since v0.39.0

- Backup and restore messages step by step, as above; a backup's files are copied right after it in the
  same pass, the `offload` pass taking only what a backup left.
- The backup & restore page keeps every full - logs are a closed block per server, read from a file
  beside the page (11.8 MB to 1.7 MB on the estate it ran on); restores one line per outcome;
  drills and servers no longer configured folded as history; a SIMPLE-recovery database asked for no log.
- `secret-remove`, refused while a login or an entry still names the ref; an MCP node reads a secret
  stored after it started; `dbabrain mcp connect --wait-for-link` runs a node as a service.
- `run-sql-adhoc` and `run-cmd-adhoc` take `confirm_target`, the second answer where an operation is
  priced at two.
- Fixed: an Oracle restore from the repository refused an entry offloaded before its SID was stated; an
  offload claimed across nodes (a hand run and the worker's pass no longer copy one backup twice); an
  Oracle backup catalogues only the pieces it wrote; the Docker image carries the MCP SDK.

## Known not to work

- **Oracle's and PostgreSQL's point in time from a source not on UTC** has not been run on a host: the
  lab sources are on UTC and stopped at the moment asked; SQL Server's was run from a +07 source.
- **A PostgreSQL or Oracle restore under another name** (`RENAME` / `DUPLICATE TO`) is not built; an
  entry mapping a name for those engines is refused.
- **After a PostgreSQL or Oracle restore the target's logins are the source's** - the whole instance
  is the source's; the inventory's password for the target no longer logs in until it is set again.
- **An MCP node cannot run a restore**: `restore-by-id` is not an MCP tool (by decision); run it on the node.
