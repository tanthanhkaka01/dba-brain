## Summary

**One chat's backlog no longer silences the bot.** The Telegram send pass takes the oldest five
messages of each chat in turn, instead of the oldest fifty of the whole queue, and a rate limit
(HTTP 429) pauses only the chat it was given for. When one group was flooded by a failing lab, every
other chat - the bot's replies to its own commands included - used to wait behind it.

**One way to run anything on a host.** Every command, script, stream and file transfer on a host now
goes through `common.cli run-cmd`'s executor. A script travels as a private file run with stdin
closed, never as the shell's stdin, where a `docker compose exec` inside it swallowed the rest of
the script and the run still ended with exit 0.

**Three bugs that stopped the Telegram bot's SQL registration and schema listing are fixed**, found
by running every `common.cli` command through to a real answer: `add-sql` refused the `display_name`
the bot sends, refused its own default chat on a new install, and `list-schemas` failed on its own
message.

## Added

- **`send_per_chat` in `telegram_config.json`** (default 5) - how many of each chat's oldest
  messages one send pass takes.

## Changed

- **The Telegram send pass takes the oldest 5 messages of each chat**, every chat in turn, every
  second.
- **A Telegram rate limit pauses that chat, not the pass.** The row stays queued; the pause is kept
  in `runtime/telegram_chat_pauses.json`.
- **One executor runs everything on a host** (`remote_exec`). The backup scripts, `run-sqlcmd`, the
  restore staging copy and the file relay no longer carry SSH or PowerShell executors of their own;
  a PowerShell script runs as a `.ps1` with `-File`, which lifts the ~8 KB command-line limit.
- **`list-databases` on SQL Server says whether the login can open each database** (`has_access`).
- **Every schedule shown is the one the scheduler reads** - the status page, the web console, the
  bot's task listing, `ops-status` and the server report read a `time_window` through the
  scheduler's own parser.
- **`db_ops.config` is removed** - **breaking** for code that imports it; import
  `db_ops.lib.config`, the module it has aliased since 0.24.0.
- **The reference describes every key every `common.cli` command answers.**

The full list is in [`CHANGELOG.md`](../../CHANGELOG.md).

## Fixed

- **Registering SQL from the Telegram bot works again** - `add-sql` refused the `display_name` the
  bot sends.
- **`add-sql` and `sql-target-add` register a task on a new install** - they defaulted to a chat
  level only an existing `sql` group defines.
- **`list-schemas` answers** instead of `KeyError: 'database'` (since 0.22.0).
- **A script run on a host runs to its last line** when a command in it reads stdin.
- **`run-sqlcmd` over WinRM reports sqlcmd's own exit code**; a failed batch could read as success.
- **A Linux node cleans a Windows target's import share** - 0.24.0's known limitation.
- **A report file sent while its chat is rate-limited is no longer lost.**

## Known limitations

- **The SMB restore onto a Windows target, and the share cleanup, are proven offline only.**
- **An existing store keeps its archive tables without keys** until `db.cli archive-keys --apply`
  is run; on a large store it reads every archived row.
- **A point in time with an offset is converted to UTC**, the clock of every container target. For
  a server whose clock is not UTC, give the moment without an offset, in that server's own clock.
- **A PC node has no supervisor.** Run a daemon started by hand under a service manager.

## Upgrading

`SCHEMA_VERSION` is unchanged, so the store needs nothing.

```bash
pip install --upgrade dbabrain
python -m db_ops.common.cli upgrade-config '{}'                   # read the plan
python -m db_ops.common.cli upgrade-config '{"dry_run": false}'   # then apply it
```

**If your code imports `db_ops.config`**, change it to `db_ops.lib.config`.
