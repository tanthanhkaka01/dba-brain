## What this release is for

A 14-step `/spbot_create_db_docker` run, on a real estate, produced this exchange:

```
bot : SSH password — secret ref? … Type - to instead give the SSH password as text below.
op  : REMOTE_192_0_2_115_DEV
bot : SSH password — value? … Type - when you gave a ref/key.
op  : -
bot : SSH key file name? … Type - when using a password.
op  : -
```

Two of three answers were `-`, for a credential that had already been given. And a value mistyped
at step 4 could not be taken back — there was no way to step backwards through a workflow, so the
only remedies were finishing a wrong run or abandoning it.

Both are the same missing idea: a conversation had no *state machine*. This release adds one, plus
the step schema that lets a command describe branches instead of asking questions that do not
apply. Minor rather than patch: new behaviour, new config keys, and a new runtime table.

## Added since v0.12.0

- **Back, Skip and Cancel**, on every prompt of every conversation command, as buttons and as typed
  words — one vocabulary, resolved in one place (`db_ops/lib/workflow_steps.py`). Cancel ends the
  run and executes nothing; Back re-asks the previous **asked** step; Skip is offered only where a
  step genuinely allows it.
- **Branching steps.** `"ask_when": {"parameter": "remote_auth", "equals": "secret_ref"}` asks a
  step only when an earlier answer matches. Replaces the pattern of asking everything and typing
  `-` at whatever does not apply.
- **A step schema** that can grow: `input_type`, `options` (`{label, value}`), `allow_text_input`,
  `allow_skip`, `skip_value`. Buttons are a reply keyboard, so tapping and typing arrive the same
  way and nothing about the update intake changed.
- **`telegram_workflow_steps`** — one row per asked step: the prompt shown, the options offered,
  the answer (masked for `secret` steps), how it arrived, and `status='active'` on exactly one row
  per run. Store schema **3 → 4**; the table is created on first start, no migration to run.
- Answers given inline (`/spbot_run_sql_task 18 0 30`) are recorded in that trail too, as
  `answer_kind='inline'`, so a command answered in one message still has a full step history.
- **`db-ops db use-store sqlite|postgresql`** — points a node at its own store instead of the one
  its config bundle came from. `store_config.json` travels inside a bundle, so an import
  faithfully aims a machine that has never run at the shared production store, and every procedure
  that stands up a node ended with "now edit that file by hand". A hand-edit on the one path where
  forgetting it writes an unproven build's rows into the record every other node shares. The
  section not switched to is kept, so the way back is not a retyping exercise, and a section that
  cannot be read is refused here rather than at connect time.
- **`db-ops control pull-node-config --from <node>/data [--merge-secrets]`** — carries back what a
  **local** node created. `db_ops` is the origin for code and deliberate config, but the bot and
  console *create* config on whichever node runs the estate: a `/spbot_create_db_docker` run
  registers a lab container and stores its password there. `deploy --merge` and
  `worker-pull-data-config` do this for the worker container over SSH; a node that is a directory
  on a PC — which is what the estate is now — had no command, so it was done by hand. Same merge
  rules, because it is the same function underneath: union by key with the master winning a shared
  key, named leaves only for field-merged files, and a secret ref differing on both sides refuses
  and writes nothing. `store_config.json` and `telegram_config.json` are never carried back: a
  node's own store declaration and its `getUpdates` cursor are per-node state.

## Fixed since v0.12.0

- **A pasted SQL body was silently mangled.** A `consume_rest` tail was rebuilt by joining shlex
  tokens with single spaces, so `WHERE name = 'Tan Thanh'` reached the CLI as
  `WHERE name = Tan Thanh` (quotes eaten), and a multi-line paste was flattened until a `--`
  comment swallowed the rest of the statement — `SELECT id ⏎ -- only the active ones ⏎ FROM users`
  ran as `SELECT id`. Both were silent: the query stayed valid, it was simply not the one anybody
  wrote. The tail is now taken from the raw message, byte for byte
  (`telegram_command_text.split_with_verbatim_tail`). Found by measuring the paste path while
  documenting it.
- **Answers are validated at the step they are given.** Validation ran only when the command
  finally executed, so a value mistyped at step 2 of a 14-step workflow was reported after step 14.
  A refused answer is now recorded and the same question asked again.

## Changed / breaking

- Every conversation prompt gains a trailing line naming the words that work
  (`Type back / cancel at any point.`) and a keyboard. Any integration asserting the exact text of
  a prompt will see the extra line; the question itself is unchanged.
- `/spbot_create_db_docker` parameters were **renumbered** (`remote_auth` inserted at position 10).
  Inline invocations written before this release have their later arguments shifted by one and must
  be retyped — answering the prompts is unaffected. Everything reads parameters by name, so
  `command_argv` and `conditional_args` are unchanged.
- An **optional** step is now asked when it declares `allow_skip: true`. Optional steps that do not
  declare it keep the previous behaviour of never being prompted for.

## Known not to work

- **0.13.0 exists as a build and as two hours of soak, and will never be released.** It was
  superseded by the two commands above, which are code — and a code change restarts the soak clock,
  so the version number moved rather than a second artifact carrying a number that had already run.
  Nothing was tagged or published under 0.13.0; the wheel is on disk only. Skipped numbers stay
  skipped: they are not queued for a later release, and their content travels to the next version.
- **This release is 0.14.0 and nothing above it.** What ships is the artifact that completed the
  soak, not the tip of the tree when the soak ends. Work that lands while this one is running
  belongs to 0.15.0 and gets its own 24 hours — two versions are never published in one pass.

- **Inline invocation does not benefit from branching.** A step a branch skips still occupies its
  position on the command line, so a long command typed in one message needs a `-` placeholder for
  the branches it does not take. Answering the prompts is the reliable form; documented in
  `docs/07_telegram_app.md`.
- **Buttons cannot be distinguished from typing.** A reply keyboard sends an ordinary message, so
  `answer_kind` records whether the answer matched an offered option, not which input produced it.
  Inline keyboards would carry that certainty and need `callback_query` intake, which this release
  does not add.
- **A multi-word answer in the last position is still fragile when replayed.** A command written
  back by `/spbot_list_my_commands` leaves its final argument unquoted — correct for a
  `consume_rest` body, wrong for an ordinary answer holding a space. Measured and documented; not
  changed, because the unquoted tail is a deliberate, tested decision.
