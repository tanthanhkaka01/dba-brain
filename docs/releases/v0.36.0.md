## What this release is for

**A figure on a report page is either the newest reading, or it says it is not.** Every number on
the five report pages - fleet inventory, server metrics, SLA, backup & restore, index usage - was
audited for a value taken from the canonical inventory's static blocks, a fresh value mixed with an
old one, a "latest row" that could pick an old row, and a page re-grading what a collector had
already graded. Each case found is fixed: a page shows the collector's verdict (before any severity
remap), a server nothing current was read from is shown as such instead of counted critical, and
what is taken from the documented inventory says *static* / *documented*.

**The SLA states how far back a restore reaches**, and the share-driven SQL Server restore checks
its backup chain before it restores. The AI assistant can be asked from the command line, so a new
install can use it before Telegram is set up.

## Fixed since v0.35.0

- **The fleet inventory page graded a volume from an old total.** A free figure with no size (SQL
  Server 2008) was divided by the size in the canonical inventory file, which may be months old; it
  now takes the OS metric's size, and a total smaller than the free space read now is not used. The
  page no longer grades drives on its own 10 / 15 %: a drive's status is the collector's, before any
  `severity_map`, and the server's status and the disk cards follow it. A drive known only from that
  file prints *not collected*. (Listed under *Known not to work* in v0.35.0.)
- **One hourly CPU reading of two no longer makes a host CRITICAL on the pages.** A severity held
  over the last hour needs two samples whenever the window has more than one.
- **Both database tables colour a backup age by the backup policy and a log's fullness by
  `LOG_FILE_SPACE`**, not by hours and percentages of their own; a type the policy does not require
  reads `n/r`.
- **A server nothing current was read from** is graded *idle* on the fleet page, kept out of every
  card, and named in one *show last known values* card.
- **SLA: a backup's age is read as of the window's end**, not frozen at collection; a current-state
  check with nothing measured reads *no data*, not compliant; freshness is the newest measurement's
  age; an age from a finish date is on the display clock.
- **Backup & restore: *last restored* is a restore that succeeded**, not any run that used a file;
  the coverage table prints each database's newest full and log; the drill table reads back far
  enough for a monthly drill; a tiered entry with no run is listed OVERDUE. The SLA's restore-drill
  policy reads the catalog's drills, and tells two servers' databases of one name apart.
- **The fleet page stops grading on rules of its own**: an Oracle database open READ WRITE is not
  badged red; page life expectancy, failed logins and password age follow the collectors' verdicts.
- **A volume read by two collectors shows the newer reading** when one has stopped, on both pages;
  the capacity forecast lists each volume once, and only those the newest collection reports.
- **An empty backup reading stays empty** on the fleet page instead of falling back to the static
  file's old backups.
- **The Markdown inventory summaries count a low disk by the collector's verdict.**
- **The AI assistant can read the guide on a pip install** (the readable root pointed at nothing in
  site-packages), and a search of a missing path says the path does not exist.

## Added since v0.35.0

- **`dbabrain db create-app-login`** - a login role and a schema of its own for another tool beside
  the store, idempotent, with `--dry-run`; it grants nothing on the store's schema.
- **`recovery_reach` on every `backup_rpo` SLA result** - the server's backup entries and their
  point-in-time reach from the backup catalog, printed after the reason and in the matrix cell's
  title. It does not change the verdict.
- **The share-driven SQL Server restore checks its chain first**: every chain file's
  `RESTORE HEADERONLY`, read through the target's `sqlcmd` in one batch, and a DIFF of another FULL
  or a missing log refused by name before any restore statement. A header it cannot read is logged
  as not judged and the restore runs as before.
- **`dbabrain telegram ai-ask "<question>"`** - the AI assistant at the command line, with the same
  limits and every call kept; `init`'s next steps name it.
- **`RECOVERY_SET_SIMPLE`** in `LOG_RECENT_CRITICAL`: a SQL Server database switched to SIMPLE
  recovery (error log message 5084) is a WARNING.

## Changed / breaking

- **Expect `RECOVERY_SET_SIMPLE` WARNINGs** on the first collection wherever a database was switched
  to SIMPLE recovery within the error log's window.
- **SQL Server error 18056 no longer pages.** It is counted as `ERROR_18056_SESSION_RESET`, a
  WARNING within the day; any other severity 19 - 25 error still pages.
- No configuration file changes shape: `upgrade-config` plans nothing for a v0.35.0 tool root. The
  runtime store's `SCHEMA_VERSION` is unchanged (5).

## Known not to work

- **No `UNEXPECTED_BACKUP` detection.** On a real estate most of the newest backups are written by
  other tools (agent jobs, VSS), so an alert on "a destination that is not dbabrain's" would fire on
  most databases every day; it needs a design that knows the other writers first.
- **The SRE app's two SSH shell-outs still pass `StrictHostKeyChecking=no`**; dbabrain's own SSH
  pins host keys when `DBABRAIN_SSH_KNOWN_HOSTS` names a file.
- **Restore staging is still pruned by the longest window** of an entry, not per file type.
- **The catalog's chain head is not copied off the node.**
- **Not yet run against a real server**: `catalog-backfill` for PostgreSQL and Oracle, the drill's
  consistency check, and the share-driven restore's new chain check (its batch was run read-only
  against real backup files; no share drill has run with it yet).
- **The reports landing page is narrower than the other pages** and indents its second card.
