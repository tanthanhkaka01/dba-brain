## Summary

**0.22.0 was built, soaked for part of a day and abandoned on 2026-09-24** - there is no 0.22.0 on
PyPI. Everything it carried ships here, with what was fixed after it.

**Messages that say what actually happened.** A SQL task no longer refuses a database before it has
connected - it connects, and when a database does not open it asks the server and says which part
failed, with the name you probably meant; a SQL Server *warning* no longer fails a run; a restore
whose integrity check failed says so instead of "restore failed", and the check can be switched off
per entry; `create-db-docker` tells a missing image tag from a registry that did not answer; the
Oracle Data Guard lab survives a restart, and its redo shipper actually ships.

**Point-in-time restore works on SQL Server, PostgreSQL and Oracle.** `/spbot_restore <id>
"<moment>"` takes the moment in any offset. The labs drilled each engine with a row written
either side of the moment: every restore kept the row before it and not the one after. Until
this release none of the three reached its moment.

**One name per concept, everywhere the tool reads or writes JSON.** A record's on/off switch was
`active` on most records and `enabled` on the inventory; a sort position was `ord`, `app_ord` and
`menu_order`; a secret reference was `password_ref` in one file and `password_env` in another -
where `password_env` elsewhere meant the name of an environment variable. This release picks one
name for each concept across the configuration, the requests `common.cli` takes and the answers it
gives. Readers take both spellings, writers write the new one, and **one command moves your files**:

```bash
python -m db_ops.common.cli upgrade-config '{}'                   # the plan
python -m db_ops.common.cli upgrade-config '{"dry_run": false}'   # apply; each file is copied first
```

**Everything is described.** `shared_config_objects.json` now describes every config file in
`data/`, every request `common.cli` takes, every answer it gives and its own shape - 159 entries - and
`describe-object` answers for any of them. The test suite fails when a config key, a request key or
an answer key exists that the reference does not describe.

**Scheduled SQL on SQL Server, PostgreSQL and Oracle.** A SQL task runs on PostgreSQL now, a
statement at a time. An Oracle task can run a PL/SQL block, which lost the `;` after its `END` and
failed every run. And a PostgreSQL statement is no longer cut at the connect timeout, which made
every task longer than 30 seconds fail as *could not reach* the server. The release drill ran a
10-, a 5- and a 1-minute task on each engine, overlapping, beside hourly backups and restores of
the same databases.

**A restore says what it is doing.** A PostgreSQL, Oracle or container SQL Server restore sends one
message per step - copy, metadata, restore, verify, delete - each naming the restore and its mode,
and its last one says what was restored and whether it opened. The copy and the cleanup are
`common.cli` commands of their own.

**Scheduled work never runs twice.** An overlapping run of the backup/restore or SQL task app used
to run again a job the other run had already finished.

**The inventory is a report, not an app.** It was its own scheduled app command beside the reports
it belongs with; it is now a report in `reports_config.json`, built by the reports app like the
metrics and backup reports.

## Added

- **A SQL task can run on PostgreSQL**, beside SQL Server and Oracle. Its script runs a
  statement at a time, so each SELECT is its own result set and each INSERT's rows are counted.
  It takes no parameters yet.
- **[`examples/lab-sql-tasks.md`](../../examples/lab-sql-tasks.md)**: scheduled SQL on SQL Server,
  PostgreSQL and Oracle labs - three overlapping tasks per engine, how each engine splits a script,
  and what `max_parallel` does to long tasks.
- **[`examples/lab-create-backup-restore.md`](../../examples/lab-create-backup-restore.md)**:
  build a lab database with `dbabrain sre`, back it up, restore it onto a second machine, then
  restore it to a moment - for SQL Server, PostgreSQL and Oracle, as drilled for this release.
- **`checkdb` on a restore entry** (default `true`): `false` skips the `DBCC CHECKDB` after each
  restored database, and the run says it did.

- **The shared-object reference describes itself** - four entries (`reference_entry`,
  `reference_field`, `reference_site`, `reference_constraint`), so `check-objects` holds it to the
  same rules as every other file. Their first run found two `legacy_fields` written as a list and
  twelve empty `rule`s. 153 entries.

- **`upgrade-config`** - run after `pip install --upgrade`. It refreshes the shipped reference files
  in `data/`, renames old field names, moves a restore's machine ids onto the entry, turns a
  Telegram record's `status: "active"` into `active: true`, and moves the inventory app command into
  `reports_config.json`. A plan unless `dry_run: false`; every changed file is copied to
  `runtime/config_upgrade/<UTC stamp>/` first; a second run changes nothing; a record whose two
  spellings disagree is reported and its file left untouched. `init` and `import-data` say when there
  is something to move.
- **`AGENTS.md`**, the operating guide for an AI agent, written into the tool root by `init`: the
  rules, the secret key, adding a database, every config file and the command that writes it, the
  checks, schedules, the daemon, the status questions, and the commands that change a database or a
  host. `init` refreshes an untouched guide after an upgrade and keeps one a person edited;
  `dbabrain guide --write` writes it before a root exists.
- **`/spbot_self_status` lists what the node schedules** - one line per app command: on or off,
  which node role runs it, `run_mode`, interval, hours, weekdays and when it last ran.
  `python -m db_ops.db.cli self-status` gives the same with the last-run column;
  `common.cli self-status` answers without a store.
- **The reference describes all of it** - 60 config entries, 45 request shapes (kind `input`), 44
  answer shapes (kind `output`, with `cli_response` the envelope). `check-objects` reports a key on a
  record that the reference does not describe instead of ignoring it.

## Changed

- **A restore's copy and staging cleanup are `common.cli` commands** (`backup-chain`,
  `copy-backup-dir`, `prune-staged-backups`). A restore is now a sequence of short commands the
  app calls one by one, each announced: copy, metadata, restore, verify, metadata, delete.
- **`create-db-docker` and `move-db-docker` run in `common.cli`**, like backup and restore: `sre`
  (and `/spbot_create_db_docker`, unchanged) resolves the passwords and the SSH logins, `common`
  builds or moves reading no configuration, `sre` registers the result. Progress streams as it
  happens. The spec moved to `db_ops.lib.docker_db_spec`, the work to `db_ops.common.docker_db`.
- **The SMB SQL Server restore runs its statements through `common.cli run-sqlcmd`** - the same
  command as before on Windows and Linux targets; the app still decides what runs and what an
  answer means.
- **`backup-database` refuses `server_metadata`**, which looked its instance up in the inventory;
  the app exports metadata through `sqlserver-export-instance` after the backup, as it always had.
- **Tests hold `common.cli` to its rule**: no config read behind backup, restore or the lab-docker
  commands, no import but `lib`, no CLI launched, and the remaining config readers may only shrink.

- **`AGENTS.md` always matches the installed version.** Every `init` (and `dbabrain guide --write`)
  replaces it; a copy somebody edited is saved to `runtime/agents_guide/` first and `init` says
  where. The guide itself covers this version's field names, SQL task warnings and `autocommit`, the
  `master` default, the check after a restore, and what each common symptom means.

- **Configuration names.** An instance says `active`, `environment`, `sort_order`,
  `database_name`, `major_version`; app and Telegram commands `sort_order`; a SQL task
  `display_name` (was `sql_name`); a restore entry `database_mappings` (was `databases`) and names
  its machines `server_id` / `target_server_id` on the entry (was `source.id` / `target.id`); a
  restore's `source` / `target` blocks `password_ref` / `sql_password_ref`; a docker connection
  `db_type`, `database_name`, `password_ref` (was `engine`, `database`, `password_env`); the store
  and the backup and restore-drill overrides `database_name`; an SLA policy's title
  `display_name` (was `name`, with `slo_target`, `aggregation_method` and `operator` as the other
  old spellings); a credential `note` (was `notes`); a console block `sort_order` (was `ord`); a
  Telegram chat or person `active: true` (was `status: "active"`). All old spellings are still read.
- **Request names**, old ones still accepted: `database_name`, `database_names`, `sql_text`,
  `destination`, `job_name`, `file_path` / `file_base64`, `refs`; `create-db-docker --password-ref`
  and `add-sql --display-name`.
- **Answer names - renamed outright.** A byte count is `size_bytes` (was `size` / `bytes`), a
  duration `duration_ms` (was `elapsed_seconds` / `duration_seconds`), one database
  `database_name`, a restore step's engine `db_type`, run-sql's profile object `target_profile`
  (was `engine`), app-command-set's list of changes `changes` (was `changed`), delete-file(s)
  `freed_bytes`, pack-backup `file_count`, copy-schema's plan and lift-example `destination`, a
  restore-database plan `database_names`. **A script that parses these answers must follow.**
- **The inventory** is the report `rp_inventory_health` in `reports_config.json` - hourly by default,
  as the app command was, and `upgrade-config` carries an estate's own interval into the report;
  `APP-REPORTS-INVENTORY-WORKFLOW` is gone and `APP-REPORTS-CREATE`'s timeout covers the inventory
  build. `reports.cli inventory-workflow` still runs it by hand.
- **`sql-command-add` and `sql-target-add` refuse a key they do not know** instead of dropping it,
  and check the record against the reference before writing it.
- **`check-references` fails a restore that names a machine the inventory does not have.**

## Fixed

- **A PostgreSQL, Oracle or container SQL Server restore reports every step**, not just its
  copy. Its END says what was restored, whether it opened, and any warning.
- **Those restores replay instance metadata again**, and clean their staging only after a
  verify that passed.
- **The shipping checks look where they should.** `check-identifiers` reads the Telegram files
  again and counts a person's or chat's id as a hit; `check-secret-literals` also searches for the
  store passphrase; both read `tests/`, `CHANGELOG.md` and `.github/` by default; Oracle Free's SID
  is not an estate name.
- **A PostgreSQL statement can run longer than 30 seconds.** The connect timeout used to bound
  every read on the connection, so a long task failed as *could not reach* the server.
- **An Oracle SQL task can run a PL/SQL block.** `BEGIN ... END;` used to fail with PLS-00103,
  because the `;` after `END` was stripped with every statement's.
- **A scheduled backup, restore or SQL task no longer runs twice** when an overlapping async run
  has already done it.
- **A point-in-time restore's messages say so**: `restore_mode=POINT_IN_TIME` and the moment on
  every one, not `LATEST`.
- **A PostgreSQL restore keeps its incremental**, which a same-second staging copy dropped. A
  point in time chooses its full in UTC; it chose by the host's clock.
- **A point-in-time restore to a moment before the newest full** copies the whole backup
  directory. Before, it staged a chain that could not reach the moment.
- **A refused unknown id is named in its refusal.**
- **`restore-add` checks a PostgreSQL, Oracle or container restore with the loader that
  runs it.** Until now nothing checked one, and an entry it wrote could stop `list-restores` and
  every `restore-workflow` on the node.
- **A point-in-time restore reaches its moment on every engine.** It reached it on none:
  - SQL Server refused a STOPAT with an offset (Msg 3217), and its log chain left out the log
    holding the moment.
  - PostgreSQL paused at the target, so the restore waited 30 minutes and failed.
  - Oracle refused the offset and needed its `SET UNTIL TIME` inside a `RUN` block.
  - The backup listings dropped every stamp's offset.

  The moment is taken in any offset, and a drill on each engine restored the row written before
  it and not the one after.
- **An Oracle duplicate reads only its own staging folder.** RMAN read `BACKUP LOCATION` as a
  prefix and mixed in a sibling lab's pieces, which carry the same image DBID. It also never
  resumes onto an earlier duplicate's files.
- **The staging copy mirrors the source**: a piece of the source's previous life no longer stays
  beside the new ones.
- **`/spbot_create_db_docker` offers `oracle-xe`**, backup-ready as built. **The MySQL ha-lab
  builds again** on `bitnamilegacy/mysql` (`bitnami/mysql` has left Docker Hub), and the image check
  covers every image a template pulls.
- **A failed `create-db-docker` stores no password**, and an unfilled `{worker_host}` is never
  recorded as a lab's host.
- **`--install-docker --dry-run` installed Docker**; a dry run connects to nothing now.
- **`move-db-docker` reported 0 bytes transferred** for every move, and **could not move a lab
  named in capitals** (compose lower-cases the project name).
- **Non-ASCII text in a `common.cli` answer** arrived mangled on a Windows node; it is UTF-8 now.
- **A SQL task refused a database it could have run on, in the wrong words.** Before connecting it
  compared `database_name` case-sensitively with the instance record's `database_names` - a list no
  code writes - so `APPDB_PROD` failed against `APPDB_Prod`, with *Target database not found in
  database-inventory.json* (a file never read) and a `service_name` SQL Server does not have. It now
  looks up the instance only, connects, and when the database does not open asks the server:
  *does not exist … did you mean*, *use the server's spelling*, *this login cannot open it*, a refused
  login, an unreachable instance. An instance the server lacks is named with the ones it has, and
  `sql-target-add` refuses it. SQL Server targets are named `server/instance.database`, `master` when
  none is given.
- **A restore whose `DBCC CHECKDB` failed was reported as a failed restore.** The database is
  `CHECK_FAILED` and the message says *restored and recovered, but the integrity check failed*, with
  SQL Server's message numbers. It still fails the run and holds back retention cleanup.
- **`install_docker = yes` prepared one of the two folders a lab writes.** `/spbot_create_db_docker`
  failed with *Cannot create /opt/db_ops/backup … Permission denied* for a user with full sudo rights.
  Both folders are prepared with sudo now - the backup mount at its top only, so the engines keep the
  backups they wrote beneath it - and a failed preparation says so.
- **`create-db-docker` called any registry failure "Image not found"**, refusing `postgres:18` and
  recommending it in the next line when the registry had failed for a moment. It says *not found*
  only when the registry does.
- **The Oracle Data Guard lab did not survive a restart, and its shipper never shipped.** After one
  host reboot the standby crash-looped (the image's own start opens it as a primary); it now starts
  mounted and is reported healthy as a mounted standby. The shipper read the standby's names once, at
  start-up, and skipped every cycle after; it reads them every cycle - verified: the standby advances
  on its own, after a standby restart and after a whole-stack restart.
- `run-sql`'s message names the database again (lost when its answer key was renamed).

- **A SQL Server warning failed the run.** pyodbc raises a warning (SQLSTATE class `01`, e.g. 8153
  *Null value is eliminated by an aggregate*) out of `nextset()`, and every result loop treated it as
  an error - a SQL task that had finished and committed was recorded `error`. A warning now ends the
  reading without failing: the task is `done` at level `warning` (*SQL task done with a warning*),
  `run-sql` answers it in `warnings`. Nothing after the warning can be read - the driver runs the
  rest of the batch on the server and hides even a later error - so a run inside a wrapping
  transaction is rolled back with that reason instead of committed.
- **`check-objects` re-read the reference for every record**; it loads it once per walk (51 s ->
  0.13 s once the reference described itself).

- **A SQL Server restore with a database list was never verified.** The check after the restore read
  the wrong field names off each mapping, found nothing to ask about, and reported the verification
  as not configured. It now asks the target about every mapped database under its target name -
  restores that list databases will start reporting their real state.
- **A PostgreSQL or MySQL instance registered with `db_name` connected to its label**: no connection
  read that field. `instance-add` now writes `database_name`.
- **A Telegram group with no `status` could run commands but was never sent an alert** - the
  permission check read it as active and the level routing as inactive. Absent now means active for
  both.
- **The status report showed a stopped web host as enabled** - it read a field app commands do not
  have.
- **`check-objects` reported every instance `instance-add` registered as broken** - the reference
  required a `metrics` block that `instance-add` deliberately does not write.
- **`check-secret` guessed a docker connection's engine from the ref's name** - it read a field the
  file did not carry.
- The shipped `sql_commands` example carried a PostgreSQL task no runner executes.

**Restores between machines**, found by a drill between two lab hosts (encrypted FULL/DIFF/LOG of a
SQL Server lab restored onto another, 2026-09-24) and fixed on it - it now restores exactly the rows
the source holds onto a fresh target:

- **Every script-driven restore failed after its first step** since 0.22.0 - *restore-full failed:
  'engine'* - leaving the database RESTORING. SQL Server container, PostgreSQL and Oracle drills alike.
- **A new cross-machine restore failed its first run** - the target folder was read before it was made.
- **SQL Server could not read the pieces the copy wrote** (Msg 3201); they are opened to the engine.
- **An encrypted backup could not be restored onto a machine without its certificate** (Msg 33111) -
  the certificate is imported before the backups are listed.
- **An unreadable backup read "no databases found"**; it is named now.
- **The plan connected to port 1433 whatever the target** - it uses the target's own port.
- **A failed restore did not say why**; the log line and the alert carry the reason.
- **The SQL Server backup job** takes over a backup folder another user made, and leaves its pieces
  readable to the copy, as the Oracle and PostgreSQL jobs do.
- **A backup of a stopped container blamed missing tools**; every backup script says it is not running.
- **`create-db-docker --backup-mount`** is mounted by PostgreSQL, Oracle and MySQL single labs and
  by the HA labs, instead of dropped.
- **A PostgreSQL restore never replayed WAL** - the recovery configuration arrived after the server
  had started - so every PostgreSQL drill stopped at its last base or incremental backup and
  reported verified. It is written before the first start; the step waits for recovery to end.
- **A PostgreSQL restore into a container no longer needs the target running**: a target a failed
  restore left crash-looping used to fail every later one. It is stopped, rebuilt from throwaway
  containers of its own image with the backups mounted read-only, and started again either way.
- **PostgreSQL and Oracle restores onto a machine that logs in by password** failed at planning, and
  every restore used `sudo docker` outright; the password travels, `sudo` is a fallback, the data
  swap runs in a throwaway container.
- **The PostgreSQL and Oracle backup jobs** take over a folder another user made, as the SQL Server
  one does.
- **An Oracle restore into a container without a backup mount** could not find its backups
  (RMAN-05579); they are staged into the container first.
- **A lab built with `--backup-mount` is backup-ready as built, HA labs included**: backups under
  `<mount>/<lab name>`, PostgreSQL archiving WAL there, Oracle in ARCHIVELOG, the HA primaries
  mounting the folder - no DBA step before the first backup.
- **A newest backup SQL Server cannot read** no longer disappears silently: the restore finishes
  *done with a warning* naming it.
- **A SQL task's credential hidden by a mismatching `service_name`** (on SQL Server a label) is found,
  and a credential in an unmatched group is named in the failure.
- **A log archived as yesterday whatever its day**; **CRLF in shipped shell scripts and templates.**
- **`/spbot_restore` runs PostgreSQL, Oracle and container SQL Server drills** - it refused them.
- **A restore no longer replays another cluster's WAL** after the source was rebuilt (a same-named,
  same-size file was taken for the same file), and a target that cannot recover fails the step at once.
- **`/spbot_create_db_docker` can make the lab backup-ready** (`backup_ready`).
- **`run-sql`'s `autocommit` on PostgreSQL** ran inside a transaction (and so did every metrics
  connection); it no longer does.

## Known limitations

- **A PostgreSQL SQL task takes no parameters.** They are written as T-SQL `DECLARE` lines, which
  PostgreSQL cannot read; `sql-command-add` refuses one. Write the values into the script.
- **An Oracle SQL task with parameters fails on a direct connection.** The same `DECLARE` lines reach
  Oracle. Parameters work on an Oracle 8i bridge target (as SQL*Plus defines), and a command may be
  registered for both, so registration does not refuse it yet. Write the values into the script.
- **An Oracle batch is one statement or one PL/SQL block.** Separate them with `GO` lines.
- **`APP-SQL_TASKS` ships with `max_parallel` 4**, and each of its runs works through its due tasks
  one at a time: with more long tasks than that, the rest wait. Raise it with `app-command-set`
  (docs/03 has the measurement), and keep the app's `timeout` above the longest chain a run can
  take - a run killed at its timeout leaves its statement running on the server.

- **A point in time with an offset is converted to UTC**, the clock of every container target.
  For a server whose clock is not UTC (a SQL Server on a Windows host in local time), give the
  moment without an offset, in that server's own clock.

- **A backup mount added to a lab that already exists** changes its compose file only: PostgreSQL's
  archiving and Oracle's ARCHIVELOG are made when the lab is first created - rebuild with `--force`.

- **`checkdb` defaults to `true`**, as every restore ran before. A target that cannot create the
  check's snapshot (Msg 1823 / 7928, seen on a SQL Server container) fails the check every night
  until its entry says `"checkdb": false`.
- **`database_names` on an instance is display data.** Nothing writes it and, from this version,
  nothing refuses a database for being absent from it; whether a database exists is asked of the
  server.

- **A node on 0.21.0 must not receive configuration from a 0.23.0 node.** It does not know `active`
  and reads an instance switched off as switched on. Upgrade every node before moving files, and
  run `upgrade-config` on each.
- **A PC node has no supervisor.** The container restarts its daemon; a daemon started by hand on a
  PC does not come back after a crash or a reboot. Run it under a service manager (`AGENTS.md` §7).
- `sre_config.json` still accepts a literal password (`<name>_password`) for throwaway lab machines;
  `<name>_password_ref` is the form to use for anything kept.

## Upgrading

`SCHEMA_VERSION` is unchanged from 0.21.0, so the store needs nothing.

```bash
pip install --upgrade dbabrain
python -m db_ops.common.cli upgrade-config '{}'                   # read the plan
python -m db_ops.common.cli upgrade-config '{"dry_run": false}'   # then apply it
```

Do this **before starting the daemon on the upgraded node** - a node that keeps the old
`APP-REPORTS-INVENTORY-WORKFLOW` app command beside the new inventory report builds the inventory
twice. Nothing breaks if you skip it otherwise: every reader takes the old spellings.

**If a script of yours parses `common.cli` answers**, check it against the renamed answer keys above.
