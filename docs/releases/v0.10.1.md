# v0.10.1 — the lines 0.10.0 forgot to put a clock on

| | |
| --- | --- |
| Date | 2026-09-07 |
| Previous | `v0.10.0` |
| Python | 3.12, 3.13 |
| Artifacts | PyPI wheel + sdist, `ghcr.io/tanthanhkaka01/dbabrain:0.10.1` |

## What this release is for

`v0.10.0` set out to make every rendered time name its clock. It missed five, and one of them was
the first line of every metrics report that reaches Telegram:

```
[Metrics Warning Report]
Run: 2026-09-07 14:44:14          <- 0.10.0: a wall clock on no named clock at all
Run: 2026-09-07 14:44:14 +07      <- 0.10.1
```

That is precisely the defect 0.10.0 was written to remove, shipped inside the release that removes
it. It was found by reading the messages the upgraded node actually sent, which is the only place
it was ever going to be found — every test passed, because no test asserted on that line.

Patch, not minor: nothing an existing tool root must do, and no schedule changes.

## Fixed since v0.10.0

- **`Run:` in every metrics report carried no offset.** `_run_time_text` borrowed
  `_local_time_text`, which is the *column* renderer — that one is allowed to omit the offset,
  because the table header states it once for a hundred rows (`Time (+07)`). A line that stands on
  its own has no header to lean on. The two now have separate jobs and each says which it is.

- **The maintenance-window refusal named an hour and not a clock.** The message that explains why a
  host restart was blocked read `now 2026-09-07 14:44 is outside the approved window`. When a tool
  refuses an operation on the grounds of what time it is, the one thing it must not be vague about
  is what time it thinks it is — otherwise the reader cannot tell whether it disagrees with them
  about the clock or about the rule. Now: `now 2026-09-07 14:47:55 +07 is outside …`.

- **The restore-drill failure reason rendered UTC** while everything beside it rendered the
  operator's clock. It was correct — it printed `UTC` — but correct-and-different still costs the
  reader a conversion in the middle of a CRITICAL line.

- **`sre move-db-docker` used the host clock twice**: the moved image's tag (`moved-<stamp>`) and
  the move manifest's `created_at`. Neither is scheduled and neither was silently wrong — the
  manifest carried `%z` — but both disagreed with every other timestamp the tool writes. The tag
  now uses the configured clock; the manifest records UTC, like every other record.

## Added since v0.10.0

- **A guard for the whole class**, `test_no_producer_renders_a_bare_wall_clock`. Two of the four
  above were missed by hand twice, so the pattern is now checked in source: a
  `strftime("%Y-%m-%d %H:%M…")` with no offset beside it fails the suite. Exactly two files are
  allowed, each named with the reason it is an exception — the column renderer, and the
  backup-retention cutoff, which is a **comparison key** compared as text against server-local file
  mtimes rather than a time anyone reads.
- Two behavioural tests beside it: the `Run:` line carries its offset at `+00` and at `+07`, and
  the window refusal names its clock. Both were verified to fail against 0.10.0's code before being
  kept.

## Changed / breaking

Nothing an existing tool root must do. `timezone` stays required and still defaults to `UTC` with a
warning — see the v0.10.0 notes, which remain the ones to read before upgrading **from 0.9.x**.

Two output strings change shape, neither machine-read as far as this repository knows:
`sre move-db-docker`'s manifest `created_at` becomes UTC `…Z` (was host-local with a `%z` offset),
and its moved-image tag becomes `moved-<YYYYMMDDHHMMSS on the configured clock>`.

## Verified

```
ruff check .                          All checks passed!
pytest tests -q                       6109 passed, 26 skipped, 10 xfailed, 0 failed
```

The same instant, rendered by the fixed `Run:` line in four zones:

```
Asia/Ho_Chi_Minh     Run: 2026-09-07 14:44:14 +07
UTC                  Run: 2026-09-07 07:44:14 +00
Asia/Kolkata         Run: 2026-09-07 13:14:14 +05:30
America/New_York     Run: 2026-09-07 03:44:14 -04
```

Each new test was confirmed to **fail against the code it fixes** before being kept — reverting
`_run_time_text` to the 0.10.0 version fails both parametrisations.

A source sweep of the shipped package finds no remaining host-clock read: no `time.localtime`, no
`time.strftime`, no naive `datetime.now()`, no `.now().astimezone()`, outside comments recording
the history.

## Known not to work

Unchanged from v0.10.0, and still the honest list:

- **Upgrading over an existing root is untested.** It is the breaking change from 0.9.x and the one
  that matters: a root on a `+07` host upgraded without adding `timezone` gets UTC and every
  hour-bounded schedule moves seven hours, silently.
- **No live DST transition has been observed.** Both sides of Europe/Berlin's are unit-tested; a
  real one has not happened under a running node, and a `+07` estate can never exercise it.
- **Midnight rollover is unobserved in production** — log rotation, the once-a-day report guard and
  the archive day boundary all fire at 00:00 in the configured zone.
- **Backup ages assume monitored servers share the operator's zone.** A database server's
  `latest_finish` arrives with no zone attached; both sides of the subtraction are now on the
  configured clock, which is right when the estate is in one timezone and wrong by the difference
  when it is not. A design limit, not a defect introduced here.
- A report file archived by an older version carries a stamp written on that node's host clock;
  `label_from_file_stamp` labels it with the configured zone.
- `DB_OPS_MESSAGE_UTC_OFFSET_HOURS` still works and is still deprecated.
- Everything listed as open in `v0.9.1` is still open.
