## What this release is for

**A dbabrain key.** Reports, backup / restore, SRE, the MCP server and the assistant now need a key from
dbabrain.dev: free, after an email sign-in, for 14 days. It is signed, kept in the node's encrypted secret
store and read offline; the node asks dbabrain.dev once a day whether it is still good. The end of a key is
said 7, 3 and 1 day before, three days of grace follow, and a restore you ask for always runs. Metrics,
instant alerts, SLA and SQL tasks need no key.

**The assistant without an Anthropic key of your own.** With `"provider": "dbabrain"` its turns go through
dbabrain.dev: $1 of AI a month, free, Claude Haiku 5.5 at effort medium. dbabrain.dev keeps each turn's
tokens and cost, never the question or the answer. Your own Anthropic key still works
(`"provider": "anthropic"`).

**The worker's secrets.** The passphrase is no longer in the container's environment or in Docker's
configuration: the worker's daemon starts locked and runs nothing until the master hands it the passphrase
(`control unlock-worker`). SSH private keys can be encrypted, their passphrases in the secret store.
`control rotate-passphrase` changes the store's passphrase on the master and the worker in one run, and
`worker-status` ends with a secret hygiene section.

## Upgrading

1. **Get a key before upgrading a node that makes backups**: `dbabrain key-request` prints a link; open it,
   sign in with your email, approve. One key per email: asking again on a second node replaces the first
   node's key - copy `DBABRAIN_KEY` to the other node with `secret-set` instead.
2. Run `dbabrain upgrade-config`: it writes `provider: "anthropic"` into an `ai_assist.json` that states
   none, so an assistant with its own Anthropic key carries on as before.
3. The runtime store's `repository_keys` and `backup_certificates` move to schema 2 the first time the new
   version opens the store.
4. **A container worker starts locked**: run `control unlock-worker` after every restart of the container or
   reboot of the host. The first `deploy-code` rewrites the compose file's `DBABRAIN_SECRET_KEY` entry into
   `DBABRAIN_UNLOCK_FILE` and unlocks the worker itself.

## Added

- `key-request`, `key-renew` and `key-status`.
- The assistant through dbabrain.dev; a new install ships it switched on, waiting for the key.
- `seal-ssh-key` encrypts an SSH private key in OpenSSH's format, its passphrase in the secret store.
- `control unlock-worker`, `control rotate-passphrase` and `control worker-prune`.
- The secret hygiene section of `worker-status`; a worker node's `key_file` in `config.json`.

## Changed / breaking

- Reports, backup / restore, SRE, the MCP server and the assistant do not start on a node without a key
  (step 1 above).
- A container worker does nothing after a restart until it is unlocked (step 4 above).
- A deploy leaves one dbabrain on the worker: older images, image tars and copies of `data/` are removed
  once the new container runs. A rollback is a rebuild of the previous version.
- `control worker-status` reads the worker through `db.cli node-status`; `python -m dbabrain.jobs.status`
  still answers.

## Fixed

- An offload pass reads which copies are sealed in one query, not one per file ever encrypted. With about
  10,000 encrypted files a pass took 13 minutes, and the files on the source waited about two hours to be
  deleted.

## Known limitations

- **Over MCP, "read only" is a hint to the client, not a security boundary.** Tools are switched off by name
  (`disabled_tools`), and `run-sql`'s check reads the statement's text. Treat an MCP client as having the
  node's own access: connect only clients and accounts you trust, keep the approval prompts on, switch off
  the tools you do not need, and give the node logins that can only read.
- **A key serves one node per email** unless it is copied; a second `key-request` replaces the first.
- **A container worker that restarts does nothing until it is unlocked**, its Telegram messages included.
- **A single node without a worker** has no command to change the store's passphrase yet.
- **Oracle's and PostgreSQL's point in time from a source whose clock is not UTC** has not been tested.
- **A PostgreSQL or Oracle restore under another name** (`RENAME` / `DUPLICATE TO`) is not supported; an
  entry mapping a name for those engines is refused.
- **After a PostgreSQL or Oracle restore the target's logins are the source's**: the inventory's password
  for the target no longer logs in until it is set again.
- **An MCP node cannot run a restore**: `restore-by-id` is not an MCP tool, by design; run it on the node.
