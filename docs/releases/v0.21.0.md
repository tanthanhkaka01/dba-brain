## Summary

**A schedule can now say which days of the week it runs on.** `time_window` gains one field,
`weekdays` — ISO 1 to 7, Monday to Sunday — and it works on everything that carries a time window:
app commands, SQL targets, metrics, reports, backup jobs and restore entries.

That field exists because of a bug it removes. The PostgreSQL and Oracle backup scripts used to pick
FULL or incremental themselves, by comparing a weekday against `7` — and the weekday they read was
the **container host's**, not the one the scheduler had just used to decide whether the same job's
hour window was open. One backup, two clocks, and no way to see it from the configuration. The level
is now stated in the job and the day is stated in its window, both read on the node's own clock.

**And a PostgreSQL incremental that cannot chain no longer produces nothing at all.** An incremental
needs WAL summaries covering its parent's LSN range; a baseline taken before `summarize_wal` was
switched on can never be chained onto, and no retry will change that. The job used to fail on this
every night and leave the backup directory without a single new entry. It now takes a full baseline
in the same run, so the night still has a backup that restores.

## Added

- **`time_window.weekdays`** — an array of ISO weekdays, `1` = Monday to `7` = Sunday, the same
  numbering `isoweekday()` and `date +%u` use.
  - **Absent** means no restriction, so nothing written before this release changes behaviour.
  - **`[]`** means no day is permitted, so the record never runs on a schedule. It is not
    `repeat_interval: -1`, which is never scheduled but still runnable on request, and not
    `active: false`, which stops the record being listed at all. What `weekdays: []` parks is the
    *window*, leaving the interval and the hour bounds exactly as written — which is what
    suspending a weekly job without losing its configuration needs.
  - **`0` is refused**, not ignored. It is the cron spelling of Sunday, and a parser that dropped it
    would leave `[]` — so a weekly full would stop for good while its config still read like a
    schedule. A day listed twice is refused too: it is a set, not a weighting.
  - **It gates due-ness, it does not grant it.** `repeat_interval` still decides *whether*;
    `weekdays` decides *whether today*. Keep the interval well under a day on a weekday-gated
    record: with a multi-day interval the due moment walks, and the cycle it lands after the window
    has closed is skipped entirely.
  - `due-check` explains a weekday verdict the same way it explains an hour one, so a schedule can
    be asked why it did not run.

## Fixed

- **A weekly backup no longer reads two different clocks.** The PostgreSQL and Oracle scripts chose
  FULL by comparing `${DB_OPS_WEEKDAY:-$(date +%u)}` against `7`. `DB_OPS_WEEKDAY` only started being
  passed in 0.20.0, so on any earlier node the fallback read the container **host's** clock. Where
  that host is UTC and the node is not, the two disagree for part of every day: measured on a +07
  estate, the host said Saturday while the node said Sunday, and the incremental ran on the night
  the weekly full was due — five nights running, each one failing.
- **A PostgreSQL incremental whose baseline cannot be used now takes a baseline instead of failing.**
  The script asks `show summarize_wal` before it tries, and classifies the server's own refusal: a
  *WAL summaries* error on an incremental takes a FULL in the same run. Every other failure is still
  fatal — answering a full disk by writing more is not a recovery — and the script never creates the
  backup directory itself, because a directory made so a run looks successful is a backup that does
  not restore.
- **`APP-BACKUP-RESTORE` now ships `repeat_interval: 30`**, down from 300. The app's own interval is
  a floor under every job inside it, because the app is one process working through its own due
  list: at 300 s, a log backup declared at 900 s ran every ~1,200 s and nothing in that job's
  configuration said why. An existing `app_commands.json` keeps whatever it already says.
- **The daemon now waits out a store restart instead of exiting.** A store outage is classified from
  the SQLSTATE the server sends, and every *connect* failure arrives wrapped — the store raises its
  own error `from` the driver's — so the code was one link down the exception chain and was never
  read. `57P03`, the very code the tolerance exists for, was therefore classified as permanent and
  the daemon exited on its first attempt. The chain is now walked, a wrapped permanent code is still
  permanent, and *"the database system is in recovery mode"* — the other wording of `57P03` — is
  recognised from its text as well.
- **A SQL task can no longer be registered on an engine no task can run on.** `sql-command-add` and
  `add-sql` accepted `postgresql` and `mysql`, and the task then failed at its first scheduled run
  with `Unsupported db_type`. Both now refuse at registration and say what a task can run on. This
  changes nothing about PostgreSQL or MySQL *instances* — metrics still collect from them and backups
  still back them up; it is only running a task script on one that was never supported.
- **A PostgreSQL incremental no longer chains onto a backup of a different cluster.** The parent was
  simply the newest directory under `base/`. A cluster that has been restored, re-`initdb`'d or
  replaced gets a new system identifier, and the server refuses the old parent **permanently**, so
  the job failed every night with nothing written. The parent's `System-Identifier` is now checked
  before the attempt, and a mismatch — or a manifest too old to carry one — takes a FULL baseline.
- **The engine scripts can now be told which database they mean.** `PG_PORT` for PostgreSQL and
  `ORACLE_SID` for Oracle, in a job's `env`; unset keeps exactly today's behaviour. Neither could be
  expressed before. With one instance per container both were right by accident; with two they were a
  coin toss that reported success against the wrong database. Note that setting `PGPORT` yourself
  would *not* have worked — `docker exec` does not carry the calling environment into the container.
- **An Oracle backup no longer rewrites a database's persistent RMAN configuration in silence.** The
  `CONFIGURE` statements live in the controlfile, apply to every later connection, and decide what the
  same run's `DELETE NOPROMPT OBSOLETE` removes — so on a database you did not create, the first run
  replaced somebody else's retention and archivelog policy with nothing said. `SHOW ALL` now runs
  first, so the previous values are in the captured output, and `RMAN_CONFIGURE=skip` leaves the
  database's own configuration alone. **Read the note under Known limitations before using `skip` on
  an archivelog job.**
- **`deploy --merge` now says which of the worker's records the master overwrote.** The rule is
  unchanged — the master wins a shared key — but it was silent, so a file whose only news was three
  discarded worker records printed `SAME` and the upload applied the master's copy anyway. Each one
  now prints an `OVERRIDE` line naming the fields, and an override that would switch off a task
  currently active on the worker says so in those words.
- **A config drift report names the fields that differ**, not just the record, because one line is
  the whole of what `--on-config-drift keep` against `adopt` is decided from.

## Changed

- **`data/shared_config_objects.json` describes two more things**, so `check-objects` can hold a
  config to them rather than a reader having to trust prose:
  - `time_window.weekdays`, with an item range and a uniqueness rule a program evaluates.
  - **`app_command`** — all fourteen fields of an app command, two of them required. It was the one
    record that decides what runs at all and nothing described it. It also names the fields that are
    **not** read at run time, which is the kind of thing a reader otherwise assumes.

## Known limitations

- **`RMAN_CONFIGURE=skip` is not free on an archivelog job.** Its `DELETE` statements name an age, but
  RMAN still consults the archivelog deletion policy before removing anything. Under the policy this
  release's script sets (`BACKED UP 1 TIMES TO DISK`) a log that has not been backed up survives its
  age; under `TO NONE`, which is the default on a fresh database, the same statement deletes it. So
  `skip` trades a silent policy overwrite for a possible silent hole in the recovery window. Both
  directions are stated in the script; neither is chosen for you.
- **PostgreSQL and Oracle backups require a container.** `DOCKER_CONTAINER` is not optional and every
  command in both engine scripts goes through `docker exec`, so an engine installed directly on a
  host cannot be backed up. The failure reads `DOCKER_CONTAINER is not set`, which looks like a
  configuration mistake rather than a missing capability. SQL Server has no such limit.

- The PostgreSQL and Oracle backup scripts **require a container**: `DOCKER_CONTAINER` is required
  and every command goes through `docker exec`, so an engine installed natively on a host cannot be
  backed up by them. There is also no `PGPORT`/`PGHOST` or `ORACLE_SID` in their environment
  contract, so **two clusters or two SIDs inside one container cannot be addressed** — the scripts
  reach the container's default socket, and the `port` in the inventory is the published host port,
  which they never use.
- An Oracle backup entry **takes ownership of that database's RMAN retention policy**. The script
  issues `CONFIGURE RETENTION POLICY`, `CONFIGURE CONTROLFILE AUTOBACKUP` and `CONFIGURE ARCHIVELOG
  DELETION POLICY`, which are persistent settings in the target's controlfile rather than options for
  one run, and `DELETE NOPROMPT OBSOLETE` then acts on the policy just installed.
- Nothing restarts the daemon if it stops. A short store outage is waited out, but an exit for any
  other reason leaves the estate with no scheduler and no alarm.
- `retry_interval` cannot postpone a retry: a failed run is due again once `repeat_interval` has
  elapsed, and a `retry_interval` larger than `repeat_interval` has no effect.
- `--force` on a SQL task runs every target of that task, including targets with `active: false`.

## Upgrading

`SCHEMA_VERSION` is unchanged from 0.20.0, so the store needs nothing.

**If you have a PostgreSQL or Oracle backup entry, it needs the two-job shape.** Those scripts no
longer derive a level, so a job that pins no `BACKUP_LEVEL` will take the **incremental** every day
instead of a full once a week. Give the entry two jobs:

```jsonc
{"job": "database_full", "env": {"BACKUP_LEVEL": "full"},      // Oracle: "0"
 "time_window": {"weekdays": [7], "from_hour": 1, "to_hour": 5, "repeat_interval": 72000}},
{"job": "database",      "env": {"BACKUP_LEVEL": "incr"},      // Oracle: "1"
 "time_window": {"weekdays": [1,2,3,4,5,6], "from_hour": 1, "to_hour": 5, "repeat_interval": 72000}}
```

Keeping the incremental on the existing job name is worth doing: the job name is part of the code
runs are recorded under, so a rename starts a new history, and the incremental is six runs in seven.

SQL Server entries already state their level in `env` and need no change.

The two reference files reach an existing node through a config deploy or `init`, not through
`pip install`.
