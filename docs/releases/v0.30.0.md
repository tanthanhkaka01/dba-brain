# v0.30.0 — metric coverage on SQL Server, Oracle and PostgreSQL, and availability counted in minutes

| | |
| --- | --- |
| Date | 2026-10-19 |
| Previous | `v0.29.0` |
| Python | 3.12, 3.13 |
| Artifacts | PyPI wheel + sdist, `ghcr.io/tanthanhkaka01/dbabrain:0.30.0` |

## What this release is for

**The three engines are watched for the same things.** Until this version much of what was graded
on SQL Server was a placeholder on Oracle and PostgreSQL - deadlocks, the session holding the locks,
failed and long-running jobs, corruption, the server's own log, the Workload section. Each of those
now runs on all three, by SQL Server's rule where the engine allows it, and the catalogue gains ten
metrics (98 - 107) for what had no reading at all: Oracle's ADR incidents, latency percentiles, the
host's and the database's CPU, memory grants, PostgreSQL's checkpoint pressure and server log, I/O
latency inside one run, SQL Server's own incidents.

**The SLA app judges what an operator is asked about.** Availability is counted in minutes, with
burn-rate alerts and a calendar-month table; backups are judged against a recovery point and
restore drills against a recovery time.

**A slow metric no longer holds the estate.** A collect pass runs one batch per server and metric
category, and the next pass starts while a slow batch is still running.

## Fixed since v0.29.0

- **A slow metric no longer holds every other metric of the estate.** A collect pass ran one
  server's metrics one after another and ended with its slowest server; a nightly
  index-fragmentation scan left `INSTANCE_STATUS` unsampled on every server for ~18 minutes. See
  *Changed* for the batches that replace it.
- **The Workload CPU is no longer 0% on SQL Server Standard, Web and Express.** Those editions keep
  no Resource Governor CPU total; the CPU rows now come from the best source each target has, and
  name it.
- **`LOCK_TRANSACTION_HOLDERS` no longer pages on a lock count the counter kept from a past peak.**
  `Lock Owner Blocks` was seen reading an Agent job's 15.7 M locks for eight minutes after the job
  ended, naming a one-second-old transaction CRITICAL. A count no open transaction could have built
  is now WARNING, and no session is named for it.
- **A backup policy whose overrides give some databases no data-backup objective**
  (`"data_backup": null`) no longer fails the SLA summary with `KeyError`.
- **`metric-severity` and `metric-toggle` keep `db_instances.json` in its own indent**: both wrote
  it back at a 1-space indent, so one remap of a 2-space file was a diff of every line in it.

## Added since v0.29.0

- **`instance-active`**: one instance switched on or off for every app - its `active` flag in
  `db_instances.json`, nothing else; `metric-toggle` stays the metrics app's own switch.
- **`metric-severity` takes a list**: `{"items": [...]}` writes every remap in one write of
  `db_instances.json`, or none, the first refused named by its place.
- **`metric-env`**: a collector script's inputs on one instance (`metrics.collector_env`), set or
  removed - `PG_BACKUP_DIR` for a PostgreSQL whose base backups are not in the default folder.
- **`sql_tasks run-sql-adhoc`**: SQL that is not a registered task, against one `server_id`, the
  login resolved by the app. Rolled back unless the request says `commit` or `autocommit`; a write
  costs one typed `yes` (operation `run-sql-adhoc`, level 50).
- **`sre run-cmd-adhoc`**: one shell command on the host of a `server_id`, the host login resolved
  from the instance's `cmd_access`. Every run asks for one typed `yes`.
- **`metrics collect --test-run`**: every metric of a target's engine tried on one named target,
  printed as graded, nothing kept - for a lab instance the inventory keeps switched off.
- **The SLA app judges backups and restore drills**: `backup_rpo` against `backup_policy.json` -
  every required type and the data backup, the newest of FULL or DIFF, counted by database -
  `restore_drill` against `restore_drill_policy.json`. Packaged policies `ALL_BACKUP_RPO_24H` and
  `RESTORE_DRILL_RTO_30D`; an override with `"required": false` retires a drill that was switched off.
- **Latency percentiles** on all three engines, recorded and never graded:
  `QUERY_LATENCY_PERCENTILES` (Query Store), `ORACLE_WAIT_LATENCY_HISTOGRAM` (`v$event_histogram`),
  `POSTGRES_STATEMENT_TOTALS` (`pg_stat_statements`), shown in the server page's *Latency
  percentiles* section.
- **New metrics**: `ORACLE_ADR_INCIDENTS` (98, with open critical Health Monitor findings),
  `MEMORY_GRANTS_PENDING` (102), `POSTGRES_CHECKPOINT_PRESSURE` (103, recorded only),
  `PERFORMANCE_IO_LATENCY_INTERVAL` (104), `SERVER_DIAGNOSTICS` (105, memory dumps and
  `sp_server_diagnostics`), `POSTGRES_SERVER_LOG` (106, a container's log or a host install's) and
  `OS_CPU_COUNTERS` (107, the host's and the database process's CPU).
- **Oracle 11g and later collect** `AVAILABILITY_DATABASE_HEALTH`, `BACKUP_JOB_STATUS`,
  `LOG_RECENT_CRITICAL`, `LOG_REUSE_WAIT` and `LOCK_SLEEPING_OPEN_TRANSACTION`; Oracle's running
  scheduler jobs are listed as SQL Server's Agent jobs are; a failed Oracle scheduler job pages
  (`JOB_FAILED`).
- **PostgreSQL** samples its wait events (`PERFORMANCE_WAIT_STATS`, 10+) and reads its temp space
  against `temp_file_limit` (`STORAGE_TEMP_SPACE`, 12+).
- **Deadlocks graded on Oracle and PostgreSQL** by SQL Server's rule; a metric variant may state its
  own `repeat_interval`.
- **The Workload section on Oracle and PostgreSQL**, and CPU, Memory and Disk space tiles that say
  what their percentage is of.
- **A Diagnostics section on the server page**: error and alert logs, ADR and Health Monitor,
  memory dumps, the PostgreSQL server log and corruption, one table on every engine.
- **A connection probe on the server page**: every SQL metric records how long it took, and
  `INSTANCE_STATUS`'s p50 / p95 / p99 and maximum over the last day open the Latency section.

## Changed / breaking

- **A collect pass runs one batch per server and metric `category`**, the batches at once, each
  claimed by one pass at a time. The shipped `APP-METRICS` is `run_mode: async`,
  `max_parallel: 4`, `repeat_interval: 1`. **A server may now get one database session per category
  at once** - one per server before. A pass with nothing due writes nothing, and every metric's
  interval is read in one query.
- **`INSTANCE_STATUS` every 30 s** (was 60) and **`STORAGE_DISK_FREE_SPACE` every 300 s** (was
  3600).
- **Availability counted in minutes**: SLA `aggregation: "minutes"`, policies
  `INSTANCE_AVAILABILITY_24H` and `INSTANCE_AVAILABILITY_30D` (99.9 % of minutes). A policy may list
  `burn_rate_alerts`; a fast burn turns a passing result into the new status **`BURNING`** and
  sends a Telegram message when it starts and when it ends. `calendar_month_report: true` adds a
  this-month / previous-month table to the SLA page. **`APP-SLA-VALIDATE` runs every 5 minutes**
  (was hourly). An earlier version's SLA parser refuses a `minutes` policy.
- **Every `app_commands.json` field is required**; `upgrade-config` writes into a node's records
  the value the daemon had been giving each field left out.
- **More of the server is graded** (thresholds in `CHANGELOG.md`): SQL Server's system databases,
  a stopped SQL Server Agent, connections against `user connections`, severities 19 and 20, worker
  starvation, Availability Group queues and tempdb contention, mirroring and log shipping, an
  unexpected sysadmin, a transaction log that cannot grow; PostgreSQL's multixact age and standby
  replay lag; Oracle's process limit, archive destinations, PDB open mode, temp space in use and
  data-file space per tablespace; corruption on every engine; an idle session holding an
  application lock it owns. **`lock_scan_skip_above` is 2,000,000** (was 500,000).
- **A backup policy judges the data backup as the newest of FULL or DIFF** (`data_backup`, 48 h by
  default); FULL keeps a bound of its own (240 h), LOG is 120 minutes to a critical. A policy file
  without `data_backup` is judged as before.
- **The Oracle SLA policies measure a modern Oracle** (`v$sysmetric` from 10g; a minute with under
  100 logical reads a second is not graded for the buffer cache, since an idle PDB reads 0), and an I/O latency
  SLO `SQLSERVER_IO_LATENCY_24H` is added.

## Known not to work

- Everything listed for v0.29.0 still holds, but for Oracle from 10g on: the process limit, the
  pools and the buffer cache are now collected there.
- **Rows from before the upgrade hold no execution time**, so the connection probe starts empty.
- **`POSTGRES_CHECKPOINT_PRESSURE` is recorded, not graded**: its counters are cumulative and there
  is no interval view yet.
- **RMAN's job history is CDB-level**: an Oracle target connected to a PDB sees none of it.
- **A restore that finishes as the stale-run check looks at it can be recorded `TIMEOUT`** (*pid …
  is gone*), although its own `END` row says done and its verify passed. Seen twice in three weeks
  on one node, on two engines; the next run is not affected. Older than this version.
- **Latency percentiles need the engine's own source**: Query Store on SQL Server 2016+,
  `pg_stat_statements` on PostgreSQL. A SQL Server database without Query Store is skipped; a
  PostgreSQL server without the extension answers one `NOT_INSTALLED` row.

## Upgrading

1. **After `pip install --upgrade dbabrain`, run `upgrade-config`** - the plan first
   (`python -m dbabrain.common.cli upgrade-config '{}'`), then `'{"dry_run": false}'`. Its step
   `earlier-defaults` states `run_mode`, `max_parallel` and `note` in every `app_commands.json`
   record that left them to the daemon; nothing a node runs changes. Then
   `python -m dbabrain.db.cli --config config.json sync-config '{}'`.
2. **Take the new metrics** from the shipped catalogue (`dbabrain/metrics/catalogue/metric_definitions.json`)
   into your `data/metric_definitions.json`: a node keeps its own file, and the metrics 98 - 107,
   the new variants and the new intervals are read only once it states them. Do it on this version,
   not before: an earlier image lacks the collector files they name.
3. **Choose the collect pass**: set `APP-METRICS` to `run_mode: async`, `max_parallel: 4`,
   `repeat_interval: 1` as the shipped record does - on this version only, since an earlier one
   has no batch claims - and count one database session per metric category per server
   (`collection.max_parallel_servers` caps the batches a pass runs at once).
4. **Add the SLA policies you want** from the shipped `sla_policies.json`
   (`INSTANCE_AVAILABILITY_24H`, `INSTANCE_AVAILABILITY_30D`, `SQLSERVER_IO_LATENCY_24H`,
   `ALL_BACKUP_RPO_24H`, `RESTORE_DRILL_RTO_30D`) and set `APP-SLA-VALIDATE` to every 300 s for the
   burn-rate windows. **Read `backup_policy.json` and `restore_drill_policy.json` first**: every
   breach there turns the SLA page red.
5. **A PostgreSQL installed on its host, not in a container**: `POSTGRES_SERVER_LOG` reads its log
   over the target's SSH `cmd_access`. A log only `postgres` may read needs `sudo -n` for that
   login, and a host running two clusters needs `PG_LOG_FILE` or `PG_LOG_DIRECTORY` in the target's
   `collector_env`.

`SCHEMA_VERSION` is unchanged, and the store keeps its database, schema and rows.
