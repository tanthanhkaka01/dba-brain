# v1.3.0 — Fewer, clearer MCP tools; the repository check no longer trips over a sibling offload

| | |
| --- | --- |
| Date | 2026-11-27 |
| Previous | `v1.2.0` |
| Python | 3.12, 3.13 |
| Artifacts | PyPI wheel + sdist, `ghcr.io/tanthanhkaka01/dbabrain:1.3.0` |

## What this release is for

**An agent picks the right MCP tool more often, among fewer of them.** The server offered 108 tools, several of
them the same operation in another form - a singular beside its plural, three restore steps, three listings of
one request. Commands that share one request and one hint are now one tool with one field choosing, a command
another tool already does is not offered, and two commands that ask a person at a terminal are not offered over
MCP. 94 tools remain. Each tool's description now says what it does first, and in a family - file transfer,
deletion, SQL, restore - which sibling to use instead.

**A backup offload no longer fails on a neighbour's files.** The repository check could list a server's folder
while another offload of the same server was writing into it, and fail on files that were not yet recorded. It
now waits for the next pass in that case, as it already did when that offload was running when the check began.

## Upgrading

1. Run `dbabrain upgrade-config` as usual.
2. If an MCP client names tools - an allow list, a saved prompt, a `disabled_tools` entry - use the new names:
   `restore`, `list-objects`, `check-config`, `sqlserver-cu-check`, `store-schema`, `store-query`. An old name in
   `disabled_tools` still switches its tool off, and a call by an old name answers which tool to use.

## Changed

- **MCP: commands too alike are one tool**, one field choosing which command runs:

  | Tool | Field | Was |
  | --- | --- | --- |
  | `restore` | `step`: full, diff, log | `restore-full`, `restore-diff`, `restore-log` |
  | `list-objects` | `kind`: databases, schemas, jobs | `list-databases`, `list-schemas`, `list-jobs` |
  | `check-config` | `check`: objects, references, credentials | `check-objects`, `check-references`, `check-credentials` |
  | `sqlserver-cu-check` | `check`: precheck, build | `sqlserver-precheck`, `sqlserver-verify-build` |
  | `list-backup-files` | `action`: list, prune-plan | `list-backup-files`, `prune-backup-files` |

  Only commands that share one request and one read-or-change hint are grouped, and no emergency operation is.
  The `common.cli` commands are unchanged.
- **MCP: a command another tool does is not a tool of its own** - `delete-verified-file` and `delete-empty-folder`
  (their plurals take a one-item list), `key-renew` (`key-request` renews), `add-sql` (`sql-command-add` then
  `sql-target-add`). `ask` and `authorize` are not offered: they ask a person at the node's terminal, which an MCP
  call does not have.
- **MCP: `store_schema` / `store_query` are `store-schema` / `store-query`**, so every tool name is kebab-case.
- **MCP descriptions** open with what the tool does, a verb first, and name the sibling to use instead where
  tools are alike; the `dbabrain common.cli` prefix is gone.
- **`prune-backup-files` is marked read-only**: it answers a retention rule's plan and deletes nothing.

## Fixed

- **Offload repository check**: when the listing of a server's repository folder finds anything, the check asks
  again whether another offload of that server ran meanwhile; if one did, the folder is checked on the next pass
  instead of failing the run on files that offload had not yet recorded. A stray file with no such offload still
  fails the run.

## Verified

- The test suite on Python 3.12 and 3.13.
- MCP: tests list every tool on an empty home and call each grouped tool with each value; the command its field
  names runs, without the field. Old names answer the new tool, and an old name in `disabled_tools` keeps it off.
- Offload: tests start a sibling offload during the folder listing - running when the listing ends, or started
  and finished within it - and the run is not failed; a stray file with no such offload still fails it.
- The wheel installed into an empty Python 3.12 virtual environment: `dbabrain --version` 1.3.0,
  `dbabrain init`, `dbabrain daemon --config config.json --once` with no key - every command that needs none
  finished `done`, and those that need a key were skipped and said so; `dbabrain mcp tools` listed 94 tools.
- `ruff check .`: all checks passed. `gitleaks` over the published files: no leaks found.

## Known limitations

- **Over MCP, "read only" is a hint to the client, not a security boundary.** Tools are switched off by
  name (`disabled_tools`), and `run-sql`'s check reads the statement's text. Treat an MCP client as having
  the node's own access: connect only clients and accounts you trust, keep the approval prompts on, switch
  off the tools you do not need, and give the node logins that can only read.
- **Switching off `prune-backup-files` switches off `list-backup-files`** over MCP, now that they are one tool.
- **A Telegram message can arrive twice** after a send that timed out but had reached the chat.
- **Oracle's `query-plan`** is refused: Oracle's `EXPLAIN PLAN` writes to a table.
- **PostgreSQL's top queries** need the `pg_stat_statements` extension; without it `db-activity` says so.
- **A key serves one node per email** unless it is copied; a second `key-request` replaces the first.
- **A container worker that restarts does nothing until it is unlocked**, its Telegram messages included.
- **A single node without a worker** has no command to change the store's passphrase yet.
- **Oracle's and PostgreSQL's point in time from a source whose clock is not UTC** has not been tested.
- **A PostgreSQL or Oracle restore under another name** (`RENAME` / `DUPLICATE TO`) is not supported; an
  entry mapping a name for those engines is refused.
- **After a PostgreSQL or Oracle restore the target's logins are the source's**: the inventory's password
  for the target no longer logs in until it is set again.
- **An MCP node cannot run a restore workflow**: `restore-by-id` is not an MCP tool, by design; run it on the
  node. The `restore` tool runs one engine step at a time.
