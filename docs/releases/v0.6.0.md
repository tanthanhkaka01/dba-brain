## What this release is for

v0.5.0 was run for the first time the way anyone else would run it — `pip install dbabrain` on a
host that had never had the source — and the first ten minutes were where it went wrong, not the
engine. This release is the result of that: the install path now refuses the mistake it used to
accept silently, the one connection error that read like a network fault now names its real cause,
and two commands were added for the questions asked most often when something looks off — *what has
this thing been doing* and *what is this thing, exactly*.

**No upgrade action is required.** See *Changed / breaking*.

## Added since v0.5.0

- **`db-ops db sql-run-history` and the Telegram `/spbot_list_sql_runs`** — the most recent SQL task
  runs and how each one ended, newest first, with the failure reason on any that failed. `list-tasks`
  answers *what is configured*; this answers *what actually ran*. It reads `sql_runs` through the
  shared `common` layer, so the bot and a shell get the identical answer, and the listing stops
  before Telegram's size limit rather than letting the transport cut the newest rows.

- **`db-ops common self-status` and the Telegram `/spbot_self_status`** — what this installation is
  and how much room it has left: the distribution (published `dbabrain` vs a private `db_ops`
  build) and version, whether it runs in Docker or on the OS and which OS, host and ip, node role,
  store, cpu, memory and disk. It reads itself — no SSH, no store — so it still answers when the
  store is the thing that is down. Memory is read from the cgroup first and every figure names its
  source, because inside a container `/proc/meminfo` is the host's memory, not the process's limit.

## Fixed since v0.5.0

- **`import-data` no longer unpacks an estate into `site-packages` and calls it success.** Run from
  a new empty directory with no `--root`, it used to resolve the tool root to the package's own
  install location, write the whole estate there, and print `imported into …/site-packages` — which
  reads like success and leaves the next command with nothing to find. It now refuses that, names
  the directory, and gives both ways forward (`--root .`, or `db-ops init` first). A stated `--root`
  is still honoured wherever it points.

- **`import-data` says when the imported schedule will not run here.** An estate exported from a
  worker declares `node_role: worker` on every command, and a process that was not told otherwise is
  `master`, so the daemon would start and do nothing. The import now says so, and names the fix,
  while the operator is still at the keyboard — not only later, in a log line.

- **A legacy-TLS connection failure names its real cause.** SQL Server 2008 R2 and 2012 offer
  nothing above TLS 1.0, and OpenSSL 3 refuses anything below TLS 1.2, so a `pip install` on a
  modern Linux host fails to reach them with `SSL routines::unsupported protocol` — which names
  neither the instance's age nor the setting behind it. The connect error now explains that the
  policy belongs to the machine running the toolkit, not the instance or the credential, and gives
  the two settings that fix it; a separate, distinct message covers the follow-on trap
  (`MinProtocol = TLSv1.0` is rejected by OpenSSL 3.5 — the token is `TLSv1`), which breaks *every*
  connection rather than only the old ones.

- **The container image's TLS floor is spelled correctly.** The Dockerfile set `MinProtocol =
  TLSv1.0`, a token OpenSSL 3.0 tolerated and 3.5 rejects; it is now `TLSv1`. The image worked only
  because its base still ships OpenSSL 3.0 — a base bump would have taken every SQL Server target
  down at once.

## Changed / breaking

Nothing. Two new read-only commands, three fixes to install and connection paths, and a
one-token Dockerfile correction. No configuration changes, no schema changes, no thresholds moved.
An existing install upgrades in place; `db-ops init` on a new tool root now writes 28 Telegram
commands instead of 26.

**One prerequisite made explicit, not new:** monitoring old SQL Server instances from a `pip`
install on Linux needs OpenSSL told to allow TLS 1.0 (`MinProtocol = TLSv1`,
`CipherString = DEFAULT@SECLEVEL=0` via `OPENSSL_CONF`); the container has always done this at
build time. `docs/installation.md` now documents it. On Windows nothing is needed — SChannel
permits it.

## Known not to work

- **OS-level metrics from a `pip` install need the `[ssh]` extra.** `OS_*` and
  `DOCKER_CONTAINER_STATS` reach monitored hosts over SSH; an install without `dbabrain[ssh]` reports
  them as `paramiko is required`. The container ships it; a `pip install` must ask for it.
- **`self-status` memory is the cgroup limit only when one is set.** A container run with no memory
  limit reports the host's memory and says so in the source line, rather than inventing a ceiling.
- Interval **grading** remains withdrawn, unchanged from v0.5.0: the workload collectors report,
  and no severity is derived from a rate.
