## What this release is for

One new bot command, and it exists because of a shape the bot's own design creates. The useful
commands take arguments nobody keeps in their head — a `sql_id` from one listing, a `server_id`
from another, a date range — and when they are not typed inline the bot asks for them one at a
time. That is the right way to ask, and it makes the command **unfindable afterwards**: the
message that started it says `/spbot_run_sql_task` and nothing else, while the `18` and the `0 30`
are separate messages further down that read as ordinary conversation. Scrolling a chat to
reassemble a command you ran an hour ago is the daily cost of a design that is otherwise correct.

`/spbot_list_my_commands` pays it back. It does not quote the chat — it **rebuilds the line**, from
the answers the bot itself stored, in the order the dispatcher reads them.

It also carries `db-ops db backfill-from-sqlite`, which was written and committed after `v0.7.2`
was cut and therefore ships for the first time here.

## Added since v0.7.2

- **`/spbot_list_my_commands` — your own last 10 distinct commands, each as one line you can run
  again.** The arguments of a prompted command live positionally in
  `telegram_conversation_states`, and the chain carries `source_telegram_command_message_id`
  forward from prompt to prompt, so the last state of a chain holds them all. Joined in that order
  they are the inline form of the same command: four messages become
  `/spbot_run_sql_task 18 0 30`, one line to copy.

  What it does beyond joining, and why each was needed:

  - **Distinct by the rebuilt line, with repeats counted.** Measured on a real chat, ten
    consecutive command messages were four distinct commands; without this, a listing of ten
    spends nine lines on the command somebody ran nine times while chasing one problem.
  - **A prompt that was never answered is skipped, and counted.** Its arguments are incomplete, and
    offering half a command invites someone to run it to find out which half is missing. The count
    is printed, because hiding without accounting is indistinguishable from losing — the rule every
    `/spbot_list_*` reply already follows.
  - **A command that ran and failed is listed, marked, and keeps the argument that was refused.**
    After a failure it is the line most likely to be typed again.
  - **Private chat only.** The history spans every chat that person has used the bot in, so
    answering it in a group would read a private command out loud there.
  - **Whose history comes from the message, never from an argument.** A history command that took
    the person as a parameter would let anyone read anyone's by typing a number.

- **`db-ops db telegram-command-history '{"user_id": "...", "limit": 10}'`** — the same answer as a
  JSON-object CLI command, for a store the bot is not attached to.

- **`db-ops db backfill-from-sqlite --source <store> [--plan-only]`** — carry a stand-in node's
  history back into the shared store. It was written and committed after `v0.7.2` was cut, so
  this is the release it first ships in. When the worker is stopped and the estate is run from
  a laptop or a fresh install, that node's store is a local SQLite file: the metrics, reports,
  SQL task runs and alerts are real, and the shared store shows a hole exactly as wide as the
  outage.

  Copying rows is not the difficulty; the ids are. Every primary key involved is an identity
  column, and a store that started numbering at 1 has ids already taken in a store with
  millions of rows — so nothing carries its key, and the links become the problem:
  `sla_results.sla_run_id` is a real foreign key and is *refused*, while
  `metric_results.run_id` and `reports.telegram_send_message_id` are plain integers that would
  be **accepted** and point at somebody else's run. The second kind is the worse one, because
  nothing reports it. Parents are carried first, their old-to-new mapping is kept, and every
  child is rewritten through it before it lands.

  `--plan-only` prints the row count per table and the destination watermark each one would
  start from, so the whole thing is readable before anything is written. The window *is* that
  watermark — the destination's own newest row per table — so a second run against an unchanged
  source carries nothing, and an interrupted run is finished by running it again. One
  transaction per table rather than one for the run, so an interruption leaves the store
  consistent. A row whose parent predates the window is dropped or crosses without the link
  depending on whether the column is nullable, and both are counted and printed.

## Changed / breaking

Nothing an existing tool root must do. Two internal moves worth knowing if you import from this
package:

- The command-message text rules (`parse_command_message`, `normalize_command_text`,
  `split_command_tokens`, `strip_bot_username`, `first_command_token`,
  `command_key_from_message`) moved from `db_ops.telegram.command_processor` to the new
  `db_ops.lib.telegram_command_text`, because `common` needed them and may not import an app.
  `command_processor` re-exports every one of them, so existing imports keep working — the same
  shim `db_ops/telegram/severity.py` already is.
- `LISTING_CHARACTER_BUDGET` and the default listing depth now live once in `db_ops.lib.listing`,
  where the `/spbot_list_*` rule already lives. `db_ops.common.sql_run_history` imports them
  instead of declaring its own copies; `sql_run_history.DEFAULT_LIMIT` is now
  `DEFAULT_LISTING_LIMIT`.
- A `cli_execute` command can now use `{user_id}` in its `command_argv`, beside the existing
  `{chat_id}`. It is always set — empty when the message carries no sender — so an unrendered
  `{user_id}` can never reach a CLI as a literal.

## Known not to work

- **A command whose argument positions changed since it was run is rebuilt against the positions
  recorded at the time.** The stored answers are positional, so a line from before a parameter was
  added or reordered may not run today. Seen on this estate: `/spbot_run_sql_task 18 0 30` was
  recorded when `task_params` was position 2 and is position 3 now. The line is a faithful record
  of what was typed; it is not a promise that a config change three weeks later left it valid.
- **A multi-line answer becomes a one-line entry.** A SQL body pasted into a prompt is shown as it
  was stored, and a line-oriented listing cannot represent it as something retypeable.
- **The window is bounded.** It reads the last 250 command messages for that person (10 × 25) and
  finds the distinct commands in them. Someone who ran one command 300 times sees fewer than ten
  entries, and the listing does not say the window ended — only that the message-size budget did.
- **No outcome is claimed for a command that needed no prompt.** `command_status = 1` means
  dispatched, not succeeded; the real result of a `cli_execute` lives in `job_runs`.
  `/spbot_list_sql_runs` is the command that answers outcomes.
- Everything listed as still open in `v0.7.2` is still open. Nothing in this release touches the
  identifier scan, the store, or the schedulers.
